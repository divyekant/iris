Write documents

A producer is a program that writes documents of the open model. This page gives the rules for a producer, and the steps to check the output with the conformance kit.

Rules for a producer

  1. Write only the fields of the minor version that your program claims. For version 1.0, do not write account, the field of 1.1. For version 1.0 or 1.1, do not write withdrawn_by or comments, the fields of 1.2. For version 1.2 or older, do not write a draft action with a drafts target. For version 1.3 or older, do not write the ready value summary.
  2. Write the model value of that version: "iris/1.4", "iris/1.3", "iris/1.2", "iris/1.1" or "iris/1.0".
  3. Make sure that each document passes the schema of its kind, with the format checks of date and date-time.
  4. Do not write a key two times in one JSON object.
  5. Do not write NaN, Infinity or -Infinity.
  6. Write the text in UTF-8.

Frequent errors

ErrorCorrect value
An item has no source with the role origin, or has two.Exactly one source has the role origin, and it has a quote.

An amount as a number, for example 312.77.A money object: {"value": "312.77", "currency": "USD"}.
A date-time with no time zone, for example 2026-11-16T09:00:00.RFC 3339 with a zone: 2026-11-16T09:00:00Z.

Install the conformance kit

The kit checks your documents with no Iris code. You need Git and Python 3.11 or newer.

  1. Get the Iris repository: 
    git clone https://github.com/divyekant/iris.git
cd iris/docs/spec/conformance
  2. Make a virtual environment: 
    python3 -m venv .venv
  3. Install the libraries with their hashes: 
    .venv/bin/pip install --require-hashes -r requirements.txt

Check your documents

  1. Write the documents of your program into one folder.
  2. Give each file a name that starts with the name of its schema, for example commitment-1.json or signal-7.json. The text before the first - or . selects the schema.
  3. Run the check: 
    .venv/bin/python run.py check <folder>

These file names have a special meaning:

FileContent
<schema>-<n>.jsonOne document.
<schema>-<n>.jsonlOne document on each line (JSON Lines).
items.jsonlItems of each form. The form of each line selects the schema.
<name>.tomlA policy file. Each .toml file is a policy file.

The runner reads only the files at the top level of the folder. It prints one line for each document that fails.

Exit codeMeaning
0Each document passed, and the folder had one or more documents.
1One or more documents failed, or the folder had no document.
2The command is not correct, or the kit is not complete.

Your producer conforms when run.py check on its output exits with 0. If the runner says "newer than the kit", get the newest kit.

Try the sample producer

The kit has a sample producer in Python, with the standard library only. It reads three synthetic messages and writes a feed item and a signal. Use it as a start for your own producer.

  1. Write the documents: 
    python3 producer/produce.py /tmp/iris-out
  2. Check the documents: 
    .venv/bin/python run.py check /tmp/iris-out

The producer refuses a folder that exists. It writes into <folder>.partial, and renames the folder after the last file. A reader thus never sees a part of the output.

Use your own validator

You can check the documents with your own JSON Schema validator (draft 2020-12). Do these steps:

  1. Load each file docs/spec/schema/*.schema.json. A schema refers to common.schema.json by its $id (urn:iris:model:1:common).
  2. Turn on the formats date and date-time. You do not need to check email, because validators do not agree on it.
  3. Read each fixture file as one or more documents:
    • A .json file is one document.
    • A .jsonl file has one document on each line.
    • A .toml file is a policy file. Parse the TOML, and change each TOML date or time into RFC 3339 text, for example 2026-12-01. Validate the result with policy.schema.json.
  4. Select the schema of each document. The text of the file name before the first - or . names the schema, for example commitment for commitment-payment.json. In items.jsonl, the form of each line names the schema.
  5. Run the validator on each document in schema/examples/. Each document must pass.
  6. Run the validator on each file in schema/examples/invalid/. Each file must fail.

The runner does the same check of its own validator:

.venv/bin/python run.py self-test
