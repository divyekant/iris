# Spec: more than one account

- Date: 2026-11-17
- Card: R6-02
- Status: Agreed

## Problem

A person often has more than one mailbox: personal mail and work mail, for
example. Iris must keep each mailbox current in one data folder and show the
mail of all of them in one brief. The person must see the mailbox of each
item, because a reply or an action goes out from that mailbox.

## Goal

1. Two or more accounts live in one data folder. Each account has its own
   sign-in and its own sync.
2. The brief shows the items of all accounts in one list, and each item names
   its account.
3. The web client has one place that lists the accounts, with the state of
   each, and tells the person how to add one more.

## Not in scope

- Remove an account. A removal deletes mail from the store and needs its own
  spec (issue to file with the code PR).
- A filter of the brief by account. The brief stays one list.
- Providers other than Gmail. R6-10, R6-03 and R6-04 add them. This card does
  not change the inside of `iris-sync` or `iris-apply`.

## Design

What exists before this card (evidence: `crates/iris/src/engine.rs`,
`Engine::tick`):

- `iris account add <client.json>` adds an account for each new address, or
  signs in again to the account of a known address (`save_sign_in`).
- Each account keeps its own OAuth client and refresh token, sealed, in
  `account.token`.
- The engine starts one sync thread for each account with a sign-in. A slow
  or stopped account does not stop the others (test
  `a_stalled_account_does_not_stop_another_account`).
- Each row of the mirror (message, thread, label) has an `account_id`.
- The brief reads the items of all accounts. It has no account filter.

What this card adds:

1. **Test of two mailboxes.** The fake Gmail server gets `set_address`, so a
   test can run two fake mailboxes with two addresses. Both come from the same
   seed, so the Gmail IDs of messages, threads and labels are the same in both.
   The test syncs both accounts into one store and runs verify on each: zero
   differences. Then it changes one mailbox, syncs again, and checks that only
   the mirror of that account changed.
2. **The account of each item.** Open model version 1.1 adds the optional
   field `account` (an `a-` ID) to each item. The engine sets it from
   `item.account_id` when it reads an item, as it does for `matter`. Each
   output of an item (the API, the read verbs, the export, MCP) uses
   `iris_api::read::doc_at`, so each output gets the field. The output claims
   `iris/1.1`. Stored documents keep their `model` value. The engine replaces
   it on each read, because the row is the true copy.
3. **The client.** The brief shows the account of each item only when the
   store has two or more accounts. Accounts get a settings view. The layout
   is a decision for the owner (before/after page).

## Options not chosen

| Option | Why not |
|---|---|
| An item-to-account map next to the items in the brief answer, with no model change | Agents through MCP and the export would not see the account. IMAP and Outlook make the account a basic fact of each item. |
| A filter of the brief by account | The brief is one list of what needs the person. A filter can come later with no change to the data. |

## Failure list

| Input or event | Result |
|---|---|
| Two mailboxes with the same Gmail IDs | Each row stays with its account (test). |
| One account needs a new sign-in | Only that account stops. The others sync. The client shows the address that needs a sign-in (exists, `SignInNotice`). |
| A reader of model 1.0 reads an item of 1.1 | Spec 4, section 4: it shows the item and takes no action from it. |

## Impact

- Memory: one `String` (the `a-` ID) for each item that the engine outputs.
  No new thread, no new cache.
- No migration. `item.account_id` exists since schema 1.

## Assumptions

| Assumption | Evidence |
|---|---|
| Each item row has an account. | `schema_1.sql`: `item.account_id INTEGER NOT NULL`. |
| Each item output goes through `doc_at`. | `grep -rn "doc_of\|doc_at" crates`: each select of an item uses the column `MATTER`. |
| Two real Gmail accounts sync as the fakes do. | `pending`: the real check on the owner's Mac after R1-07 (2026-11-23). If it fails, the brief still shows only synced mail. |

## Acceptance criteria

- Two accounts sync with zero differences on the fake Gmail server.
- The brief shows the items of both accounts, each with its `account`.
- Each item output passes the schema of model 1.1.

## Verify

`cargo test -p iris --test engine two_accounts` and
`cargo test -p iris-api --test api the_brief_shows_the_items_of_each_account`.

## Rollout

Release gate: the real two-account check on the owner's Mac after R1-07.

## Risks

A program that checks items with the schemas of 1.0 refuses the new field.
Spec 4 says that such a reader shows the document and takes no action.
