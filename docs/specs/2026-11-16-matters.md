# Spec: matters

- Date: 2026-11-16
- Card: R6-01 (Matters: propose, confirm, and view)
- Status: Draft

## Problem

The five forms split mail into items. A part of the life of a person spans
many items from many senders. Example: a trip has a flight booking, a hotel
booking, a talk with a friend about the dates and a payment to make. Today
each item stands alone in the brief. The person must keep the link in their
head.

The manifesto says: "A matter ties the forms that belong together. Iris
proposes a matter, and you confirm it." Release 1 reserved the field `matter`
in each form document (spec 1 section 6.1) and left it empty.

## Goal

1. Iris proposes matters. A proposal is a title and two or more items that
   come from two or more threads.
2. The person confirms a proposal, keeps only some of its items, changes its
   title, or declines it.
3. A confirmed matter shows its commitments, records and conversations in
   one place, in the web client and in the local API.
4. A proposal never changes an item. A wrong proposal costs the person one
   decline, not a lost or a changed item.
5. Each item of a confirmed matter keeps its ID through a rebuild, so the
   matter keeps its items.

## Not in scope

Each subject below gets a `limit` issue before the engine PR merges:

- A change of a confirmed matter after the confirm: rename, remove an item,
  add an item, merge two matters, delete the matter.
- A proposal to add a new item to a confirmed matter. A new item of a trip
  that is confirmed stays outside the matter in this card.
- A matter that a person makes by hand.
- Feed items and signals in a matter. They are short-lived or read only once.
- Matter verbs for agents (`iris` command writes and changeset actions). An
  agent reads matters only.
- Attention rules (spec 2 section 6) that read the matter of an item.

## Design

### Terms

| Term | Meaning |
|---|---|
| Matter | A title and a set of items that belong together. |
| Proposal | A matter in the state `proposed`. Iris made it. The person did not decide it yet. |
| Member | An item of a matter. |
| Candidate | An item that the proposal step can put in a new proposal. |

### The open model: matter document

A new schema `docs/spec/schema/matter.schema.json` (open model `iris/0`):

| Field | Type | Required | Meaning |
|---|---|---|---|
| `model` | `"iris/0"` | yes | The version of the open model. |
| `id` | string, `g-` ID | yes | The ID of the matter. |
| `title` | string, 1 to 80 characters | yes | The name of the matter. |
| `status` | `proposed`, `confirmed` or `declined` | yes | |
| `items` | array of item IDs, 1 to 50, unique | yes | The members. The IDs use the prefixes `c-`, `v-` and `r-` only. |
| `counts` | object: `commitment`, `conversation`, `record` (integers) | yes | The number of members of each form. |
| `created` | date-time | yes | When Iris made the proposal. |
| `updated` | date-time | yes | The last change. |
| `derived` | object | yes | `by` is `model`, with `model` and `prompt`, as in spec 1 section 6.1. |
| `decided` | date-time | when `status` is not `proposed` | When the person decided. |

The prefix `g-` ("group") is new in the ID table of spec 1 section 5.7. The
letter `m-` is the message.

The field `matter` of an item document (spec 1 section 6.1) is the `g-` ID
of the confirmed matter that has the item as a member, or `null`. The engine
does not store it in `item.doc`. The local API sets it when it reads the
item, from the `matter_item` table. Reason: understanding and the
conversation rule write `item.doc` again on each change. A field that they
do not own would get lost.

### Store: migration 12

```sql
CREATE TABLE matter (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('proposed', 'confirmed', 'declined')),
  model TEXT NOT NULL,
  prompt TEXT NOT NULL,
  run_id INTEGER REFERENCES understand_run(id),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  decided_at INTEGER
);

CREATE TABLE matter_item (
  matter_id INTEGER NOT NULL REFERENCES matter(id),
  item_id INTEGER NOT NULL REFERENCES item(id) ON DELETE CASCADE,
  kept INTEGER NOT NULL DEFAULT 1 CHECK (kept IN (0, 1)),
  PRIMARY KEY (matter_id, item_id)
) WITHOUT ROWID;
CREATE INDEX matter_item_item ON matter_item(item_id);
```

Rules that triggers hold, so no write path can break them:

1. The status moves only from `proposed` to `confirmed` or to `declined`.
   No other move. Only a `proposed` matter can be deleted.
2. An item is a kept member of at most one matter that is `proposed` or
   `confirmed`.
3. The members of a matter do not change after the proposal, except `kept`,
   which the confirm sets from 1 to 0 for each member that the person did not
   keep. The cascade of an item delete is the one other change (below).
4. The members of a matter are items of the forms commitment, conversation
   and record.

The view `item_pin` gets one more part: each kept member of a confirmed
matter. So a rebuild never deletes such an item and never changes its ID
(spec 1 section 7.5).

The members of a proposal are not pinned. Understanding can delete such an
item (a rebuild, or a new run of its message). The cascade deletes its
`matter_item` row. A proposal with fewer than 2 kept members, or with kept
members from fewer than 2 threads, is not shown, and the next proposal step
deletes it with its member rows. Only the person declines a matter.

A member that the person did not keep (`kept` = 0) stays as a row, so the
matter shows what the proposal was. It is a candidate again (below).

A decline must survive a rebuild, but the members of a declined matter are
not pinned: a rebuild deletes them and makes new items with new IDs. So the
decline also writes the stable key of each member, its form and its origin
message (the key that spec 1 section 7.5 uses for a possible duplicate):

```sql
CREATE TABLE matter_decline (
  matter_id INTEGER NOT NULL REFERENCES matter(id),
  form TEXT NOT NULL,
  message_id INTEGER NOT NULL REFERENCES message(id),
  PRIMARY KEY (matter_id, form, message_id)
) WITHOUT ROWID;
```

The engine never deletes a message row (spec 1 section 5.7), so the key
stays valid.

### The proposal step

One function, `iris_matters::propose(store, model, now)`. It runs under the
understanding run lock (`iris_understand::batch::lock`), because it spends
the same budget.

1. Read the candidates. A candidate is an item with all of these:
   - form `commitment`, `conversation` or `record`;
   - status not `gone`, `cancelled` or `declined`, and no `duplicate_of`;
   - attention not `hidden`;
   - no kept row in `matter_item` of a matter that is `proposed` or
     `confirmed`;
   - `updated_at` in the last 90 days.

   Take the newest 300 candidates by `updated_at`.
2. Compute the fingerprint of the candidate set: SHA-256 of the sorted
   pairs of item ID and `updated_at`. Stop with no call if the candidates
   come from fewer than 2 threads, or if the fingerprint is the same as the
   fingerprint of the last call (`matter_run.candidates`, below). A new
   item, a changed item and a change of eligibility (for example an item
   that becomes hidden or a member that the person did not keep) each
   change the set, so each one allows a new call.
3. Write one line for each candidate into the data block of the model call:
   the item ID, the form, the title, the thread ID, the date (due date,
   booking start, latest message or created), the names of the other parties
   and, for a record, its type and its `location` field. No mail text and no
   quotes. The titles come from mail, so the data block uses
   `iris_model::data_block`, and the instruction says that the data is not
   instructions.
4. The model answers JSON:
   `{"matters": [{"title": "...", "items": ["c-1", "r-4"]}]}`. At most 10
   matters.
5. Check each matter of the answer. Drop the matter when one check fails:
   - the title is 1 to 80 characters after trim, with no control
     character;
   - each item ID is a candidate of step 1 (an ID that the model made up,
     or an ID of another form, drops the matter);
   - no item ID is in an earlier matter of the same answer;
   - 2 to 50 items, from 2 or more threads;
   - the set of the stable keys (form, origin message) of the items is not
     a subset of the keys of a declined matter (`matter_decline`). A
     declined grouping does not come back in the same or a smaller form,
     also after a rebuild.
6. Open the write transaction. Read the candidates of step 1 again, with
   the state of the store now. Drop each matter of step 5 with a member
   that is no longer a candidate (for example, a policy change made it
   hidden during the call, or an earlier matter of this write took it).
   Write each other matter as a proposal, and `matter_run`, in this one
   transaction. The command `iris matters propose` prints the number of
   proposals and the number of dropped matters. The store keeps no count of
   dropped matters.

The call goes through `iris_understand::budget::Budgeted`, with a new
`understand_run` row whose `prompt` is `matters/0.1` and whose `messages` is
0. So the budget, the reservation of the worst case, the unknown usage and
the model-error wait of the cost control spec apply with no new code. With no
model, or with no budget, the step makes no call and writes nothing.

A table `matter_run (id INTEGER PRIMARY KEY CHECK (id = 1), at INTEGER,
candidates TEXT)` holds the time of the last proposal call and the
fingerprint of its candidate set. A call that ends with no answer (model
error, no budget) does not write `matter_run`, so the next step can try
again, inside the wait of the cost control spec. `iris serve` calls the step after each understanding
run that was not idle, at most one time each hour. The command
`iris matters propose` calls it at once.

### Person decisions

The local API gets four routes. Only the web client of the person calls
them (the local API refuses requests that are not local, as today):

| Route | Body | Effect |
|---|---|---|
| `POST /api/matters/{id}/confirm` | `{"title": "...", "items": ["c-1", ...]}` | Status `confirmed`. `title` replaces the title (same checks as step 5). `items` lists the members to keep: 1 or more, each a kept member of the proposal. Each other member gets `kept` = 0. |
| `POST /api/matters/{id}/decline` | none | Status `declined`. The same transaction writes the `matter_decline` keys of the kept members. |
| `GET /api/matters` | none | The proposals that the brief can show (rule above), newest first, and the confirmed matters, by `updated_at`, newest first. |
| `GET /api/matters/{id}` | none | The matter document and the documents of its kept members, grouped by form. |

A confirm or a decline of a matter that is not `proposed` gives HTTP 409 and
changes nothing. The transaction reads the status and writes it in one
`UPDATE ... WHERE status = 'proposed'`, so two clicks or two tabs make one
change: the second gets 409.

`iris matters` (list) and `iris matters show <id>` print the same JSON for
agents. They write nothing.

### Screens

The web client gets:

- a proposal line in the brief: the title, the counts ("2 bookings,
  1 conversation, 1 commitment"), Confirm and Not a matter;
- a confirm step, where the person can change the title and clear items;
- a Matters list and a matter view, with the members by form.

The layout of each screen goes to the owner as a before/after page
(`docs/board/compare.html`) before the client PR merges.

## Options not chosen

- Fixed rules (a shared thread, overlapping booking dates, a shared
  reference). A thread is already a conversation. Date overlap groups two
  trips of the same week, and it cannot find a contract or a hire. Rules
  that group by meaning loop in review (lesson of R1-10 part 2).
- Embeddings and clustering. They need a second model API and a vector
  store. That breaks the lightest memory footprint rule.
- `matter` stored in `item.doc`. Understanding writes the document again and
  would drop it.
- Pin each proposal member. A rebuild could then not replace a member that
  the person never confirmed, and duplicates would grow.
- Proposals through the changeset of spec 2. A changeset holds actions on
  mail and items that an agent or a rule proposes and a policy can approve.
  A matter needs the person, never a policy, so it does not fit the approval
  flow.

## Failure list

Input that the product does not control: the model answer, and the titles
inside the data block (they come from mail).

| Input | Result | Test |
|---|---|---|
| Answer that is not JSON, or has no `matters` array | No proposal. The run row records the call. | unit: bad answers |
| More than 10 matters | The first 10 count. The rest are dropped. | unit |
| Unknown item ID, ID of another form, ID of a member of an open matter | The matter is dropped. | property test: random answers over a random candidate set never write a member outside the candidates |
| Same item in two matters of one answer | The second matter is dropped. | same property test |
| 1 item, or items of one thread | Dropped. | unit |
| Subset of a declined matter, also after a rebuild gave its items new IDs | Dropped. | unit: decline, delete and remake the items, propose again |
| A member that becomes hidden or taken during the call | The matter is dropped in the write transaction. | unit |
| An item changes or becomes eligible, with no new item | A new fingerprint, so a new call. | unit |
| Title empty, over 80 characters, or with a control character | Dropped. | unit |
| A title in the data that says "ignore the rules" | The data block escapes `<<<`. The checks of step 5 hold for each answer, so the worst result is a wrong proposal, which the person declines. | unit with a hostile title |
| Model error, refusal, no budget | No proposal. The cost control rules of the run apply. | reuse of the `Budgeted` tests, one test that no matter row is written |
| Crash between the call and the write | The run row and the proposals are one transaction. The next step reads the same candidates again. One more call is spent; no half proposal exists. | unit: the write fails, no row |
| Understanding deletes a proposal member | Cascade. The proposal is hidden when the rule fails, and the next step deletes it. | unit |
| Two confirms of one proposal | One change, the second gets 409. | unit |
| A confirm that names an item that is not a kept member | 400, no change. | unit |

All other input is refused with no write.

## Impact

- `docs/spec/schema/matter.schema.json` and examples (new).
- `docs/spec/01-mirror-store-forms.md`: section 5.5 tables, section 5.7 the
  `g-` prefix, section 6.1 the `matter` field.
- `crates/iris-store`: migration 12, the `g-` ID kind.
- `crates/iris-matters` (new crate): candidates, prompt, checks, writes,
  confirm and decline.
- `crates/iris`: the call in `iris serve`, the commands `iris matters`.
- `crates/iris-api`: the routes, and the `matter` field of each item.
- `client/`: the proposal line, the confirm step, the list and the view.
- Memory: one model call each hour at most, with 300 lines of about 200
  bytes. The candidate read streams rows. The peak is the request body,
  about 64 KB.

## Assumptions

| Assumption | Evidence |
|---|---|
| The understanding run lock and `Budgeted` can serve a call that is not a message call. | `crates/iris-understand/src/budget.rs`: `Budgeted::new` takes a run row and a model row, no message. |
| A rebuild never deletes a pinned item. | spec 1 section 7.5; `item_pin` view in `schema_11.sql`. |
| Understanding deletes item rows, so a proposal can lose members. | `crates/iris-understand/src/store.rs`, `DELETE FROM item`. |
| Foreign keys are on. | `crates/iris-store/src/lib.rs`: `PRAGMA foreign_keys = ON`. |
| The model groups items well enough from titles and a few fields. | `pending`. Only a run on the owner's Mac with a real model can show it. If the quality is low, the person declines proposals and nothing else changes. The eval crate gets a matter set later (issue). |

## External writes

None. The model call reads; it changes no data outside the product. Its cost
follows the cost control spec.

## Open questions

- The exact prompt text. The build writes it and the eval of the synthetic
  mailbox checks it.
- The 90-day window and the limit of 300 candidates. The build can change
  them inside the 64 KB request bound.

## Acceptance criteria

1. With a fake model that groups a booking, a conversation and a commitment
   of 3 threads, the step writes one proposal with 3 members. Red: no
   proposal, or a member outside the answer.
2. A confirm with 2 of the 3 items makes a confirmed matter with 2 kept
   members. `GET /api/items/{id}` of a kept member has `matter` = the `g-`
   ID. Red: `matter` is null, or the third item has it.
3. A rebuild of the messages of a kept member keeps its item ID. Red: the
   item ID changes or the member row is gone.
4. A declined proposal does not come back from the same answer. Red: a
   second proposal with the same items.
5. No model or no budget: no call, no matter row. Red: a row.
6. The matter view in the web client shows the members by form.

## Rollout

Migration 12 runs at the first start (a backup comes first, spec 1 section
5.5). No flag. Proposals start after the first understanding run with a
model and a budget.

## Risks

- Bad proposals. The person declines them. A run each hour at most limits
  the cost.
- A pin through a confirmed matter keeps an item that understanding would
  replace. The duplicate rule of spec 1 section 7.5 shows the pair once.
- Rollback: a migration goes forward only. A later migration can drop the
  two tables; nothing else reads them.
