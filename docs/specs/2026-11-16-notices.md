# Spec: Notices by rule

- Date: 2026-11-16
- Card: R5-08
- Status: Agreed

## Problem

Iris is quiet by default (manifesto, principle 3). But some mail must reach
the person at once: a mail from a doctor, a reply from a lawyer, a code from
the bank. Today the person must open the brief to see it. The manifesto
gives the capability "Notices: an interrupt only when a rule of yours
matches" to release 5.

Decision D24 adds one more interrupt that no rule writes: the due date
that the person gave to a job (`docs/specs/2026-11-24-job-due-date.md`).

## Goal

A rule of the effect `notify` in `policy.toml` gives one notice for each new
mail that it matches. The notice shows in the web client and in the system
of the computer that runs Iris. No mail notice appears without a rule that
matches (the `doneWhen` of the card). The system notice of a due job
(decision D24) is not a mail notice, and this rule does not apply to it.

## Not in scope

- A notice for each watch (card R5-07 has its own notice in the brief).
- Push to a phone, mail or a chat service.
- The Notification API of the browser. The system notice of the engine
  reaches the same screen, with no permission prompt, also when no browser
  tab is open.
- A form in the web client to add a `notify` rule (issue #146 covers each
  effect). The person adds the rule in the file.

## Design

### The rule

Spec 2 section 6.2 gets the effect `notify`. It is an attention effect, as
`hide` and `bundle`: no `verbs`, no `author`, no `job`. Its conditions are the
conditions of section 6.2.

```toml
[[rule]]
id = 7
name = "Mail from the clinic"
effect = "notify"
when = { sender = "@clinic.example" }
by = "person"
added = 2026-11-16
```

A `notify` rule does not change the attention of an item. It is apart from
`hide` and `bundle`: an item can be hidden and still give a notice, because
the person wrote both rules. The evaluation of actions does not read
`notify` rules.

A `notify` rule matches a message when its `when` matches the message with
the reading of a `review` rule (section 6.2): an item condition matches when
one or more items of the message have the value. A rule without an item
condition matches a message with no items too.

### A new mail

A message gets a notice when all of these are true:

1. It came into the mirror one hour ago or less (`fetched_at`), or the
   understanding wrote its items one hour ago or less (`understood_at`) and
   it came into the mirror 24 hours ago or less. So a rule on a form waits
   for a late model result, and an interrupt never comes a day late.
2. Its date (`internal_date`) is at most one hour before `fetched_at`. So the
   old mail of a first sync, of a full resync or of a fetch again does not
   give a notice.
3. It has a `body` row, and no `link_check` row. The understanding step
   writes the body, the header and the hostile marks in one write, with no
   model. The link check of spec 1 section 6.7 removes the `link_check` row
   (migration 20: mail saved before the mark `link`, new content, and mail
   that loses the label `SENT` or `DRAFT`). So the hostile checks ran.
4. At the time of the pass, it has no hostile mark, and its sender is not of the kind `hostile`. This
   is a hard limit (spec 2 section 6.5): a rule cannot give a notice for
   hostile mail, because a notice is the place where a phishing mail does
   the most harm.
5. It has no label `SENT`, `DRAFT`, `SPAM` or `TRASH`, and no IMAP label
   `UNSENT` or `SENT_COPY` (`iris_store::draft_or_copy!`, IMAP provider
   spec section 4). A notice is for mail that you get, and Gmail can move a
   mail to `SPAM` after the body came.
6. It is not gone.
7. A `notify` rule of the active policy matches it.
8. It has no notice yet.

The pass reads each guard in the transaction that writes the notice, so a
guard reads the store as it is at the time of the notice, not at the time of
the body.

A notice is a record of one interrupt. It keeps the rule and the policy
version that matched when the pass made it. A later change of the policy, or
of a fact of the mail, does not withdraw it: the person got the interrupt
already. The person marks it done.

A message that matches no rule now stays a candidate for its hour. So a rule
on a form gives the notice when the model writes the items, and a rule that
the person adds gives a notice for the matching mail of the last hour.

### Data

Store migration 17 adds:

- The table `notice`: `id`, `message_id` (unique, no foreign key, so the
  cleanup of gone mail keeps the notice), `rule`, `rule_name`,
  `policy_version`, `title`, `text`, `created_at` and `done_at`. `rule_name`,
  `title` and `text` keep the words of
  the notice, so the notice still reads when the mail is gone.
- The indexes `message_fetched` on `message(fetched_at)` and
  `message_understood` on `message(understood_at)`.

The ID of a notice is `n-<row>`.

### The pass

`iris_policy::notice::refresh(store, now_ms)` runs in the attention thread of
`iris serve`, each 10 seconds. One write transaction reads the active policy
and the candidates (the two indexes), and inserts one row for each
message that a rule matches, with `INSERT ... ON CONFLICT(message_id) DO
NOTHING`. If more than one rule matches, the rule with the lowest ID names
the notice. The pass gives the new rows.

The words:

- `title`: the name of the sender, else the address, else "Unknown sender".
- `text`: the subject, else "(No subject)".

Each is one line: control characters become spaces, and at most 200
characters stay.

### The system notice

For each new row, Iris shows one system notice, with the text
"<title>: <text>". A notice of the engine has the title "Iris: <rule name>".
A notice of the Mac app has the title "<rule name>", because macOS shows
the name of the app above it. If the notice API of the app fails, the app
uses the command and the title of the engine. The Mac app shows the
notices after its start while it polls the engine (socket verb
`app.notices`), and the engine shows all others. The engine decides before it puts
the notice in the queue of its notice thread: the rule and the lock are in
`docs/specs/2026-11-17-mac-app.md`, part 2. The engine shows its notices
with these commands:

| System | Command |
|---|---|
| macOS | `/usr/bin/osascript -e 'on run argv' -e 'display notification (item 2 of argv) with title (item 1 of argv)' -e 'end run' <title> <text>` |
| Linux | `notify-send --app-name=Iris <title> <text>`, from `PATH` |

The words go as arguments, never in the script or a shell line. Mail text is
data. The engine waits at most 5 seconds for the command. If the command is
not there (a server with no desktop) or fails, the engine writes one line to
its log the first time, and the notice stays in the web client.

### The web client

- `GET /api/notices`: the notices that are not done, newest first, at most
  50, each with `id`, `rule`, `rule_name`, `title`, `text`, `created`, and
  `message` (the summary of the mail, or null when the mail is gone).
- `POST /api/notices/{id}/done`: sets `done_at`. A notice that is done
  already gives 200. An unknown ID gives 404.

The web client shows each notice that is not done above every view, with a
Done control. The look is the choice of the owner (before/after page).

The Rules screen gets the group "Notify" for the `notify` rules.

## Options not chosen

- A notice for each new item: one mail with three items would give three
  notices. One notice for each mail is enough.
- The Notification API of the browser: it needs a permission prompt and an
  open tab, and on the Mac it shows the same notice two times.
- A check of the message row ID, as the watch does: a message row ID does
  not tell when the mail came, and the engine can be off for hours.
  `fetched_at` with the date check does.
- A crate for desktop notices (`notify-rust`, `mac-notification-sys`): both
  pull a D-Bus or an Objective-C stack into the one program for one call.
  The two system commands do the same work with no dependency.

## Failure list

Supported input: a valid `policy.toml` (spec 2 section 6), and mail of the
mirror. Mail text is input that Iris does not control.

| Input or event | Result | Test |
|---|---|---|
| No `notify` rule matches | No notice. | `no_notice_without_a_rule_that_matches` (property) |
| Old mail of a first sync or a resync | No notice (date check). | `old_mail_gives_no_notice` |
| Hostile mail, a hostile sender, sent mail, a draft, `SPAM` or `TRASH` mail (also when the label came after the body), gone mail, no body yet | No notice. A message with no body yet gets the notice after the body comes, inside its hour. | `unsafe_mail_gives_no_notice` |
| Two passes, or two engine processes | One notice for each message (unique `message_id`). | `one_notice_for_each_message` |
| A subject with line breaks, control characters or 10,000 characters | One line of at most 200 characters. | `notice_words_are_one_short_line` |
| A subject with quotes or AppleScript or shell text | It goes as one argument. No script or shell reads it. | `system_notice_passes_words_as_arguments` |
| No `osascript` or `notify-send`, or the command fails or hangs | One log line. The web client still shows the notice. | `a_missing_command_logs_once` |
| A slow or hung notice command, or many new notices at one time | The system notices run on their own thread, one at a time, from a queue of 100. The pass never waits for them. A notice that finds the queue full gets no system notice; the web client shows it. | `slow_system_notices_never_hold_the_sender` |
| A crash after the insert and before the system notice | The web client shows the notice. The system notice does not come. | By construction (the row is committed first) |
| The person removes or changes the rule after the notice | The notice stays, with the rule and the version of its time, until the person marks it done. | `a_notice_keeps_the_rule_of_its_time` |
| An invalid policy file | The active policy stays (spec 2 section 6.3). | Existing tests |
| Any other input | No notice. | |

## Assumptions

- `fetched_at` is the time of the last fetch of the content, in milliseconds.
  Evidence: `crates/iris-sync/src/lib.rs` (`fetched_at: Some(now_ms())`) and
  the upsert in `crates/iris-store/src/lib.rs`.
- The body, the header and the hostile marks come in one transaction.
  Evidence: `crates/iris-understand/src/store.rs`, write 1 (the watch spec
  uses the same fact).
- `osascript` can show a notice from a launchd user agent. Evidence: pending
  (check on the owner's Mac). If it is wrong, the notice stays in the web
  client only.

## External writes

None. The system notice is a local command with no state outside Iris.

## Open questions

None.

## Acceptance criteria

- No mail notice appears without a rule that matches. The system notice of
  a due job (decision D24) is exempt. Red if the property test
  finds a notice whose message no `notify` rule of the policy version of the
  notice matched at the time of the pass.
- One mail gives at most one notice. Red if a second pass adds a row.
- Mail text never runs. Red if the words of the notice go into the script or
  a shell line.

## Rollout

Migration 17 runs at the first start of the new version. With no `notify`
rule, nothing changes.

## Risks

- A mail that comes more than one hour after its date gives no notice
  (issue #318).
- Phishing that only the model finds can give a notice before the model
  call, as for a watch (issue of R5-07).

Rollback: remove the pass and the routes. The table can stay.
