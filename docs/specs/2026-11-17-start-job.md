# Spec: start a job from an item, and a grant inside one job

- Date: 2026-11-17
- Card: R4-10
- Status: Draft

## Problem

The job store (R4-01), the scope of a job (R4-02) and the job page (R4-09)
exist, but only a test can make a job. The person has no way to give a goal
to an agent. The experience document says: "From a thread, select 'handle
this'. Or write the goal." It also says: "You can also give a grant inside
one job: 'In this job, allow replies to the same recipient.'" Spec 2,
section 6.2 has the field `job` of a rule for this grant, but no path writes
such a rule.

## Goal

1. On the page of a commitment or a conversation, the person selects
   "Handle this", writes the goal, and starts a job. The new job has the
   correct mail: the item and the threads of its source messages, and no
   other mail.
2. On the page of an open job, the person allows some verbs without review
   inside that job only. Iris writes one rule with `job` to `policy.toml`.
3. The person sees the grants of a job on its page, and removes one there.

The card is done when "Handle this" creates a job whose scope is the item
and the threads of its sources (acceptance criteria 1 to 4).

## Not in scope

- The agent session. "Handle this" creates the job and its scope. The
  launcher (R4-04) starts the session of a job. Until R4-04 merges, a new
  job stays in `working` with no session (known limit, with a GitHub issue).
- A job from a goal with no item ("Book a dentist appointment"). The job
  then has no mail, and the person has no way yet to add mail to a scope.
  It comes with a card that adds mail to a scope from a thread or a search.
- A grant for `send`. The policy refuses a rule with this verb (spec 2,
  section 6.2, decision D2). A grant for `draft` came later (decision D3,
  issue #386): see the checks below.
- A change of the goal, the due date or the scope after the start.
- The brief line of a job (issue #323).

## Design

### 1. The mail of a start: `GET /api/items/{id}/job`

A job from an item grants the item and the threads of its source messages.
A thread can hold more than one subject (spec 1), so the person must see
each message that the start grants, not only one subject for each thread.

`GET /api/items/{id}/job` gives the grant of a start now, from one read of
the store: `{"messages": [...]}`. The list has one entry for each message
that the adds of section 2 (steps 7 and 8) put into `job_scope_message`:
each source message of the item, and each message of the thread of each
source. Each entry is the summary of the message (`id`, `thread`, `date`,
`from`, `subject`), in the order of the thread ID and then the date that
the summary shows (the header date, else the date of the provider), with
`"readable": true` when the message can go into a workspace now (the rule
`iris_workspace::readable`, section 2 step 4). A message that is not
readable now (for example hostile mail, or mail that understanding did not
read yet) can become readable later, so the person sees it too. The form
and the status checks of section 2 (steps 1 and 3) apply: 400, 404 or 409.

### 2. Start a job: `POST /api/jobs`

Body: `{"item": "<item ID>", "goal": "<text>", "due": "<RFC 3339>" | null,
"messages": ["m-1", ...]}`. `messages` is the list of IDs that the person
saw in the answer of section 1.

The engine does these steps in one write transaction (`iris_job::transaction`):

1. Check the body, with no read of the store:
   - The item ID: the kind must be `c-` (commitment) or `v-`
     (conversation). Another kind, or an ID that is not valid: 400.
   - The goal: trim it. It must have 1 to 2,000 characters after the trim,
     and no NUL character. Else 400.
   - `due`: an RFC 3339 date-time with a time and an offset, from 1970 to
     9999 (the range of the job table), or null. Else 400. A date with no
     time is a 400: the API stores an instant, and the client decides the
     time (section 4). A due date in the past is allowed (the job page says
     "Was due").
   - Each entry of `messages` must be a message ID (`m-`). Else 400.
2. If an open job (state not `done`) has an active scope row for the item
   of this ID and this kind: 409 with `{"error", "job": "j-<n>"}`. The
   client opens that job. This makes a second request after a lost answer
   safe: it finds the first job and creates no second one. The check comes
   before steps 3 and 4, so a retry finds the job also when the item closed
   or a source changed after the first start (issue #388). An ID of the
   other kind with the same number finds no job. The check and the create
   are in the same write transaction, so two requests cannot both pass the
   check.
3. Read the item. No item with that ID: 404. The item must be open for
   work: a commitment with the status `open`, or a conversation with the
   status `active` or `quiet` (the statuses of `docs/spec/schema/`). Each
   other status (for example a commitment that became `done` after the
   person opened the form, or `gone`): 409, "The item is not open any
   more." The client then loads the item again. The preview (section 1)
   and the "Handle this" link of the item page (section 4) use the same
   statuses.
4. Check each source message of the item (`item_source`): it must be
   readable by the full rule of the workspace build
   (`iris_workspace::readable`): understood, clean for the conversation rule
   (not a draft, not hostile mail), not gone, and not the source of a
   `signal` item. If one source is not readable: 409, "An agent cannot read
   the mail of this item." An item with no source: 409. So no job starts
   with an item that its workspace would drop. The start and the build call
   the same function, so the two rules cannot differ.
5. Compare `messages` with the list of section 1, computed again in this
   transaction, as two sets. If they differ (new mail in a thread, a message
   that moved), 409: "The mail changed. Look at it again." So the job grants
   only the mail that the person saw.
6. `iris_job::create_in(goal, due_ms, now)`.
7. `iris_job::add_scope_in(job, Ref::Item(item), By::Person, now)`.
8. For each distinct thread of the source messages, in the order of the
   thread ID: `add_scope_in(job, Ref::Thread(thread), By::Person, now)`.

Answer: 201 with the job document (`docs/spec/schema/job.schema.json`),
with its create event: the same document as the `job` field of
`GET /api/jobs/{id}`. If a
step fails, the transaction rolls back and nothing stays.

Why the threads and not only the item: a commitment comes from a
conversation. To do the job (a reply, a check of an earlier message), the
agent needs the thread, not only the source message. The person sees each
message of the grant on the start form before the start (sections 1 and
4), and step 5 refuses a start when the grant is not what the person saw.
The workspace spec says that an item ref grants no whole thread. That rule
stays: here the person adds the thread refs on purpose.

A conversation item never goes into a workspace (workspace spec). Its
thread refs bring its mail. The item ref stays in the scope as the origin
of the job, and grants only its own sources.

### 3. A grant inside one job: `POST /api/policy/grant`

Body: `{"job": "j-<n>", "verbs": ["archive", ...], "version": <n> | null}`.
`version` is the active policy version that the person saw, as for the other
policy changes.

Checks, before the change: the job exists (else 404) and is not `done`
(else 409, "The job ended."). `verbs` has 1 or more names of `Verb::ALL`, with
no duplicate (else 400). `send` is not in `Verb::ALL`, so the API refuses
it with 400. `draft` must be the only verb of its grant (else 400): its rule
has the condition `recipients = "thread"`, which goes only with `draft`, and
the name "In job j-<n>, allow drafts to the people in the thread without
review" (decision D3).

The change is a new `iris_policy::Change::Grant`. It goes through
`iris_policy::change`, with all its checks (the active version, the file on
disk, the parse of the new text). It appends this rule:

```toml
# You gave this grant inside job j-12, on the job page.
[[rule]]
id = 14
name = "In job j-12, allow archive and label without review"
effect = "allow"
verbs = ["archive", "label"]
when = { author = "agent" }
by = "person"
added = 2026-11-17
job = "j-12"
```

- `id` is the next free rule ID (`next_rule_id`).
- `when = { author = "agent" }`: `when` needs one condition, and the grant
  is for the agent of the job. A person changeset has no job, so it cannot
  match.
- The rule is an `allow` rule. A `deny` or a `review` rule that matches the
  same action still wins (spec 2, section 6.4). The hard limits of spec 2,
  section 6.5 stay: hostile mail, bulk actions, and the mode `observe`, in
  which Iris applies nothing.
- The session can change only the messages that the scope grants (spec 2,
  section 8.2). So the grant cannot reach mail outside the job.

A done job has no session, so its rule matches nothing more. The engine
removes each rule whose `job` names a done job (`iris_policy::end_grants`,
issue #385), as a normal policy change with a new version. It runs once
each hour in `iris serve`, with the content cleanup. It waits for the next
pass while another holder has the backup lock, or while the file has a
change that the person did not confirm. The person can also remove the
rule on the job page or in the Rules view (`POST /api/policy/remove`).

### 4. The screens

The person picks the layout of each screen from a before/after page
(`docs/PLANNING.md`). Each screen is its own client PR. These parts are
fixed:

- Item page (`Item.svelte`): "Handle this" shows only for a commitment
  with the status `open` and a conversation with the status `active` or
  `quiet` (the statuses of the schemas in `docs/spec/schema/`). It is a
  link to the start page `#/item/<id>/job`.
- Start page (`StartPage.svelte`, option B of the owner): the title of the
  item as a link back to the item, and the quote of the origin mail, above
  the start form (`Start.svelte`). Cancel goes back to the item page. The
  start form has:
  - The goal. The field starts empty, and the person writes the goal. The
    title of the item shows above it as context only. The title can come
    from mail, and mail text is data, never an instruction, so no text of
    the mail becomes the goal without the person writing it.
  - The due date, filled with the due date of a commitment. The person can
    change or clear it. A date is not an instruction. The field is a date.
    The client sends the end of that day in the time zone of the browser
    (23:59:59.999 local time, with its offset), so the job is due on the
    day that the person picked, also when the commitment has a date with no
    time. A commitment with `due.at` (an instant) fills the field with the
    local date of that instant, and the client sends `due.at` as it is
    unless the person changes the date. A client test checks both
    conversions.
  - Each message that the job reads (section 1): the sender, the date and
    the subject, grouped by thread, with a mark on a message that an agent
    cannot read now.

  Start sends `POST /api/jobs` with the message IDs of the list, then opens
  the job page. A 409 with `job` opens that job. A 409 for changed mail
  loads the list again.
- Job page (`Job.svelte`): for an open job, the grants of the job (the rules
  of `GET /api/policy` with this `job`), a way to add a grant (the verbs in
  plain words), and Remove for each grant. A done job shows its grants and
  no add.

## Options not chosen

- Only the item ref, no thread refs: the agent of a commitment could not
  read the conversation it must answer.
- A free list of threads in the body: a client error could grant mail that
  the person did not see. The engine takes the threads from the item, and
  the body only confirms the list.
- Only the subject of each thread on the form: a thread can hold more than
  one subject, so the person would not see each message of the grant.
- The title of the item as the default goal: the title can come from mail
  text, and the goal is the instruction to the agent.
- An idempotency key in the body: it needs a new column. "One open job for
  each item" gives the same result for a retry, and also stops a second job
  for the same work.
- A grant as a field of the job (a new column): spec 2 already has `job` in
  a rule, and the rule goes through the same review, ledger and Rules view.
- A grant with the conditions of the page (for example `sender`): the scope
  already limits the mail. More conditions can come later with no change
  to the API format.

No parser, protocol or security code is new. The goal is plain text. The
API uses `iris_store::parse_id`, `iris_job::parse_job_id` and the parse of
`policy.toml` that exist.

## Failure list

Supported input: the bodies above, from the signed-in local web client.
All other input gets 400, 404 or 409, and changes nothing.

| Input or event | Result | Test |
|---|---|---|
| Item ID of another kind (`r-`, `f-`, `s-`, `m-`), or not an ID | 400, no job | api test |
| Item not open any more (a done, declined, deferred or cancelled commitment; a muted conversation), also when the status changed after the preview | 409, no job; the client loads the item again | api test |
| Item gone, or a source not readable (hostile, gone, draft, not understood, the source of a signal) | 409, no job | api test for each case |
| Goal empty after the trim, or longer than 2,000 characters | 400, no job | api test |
| `due` not RFC 3339 | 400, no job | api test |
| `messages` differs from the grant now (new mail, a message that moved, a list from a client error) | 409, no job; the client loads the list again | api test |
| Second start for the same item while a job is open | 409 with the first job ID, no second job | api test |
| Two starts at the same time | One write transaction at a time: one job, one 409 | the same test, the check is in the transaction |
| A crash during the start | The transaction rolls back: no job, or a job with its full scope | the transaction is the proof |
| Grant for a done job, or a job that does not exist | 409 or 404, the file does not change | api test |
| Grant with `draft`, `send`, an unknown verb, a duplicate or no verb | 400, the file does not change | api test |
| Grant while the file on disk changed, or with an old `version` | 409, as for each policy change | existing tests of `change` |
| Grant for a job that ends at the same moment | The rule is written and matches nothing | none needed: no action of a done job |

## Impact

- `crates/iris-api`: `GET /api/items/{id}/job` and `POST /api/jobs` (`jobs.rs`), `POST /api/policy/grant`
  (`policy.rs`), the routes in `lib.rs`, the README.
- `crates/iris-policy`: `Change::Grant`, and `add_rule` writes `author`
  and `job`.
- `crates/iris-workspace`: `readable`, the rule of the build as a public
  function.
- `client/`: the start page `#/item/<id>/job`, the grants on the job page,
  `docs/DESIGN.md` for each new part.
- No migration. No change to a schema of the open model.

## Assumptions

- The scope functions take refs from the person in a write transaction.
  Evidence: `iris_job::add_scope_in` (`crates/iris-job/src/lib.rs`).
- The policy decides the actions of a session with `job` from the author.
  Evidence: `crates/iris-policy/src/eval.rs`, `r.job ... action.job`.
- The session changes only granted messages. Evidence: spec 2, section 8.2.
  `pending` until R4-03 builds the check. If the check is missing, a grant
  still allows only the verbs of the rule, and only for the agent of that
  job.
- One item has a small number of source messages and threads. Evidence:
  understanding writes an origin, updates and evidence (spec 1). The start
  reads them in one transaction with no page.

## External writes

None. The start writes only the store. The grant writes `policy.toml` in
the data folder through `iris_policy::change`, which already handles a
failed write (the file stays a change for the person to confirm or
discard).

## Open questions

None.

## Acceptance criteria

1. A start from a commitment with two source messages in two threads makes
   a job whose scope is the item and the two threads. Red if a thread is
   missing or another thread is in the scope.
2. The list of section 1 has each message of those two threads and no other
   message, and a start with a list that misses one message gives 409 and
   no job. Red if a granted message is not in the list, or if the start
   passes.
3. A start from a conversation makes a job whose scope holds its thread.
   Red if the thread is missing.
4. A second start for the same item while the first job is open gives 409
   with the first job ID, and the store has one job. Red if a second job
   exists.
5. A start from an item with a hostile source, a source of a signal, a gone
   item, a done commitment, a muted conversation or a record gives an
   error, and the store has no job. Red if a job exists.
6. A grant writes one rule with `job`, `when.author = "agent"` and the
   verbs, and the policy then allows such an action of an agent changeset
   of that job, and not of another job. Red if the rule matches another job.
7. A grant with `send`, or for a done job, leaves `policy.toml` as it was.
   Red if the file changes.

## Rollout

None. The routes are new, and the client calls them in its own PRs.

## Risks

- A grant allows agent actions without review. The scope, the hard limits
  and the deny and review rules still apply. Rollback: remove the rule in
  the Rules view, or revert the PR.
- A start grants whole threads. The start form shows each message of the
  grant first, and the start refuses a list that differs from the grant.

## Spec checks

  check and create are one write transaction; the grant uses `version`.
- [x] Each assumption holds when an outcome is unknown: a retry of the start
  finds the first job (409 with its ID); a retry of a grant gives 409 (old
  `version`), and the page reloads the policy.

  unnecessary: the idempotency key (see "Options not chosen").

- [x] Each property that the design depends on has a test: see "Test plan".

  job gets, and that the person sees each message of it.
