# Spec: start a job from an item, and a grant inside one job

- Date: 2026-11-17
- Card: R4-10
- Status: Draft

## Problem

The job store (R4-01), the scope of a job (R4-02) and the job page (R4-09)
exist, but only a test can make a job. The person has no way to give a goal
to an agent. The experience document says: "From a thread, select 'handle
this'. Or write the goal." It also says: "You can also give a grant inside
one job: 'In this job, allow replies to the same recipient.'" Spec 2,
section 6.2 has the field `job` of a rule for this grant, but no path writes
such a rule.

## Goal

1. On the page of a commitment or a conversation, the person selects
   "Handle this", writes the goal, and starts a job. The new job has the
   correct mail: the item and the threads of its source messages, and no
   other mail.
2. On the page of an open job, the person allows some verbs without review
   inside that job only. Iris writes one rule with `job` to `policy.toml`.
3. The person sees the grants of a job on its page, and removes one there.

The card is done when "Handle this" creates a job whose scope is the item
and the threads of its sources (acceptance criteria 1 to 4).

## Not in scope

- The agent session. "Handle this" creates the job and its scope. The
  launcher (R4-04) starts the session of a job. Until R4-04 merges, a new
  job stays in `working` with no session (known limit, with a GitHub issue).
- A job from a goal with no item ("Book a dentist appointment"). The job
  then has no mail, and the person has no way yet to add mail to a scope.
  It comes with a card that adds mail to a scope from a thread or a search.
- A grant for `draft` or `send`. The policy refuses a rule with these verbs
  until R3-03 (spec 2, section 6.2). "Allow replies to the same recipient"
  also needs a new condition of `when`. Both are a known limit, with a
  GitHub issue.
- A change of the goal, the due date or the scope after the start.
- The brief line of a job (issue #323).

## Design

### 1. Start a job: `POST /api/jobs`

Body: `{"item": "<item ID>", "goal": "<text>", "due": "<RFC 3339>" | null}`.

The engine does these steps in one write transaction (`iris_job::transaction`):

1. Parse the item ID. The kind must be `c-` (commitment) or `v-`
   (conversation). Another kind, or an ID that is not valid: 400.
2. Read the item. No item with that ID: 404. The status `gone`: 409.
3. Check each source message of the item (`item_source`): it must be clean
   by the rule of the workspace spec (`iris_talk::Mail::for_reader`: understood,
   not a draft, not hostile mail; not gone). If one source is not clean: 409,
   "An agent cannot read the mail of this item." An item with no source:
   409. So no job starts with mail that its workspace would drop.
4. If an open job (state not `done`) has an active scope row for this item:
   409 with `{"error", "job": "j-<n>"}`. The client opens that job. This
   makes a second request after a lost answer safe: it finds the first job
   and creates no second one. The check and the create are in the same write
   transaction, so two requests cannot both pass the check.
5. Check the goal: trim it; 1 to 2,000 characters after the trim; else 400.
   Check `due`: RFC 3339 or null; else 400. A due date in the past is
   allowed (the job page says "Was due").
6. `iris_job::create_in(goal, due_ms, now)`.
7. `iris_job::add_scope_in(job, Ref::Item(item), By::Person, now)`.
8. For each distinct thread of the source messages, in the order of the
   thread ID: `add_scope_in(job, Ref::Thread(thread), By::Person, now)`.

Answer: 201 with the job document (`docs/spec/schema/job.schema.json`). If a
step fails, the transaction rolls back and nothing stays.

Why the threads and not only the item: a commitment comes from a
conversation. To do the job (a reply, a check of an earlier message), the
agent needs the thread, not only the source message. The person sees each
thread on the start form before the start (section 3), so the grant is what
the person saw. The workspace spec says that an item ref grants no whole
thread. That rule stays: here the person adds the thread refs on purpose.

A conversation item never goes into a workspace (workspace spec). Its
thread refs bring its mail. The item ref stays in the scope as the origin
of the job, and grants only its own sources.

### 2. A grant inside one job: `POST /api/policy/grant`

Body: `{"job": "j-<n>", "verbs": ["archive", ...], "version": <n> | null}`.
`version` is the active policy version that the person saw, as for the other
policy changes.

Checks, before the change: the job exists (else 404) and is not `done`
(else 409, "The job ended."). `verbs` has 1 to 11 names of `Verb::ALL`, with
no duplicate (else 400). `draft` and `send` are not in `Verb::ALL`, so the
API refuses them with 400.

The change is a new `iris_policy::Change::Grant`. It goes through
`iris_policy::change`, with all its checks (the active version, the file on
disk, the parse of the new text). It appends this rule:

```toml
# You gave this grant inside job j-12, on the job page.
[[rule]]
id = 14
name = "In job j-12, allow archive and label without review"
effect = "allow"
verbs = ["archive", "label"]
when = { author = "agent" }
by = "person"
added = 2026-11-17
job = "j-12"
```

- `id` is the next free rule ID (`next_rule_id`).
- `when = { author = "agent" }`: `when` needs one condition, and the grant
  is for the agent of the job. A person changeset has no job, so it cannot
  match.
- The rule is an `allow` rule. A `deny` or a `review` rule that matches the
  same action still wins (spec 2, section 6.4). The hard limits of spec 2,
  section 6.5 stay: hostile mail, bulk actions, and the mode `observe`, in
  which Iris applies nothing.
- The session can change only the messages that the scope grants (spec 2,
  section 8.2). So the grant cannot reach mail outside the job.

A job that ends keeps its rule in the file. The rule matches nothing more,
because a done job has no session. The person removes it on the job page
or in the Rules view (`POST /api/policy/remove`). An automatic removal at
the end of a job is a known limit, with a GitHub issue.

### 3. The screens

The person picks the layout of each screen from a before/after page
(`docs/PLANNING.md`). Each screen is its own client PR. These parts are
fixed:

- Item page (`Item.svelte`): "Handle this" shows only for an item of the
  form `commitment` or `conversation`, with the status `open`. The start
  form has the goal (filled with the title of the item, which the person
  edits), the due date (filled with the due date of a commitment), and the
  threads that the agent reads (the subject of each thread of a source
  message, from `GET /api/messages/{id}`). Start sends `POST /api/jobs`,
  then opens the job page. A 409 with `job` opens that job.
- Job page (`Job.svelte`): for an open job, the grants of the job (the rules
  of `GET /api/policy` with this `job`), a way to add a grant (the verbs in
  plain words), and Remove for each grant. A done job shows its grants and
  no add.

## Options not chosen

- Only the item ref, no thread refs: the agent of a commitment could not
  read the conversation it must answer.
- A free list of threads in the body: a client error could grant mail that
  the person did not see. The engine takes the threads from the item.
- An idempotency key in the body: it needs a new column. "One open job for
  each item" gives the same result for a retry, and also stops a second job
  for the same work.
- A grant as a field of the job (a new column): spec 2 already has `job` in
  a rule, and the rule goes through the same review, ledger and Rules view.
- A grant with the conditions of the page (for example `sender`): the scope
  already limits the mail. More conditions can come later with no change
  to the API format.

No parser, protocol or security code is new. The goal is plain text. The
API uses `iris_store::parse_id`, `iris_job::parse_job_id` and the parse of
`policy.toml` that exist.

## Failure list

Supported input: the bodies above, from the signed-in local web client.
All other input gets 400, 404 or 409, and changes nothing.

| Input or event | Result | Test |
|---|---|---|
| Item ID of another kind (`r-`, `f-`, `s-`, `m-`), or not an ID | 400, no job | api test |
| Item gone, or a source not clean (hostile, gone, draft, not understood) | 409, no job | api test with a hostile source |
| Goal empty after the trim, or longer than 2,000 characters | 400, no job | api test |
| `due` not RFC 3339 | 400, no job | api test |
| Second start for the same item while a job is open | 409 with the first job ID, no second job | api test |
| Two starts at the same time | One write transaction at a time: one job, one 409 | the same test, the check is in the transaction |
| A crash during the start | The transaction rolls back: no job, or a job with its full scope | the transaction is the proof |
| Grant for a done job, or a job that does not exist | 409 or 404, the file does not change | api test |
| Grant with `draft`, `send`, an unknown verb, a duplicate or no verb | 400, the file does not change | api test |
| Grant while the file on disk changed, or with an old `version` | 409, as for each policy change | existing tests of `change` |
| Grant for a job that ends at the same moment | The rule is written and matches nothing | none needed: no action of a done job |

## Impact

- `crates/iris-api`: `POST /api/jobs` (`jobs.rs`), `POST /api/policy/grant`
  (`policy.rs`), the routes in `lib.rs`, the README.
- `crates/iris-policy`: `Change::Grant`, and `add_rule` writes `author`
  and `job`.
- `client/`: the start form on the item page, the grants on the job page,
  `docs/DESIGN.md` for each new part.
- No migration. No change to a schema of the open model.

## Assumptions

- The scope functions take refs from the person in a write transaction.
  Evidence: `iris_job::add_scope_in` (`crates/iris-job/src/lib.rs`).
- The policy decides the actions of a session with `job` from the author.
  Evidence: `crates/iris-policy/src/eval.rs`, `r.job ... action.job`.
- The session changes only granted messages. Evidence: spec 2, section 8.2.
  `pending` until R4-03 builds the check. If the check is missing, a grant
  still allows only the verbs of the rule, and only for the agent of that
  job.
- One item has a small number of source messages and threads. Evidence:
  understanding writes an origin, updates and evidence (spec 1). The start
  reads them in one transaction with no page.

## External writes

None. The start writes only the store. The grant writes `policy.toml` in
the data folder through `iris_policy::change`, which already handles a
failed write (the file stays a change for the person to confirm or
discard).

## Open questions

None.

## Acceptance criteria

1. A start from a commitment with two source messages in two threads makes
   a job whose scope is the item and the two threads. Red if a thread is
   missing or another thread is in the scope.
2. A start from a conversation makes a job whose scope holds its thread.
   Red if the thread is missing.
3. A second start for the same item while the first job is open gives 409
   with the first job ID, and the store has one job. Red if a second job
   exists.
4. A start from an item with a hostile source, a gone item or a record
   gives an error, and the store has no job. Red if a job exists.
5. A grant writes one rule with `job`, `when.author = "agent"` and the
   verbs, and the policy then allows such an action of an agent changeset
   of that job, and not of another job. Red if the rule matches another job.
6. A grant with `send`, or for a done job, leaves `policy.toml` as it was.
   Red if the file changes.

## Rollout

None. The routes are new, and the client calls them in its own PRs.

## Risks

- A grant allows agent actions without review. The scope, the hard limits
  and the deny and review rules still apply. Rollback: remove the rule in
  the Rules view, or revert the PR.
- A start grants whole threads. The start form shows each thread first.

- [x] Each assumption holds with a second caller, worker or tab: the start
  check and create are one write transaction; the grant uses `version`.
- [x] Each assumption holds when an outcome is unknown: a retry of the start
  finds the first job (409 with its ID); a retry of a grant gives 409 (old
  `version`), and the page reloads the policy.

  unnecessary: the idempotency key (see "Options not chosen").

  job gets.
- [x] Each acceptance criterion can go red.
