# Spec: one mail provider interface

- Date: 2026-11-17
- Card: R6-10
- Status: Agreed

## Problem

The sync (`iris-sync`), the verify of the mirror (`iris-sync` verify), the
apply and the send (`iris-apply`) and the engine (`crates/iris`) call the
Gmail client (`iris-gmail`) directly. Cards R6-03 (IMAP) and R6-04 (Outlook
through Microsoft Graph) add two more mail providers. Without one interface,
each provider needs its own copy of the sync and of the apply, and the three
copies drift.

## Goal

1. One Rust trait, `Provider`, in a new crate `iris-provider`. The trait has
   each call that the sync, the verify, the apply and the send make: the
   profile, the labels, the list of messages, the changes after a cursor, the
   read of one message (labels, headers or raw data), the label changes, the
   trash, the drafts and the send.
2. `iris_gmail::Gmail` implements the trait. It is the first provider.
3. `iris-sync` and `iris-apply` take `&dyn Provider`, not `&Gmail`. The
   engine makes the Gmail provider and gives it to them.
4. The behavior does not change. Each test passes with the Gmail provider and
   the fake Gmail server (`iris-fakegmail`).
5. The trait has a documented mapping for IMAP and for Microsoft Graph, so
   that R6-03 and R6-04 implement it with no change to the sync or the apply.

## Not in scope

- The IMAP provider and the Graph provider. R6-03 and R6-04 build them.
- More than one account (R6-02), and a choice of the provider for each
  account. The account row gets its provider kind in R6-02 or R6-03, when a
  second kind exists.
- Sign-in. `iris-auth` stays Google only. Each provider gives the access
  token (or the password) to the trait as the `token` string.
- A change to the store schema. The mirror keeps the label model of today.
- New words in the user texts. The texts of the apply and the send that name
  Gmail stay. The provider cards change them when a second provider can run.

## Design

### 1. The crate `iris-provider`

The crate holds the trait, the shared types, the shared error and two shared
limits. It has no HTTP client and no provider code. It depends only on
`serde`: the types that Gmail sends as JSON keep their Gmail field names for
the parse. Other providers build the types in code.

The types move from `iris-gmail` to `iris-provider` with the same fields,
except the Gmail history IDs (section 3). `iris-gmail` re-exports them, so that the old
paths (`iris_gmail::Label`, `iris_gmail::Error`) still compile.

| Type | Content |
|---|---|
| `Profile` | The mailbox address (`email_address`) and the cursor of now. |
| `Label` | ID, name, kind (`system` or `user`). |
| `MessageRef`, `MessagePage` | The message ID and the thread ID; one page of them and the next page token. |
| `Minimal` | The message ID and its label IDs. |
| `Metadata`, `Header` | The message ID, its label IDs and the named headers. |
| `RawMessage` | The fields of a raw read. The data went to the sink. |
| `HistoryMessage`, `Change`, `History`, `HistoryPage` | The change records after a cursor, and the new cursor. |
| `Sent`, `Draft`, `DraftRaw` | The answers of the send and of the drafts. |
| `Error`, `Result` | The shared error (section 5). |

Shared limits:

- `DRAFT_LIMIT` (4 MiB): the most bytes of a draft that `draft_raw` keeps.
  It moves from `iris-gmail`.
- `BATCH_LIMIT` (1,000): the most message IDs in one `modify` call. A
  provider with a lower limit splits the call. It must then apply all parts
  or give an unknown result (section 6).
- `MAX_GETS` (8): the most reads of messages that the sync runs at the same
  time.

### 2. The trait

```rust
pub trait Provider: Send + Sync {
    fn profile(&self, token: &str) -> Result<Profile>;
    fn labels(&self, token: &str) -> Result<Vec<Label>>;
    fn messages(&self, token: &str, label: Option<&str>, page: Option<&str>) -> Result<MessagePage>;
    fn changes(&self, token: &str, from: &str, page: Option<&str>) -> Result<HistoryPage>;
    fn minimal(&self, token: &str, id: &str) -> Result<Minimal>;
    fn metadata(&self, token: &str, id: &str, headers: &[&str]) -> Result<Metadata>;
    fn raw(&self, token: &str, id: &str, sink: &mut dyn Write) -> Result<RawMessage>;
    fn messages_with_id(&self, token: &str, message_id: &str) -> Result<Vec<MessageRef>>;
    fn modify(&self, token: &str, ids: &[&str], add: &[&str], remove: &[&str]) -> Result<()>;
    fn trash(&self, token: &str, id: &str) -> Result<Minimal>;
    fn untrash(&self, token: &str, id: &str) -> Result<Minimal>;
    fn create_label(&self, token: &str, name: &str) -> Result<Label>;
    fn drafts_with_id(&self, token: &str, message_id: &str) -> Result<Vec<Draft>>;
    fn draft_raw(&self, token: &str, id: &str) -> Result<DraftRaw>;
    fn create_draft(&self, token: &str, raw: &[u8], thread: Option<&str>) -> Result<Draft>;
    fn send_draft(&self, token: &str, id: &str, raw: &[u8], thread: Option<&str>) -> Result<Sent>;
}
```

The rules of each call:

- `messages`: all mail, spam and trash included, newest first. With
  `label`, only the messages with that label. One page for each call. A
  provider with folders and location IDs (IMAP) gives `INBOX` first, then
  each other folder, newest first in each folder. The first sync then
  fetches the newest mail of `INBOX` first, but the old mail of one folder
  can come before the new mail of the next folder.
- `changes`: the change records after the cursor `from`, in order, one page
  for each call. The last page gives the new cursor. `Error::HistoryExpired`
  means that the provider cannot give the changes from `from`: the sync does
  a full resync. The sync applies `Change::Added` as a set of all labels of
  the message, and `Change::Deleted` as gone (spec 1 section 4.3). A gone
  message does not come back. Thus each provider keeps these rules:
  - It gives `Change::Deleted` only for a message that no longer exists. A
    folder provider confirms this before the record: no folder of the
    mailbox has the ID now.
  - A move of a message with a stable ID between two folders is one
    `Change::Added` with the full label set after the move, never a delete
    and an add. A folder provider reads the changes of all folders, joins
    the events of each ID, and gives one record for each ID.
  - The cursor of the last page covers all folders. The provider gives the
    last page only after it read the changes of each folder up to that
    cursor. A stop before the last page leaves the old cursor, and the next
    call reads the same changes again (spec 1 section 4.3).
- `draft_raw`: streams the draft and keeps at most `DRAFT_LIMIT` (4 MiB)
  bytes. A larger draft gives `raw: None`, as Gmail does today. The
  provider never holds more than the limit in memory.
- `raw`: streams the RFC 5322 data of the message into `sink`. The provider
  never holds the full message in memory (spec 1 section 9).
- `messages_with_id` and `drafts_with_id`: the messages and the drafts whose
  `Message-ID` header is `message_id`. The send recovery uses them (send
  spec, section 6). They replace the Gmail search strings
  (`rfc822msgid:<id>`), which are not portable.
- `modify`: adds the labels `add` to each message of `ids` and removes the
  labels `remove`.

`token` is the secret that the provider needs for the call: an OAuth access
token for Gmail and Graph, an OAuth token or a password for IMAP. The trait
does not store it. `Error::Unauthorized` tells the caller to get a new
`token` one time, as today.

The trait is object safe (`&dyn Provider`), so that the engine can choose the
provider of each account when it runs. The cost is one indirect call for each
network call, which is small compared to the network time.

### 3. The cursor

The cursor is an opaque string. The caller stores it and gives it back. It
never reads it, and never compares two cursors.

- Gmail: the history ID, as its decimal text. The column
  `account.history_id` is `TEXT` already (schema 1), so the stored values do
  not change.
- IMAP: the provider encodes its state in the string, for example the
  `UIDVALIDITY`, the `HIGHESTMODSEQ` (RFC 7162) and the highest UID of each
  folder.
- Graph: the provider encodes the delta link of each mail folder.

Today the code reads the history ID as `u64`. After this card, the sync and
the verify keep it as `String`. `Profile` and `HistoryPage` carry
`cursor: String` in place of `history_id: u64`. `RawMessage` and `History`
lose their Gmail history ID: no caller reads it, and a folder provider has
none. The Gmail provider checks that a cursor is a decimal number before
the call, and gives `Error::Decode` if not, as the sync did before with
`BadState`.

### 4. The label model

The mirror stores labels. Each provider maps its own model to labels, so that
the store, the forms, the policy and the verbs stay the same.

Each label has the kind that the provider gives: `system` or `user`. The
kind does not change because the provider is not Gmail. The rules:

- The seven labels of the table below have the Gmail IDs on each provider:
  `INBOX`, `UNREAD`, `STARRED`, `SENT`, `DRAFT`, `SPAM` and `TRASH`.
- Gmail keeps its own kind for each label. `IMPORTANT`, `CHAT` and the
  `CATEGORY_*` labels stay `system`, as today (spec 1 section 4.1). So a
  `label` action cannot target them (spec 2).
- A folder provider gives `system` to each special-use folder (RFC 6154,
  Graph well-known folders) and to each folder or flag that it cannot change
  as a user label. Only a folder that the person made, a keyword and a
  category are `user`.
- The ID of a user label comes from the provider and does not change.

| Iris label | Gmail | IMAP | Graph |
|---|---|---|---|
| `INBOX` | `INBOX` | Folder `INBOX` | Well-known folder `inbox` |
| `UNREAD` | `UNREAD` | No `\Seen` flag | `isRead` is false |
| `STARRED` | `STARRED` | `\Flagged` flag | `flag.flagStatus` is `flagged` |
| `SENT` | `SENT` | None: a message in the `\Sent` folder is not proof that the owner wrote it | Well-known folder `sentitems` |
| `DRAFT` | `DRAFT` | None, for the same reason as `SENT` | Well-known folder `drafts` |
| `SPAM` | `SPAM` | Folder with `\Junk` | Well-known folder `junkemail` |
| `TRASH` | `TRASH` | Folder with `\Trash` | Well-known folder `deleteditems` |
| User label | User label | Other folder, or a keyword | Other folder, or a category |

A message in the archive folder (IMAP `\Archive`, Graph `archive`) or in
no folder of the table has no system label, as a Gmail message with no
`INBOX` label.

The verbs map as follows. The apply sends the same `modify` call for each
provider. The provider makes the calls of its own model.

| Verb | Trait call | IMAP | Graph |
|---|---|---|---|
| `archive` | `modify(remove: INBOX)` | `MOVE` (RFC 6851) to the `\Archive` folder | `move` to the well-known folder `archive` |
| `inbox` | `modify(add: INBOX)` | `MOVE` to `INBOX` | `move` to `inbox` |
| `read`, `unread` | `modify(remove or add: UNREAD)` | `STORE` of `\Seen` | `PATCH` of `isRead` |
| `label`, `unlabel` | `modify(add or remove: <label>)` | A keyword: `STORE` | A category: `PATCH` of `categories` |
| `trash` | `trash` | `MOVE` to the `\Trash` folder | `move` to `deleteditems` |
| `untrash` | `untrash` | `MOVE` to `INBOX` | `move` to `inbox` |

A folder is exclusive: a message is in one folder. The ledger records the
labels that an action changes, not the folder of a message, so a move out of
a user folder has no undo. Thus a folder provider keeps these rules:

- It moves a message only between `INBOX`, the archive folder and the trash
  folder. The undo of each move is a move back: `archive` and `inbox`
  reverse each other. The undo of `trash` is `untrash` to `INBOX`, then
  `archive` of each message that had no `INBOX` before the trash, as today
  (spec 2 section 7.4).
- A `modify` or a `trash` of a message that is in a user folder is a
  definite rejection (`Error::Api` with status 400), before any write.
- Each move has a condition on its source folder at the server, so that a
  message that another client moved after the check does not move. IMAP
  gives this: `UID MOVE` acts in the selected source folder only, and a
  message that left it is not moved. A provider that cannot make a move
  conditional (for example, if Graph `move` has no such condition) refuses
  each move with a definite rejection before any write. R6-04 states which
  case Graph is.
- A `modify` that adds or removes a user folder label is a definite
  rejection before any write. A user label of a folder provider that the
  apply can change is a keyword (IMAP) or a category (Graph).

The apply records a definite rejection as `failed`, as it does today for a
refused call. These rules limit the verbs on a folder provider. A later card
can record the folder of each message in the ledger and lift them.

A message ID is one of two kinds. Each provider states its kind:

- A stable ID: it does not change when the message moves. Gmail IDs and
  Graph immutable IDs (`Prefer: IdType="ImmutableId"`) are stable. A move is
  one `Change::Added` with the new label set (section 2).
- A location ID: it names the place of the message, for example the
  folder, the `UIDVALIDITY` and the UID of IMAP. This is the normal IMAP
  path, because an IMAP server fetches by UID in one folder, and an
  `EMAILID` (RFC 8474) alone cannot fetch a message. A move is a delete of
  the old ID and an add of the new ID. The mirror marks the old message
  gone and fetches the new one. The forms of the old message stay on the
  gone row (spec 1 section 7).

The apply needs a stable ID. The ledger marks the messages of an entry
`done`, and the undo finds them by that row (spec 2 section 7.4). After a
move with a location ID, the next sync marks that row gone, so the undo
loses the message. Thus a provider with location IDs refuses each write
that moves a message (`modify` of `INBOX` or of a folder label, `trash`,
`untrash`) with a definite rejection (`Error::Api` with status 400),
before any write. A write that does not move (`UNREAD`, `STARRED`, a
keyword) is allowed. A later card can lift this rule: it must give the
rebind of a moved message to its new ID in the mirror, the ledger and the
crash recovery, and say how the undo finds the message.

The thread ID comes from the provider: Gmail `threadId`, IMAP `THREADID`
(RFC 8474) or a thread from the `References` and `In-Reply-To` headers, Graph
`conversationId`.

### 5. The error

`Error` keeps the variants of today: `Unauthorized`, `NotFound`,
`HistoryExpired`, `Api { status, reason, message }`, `Transport`, `Decode`
and `Sink`. `Error::write_result_unknown` keeps its rule. A provider that is
not HTTP maps its answers to these variants:

| Answer | Variant |
|---|---|
| The secret is refused (HTTP 401, IMAP `AUTHENTICATIONFAILED`) | `Unauthorized` |
| The message, the label or the draft is not there | `NotFound` |
| The cursor is too old (Gmail HTTP 404, Graph HTTP 410 of a delta link) | `HistoryExpired` |
| A new `UIDVALIDITY` of one IMAP folder | `HistoryExpired`, or a delete of each old ID and an add of each new ID of that folder in `changes` (the choice of R6-03) |
| A definite rejection (HTTP 4xx, IMAP `NO` or `BAD` of a write) | `Api` with a 4xx status |
| A rate limit (HTTP 429) | `Api` with status 429 |
| A server error (HTTP 5xx, IMAP `BYE` during a call) | `Api` with a 5xx status, or `Transport` |
| A lost connection, a time-out | `Transport` |

The display texts of the error stop naming Gmail, because the type is
shared. No code and no test reads these texts (`grep` of the texts in
`crates/` and `client/`).

### 6. The writes of the trait

The trait adds no new write. The apply and the send keep their rules
(spec 2 section 7, send spec section 5). Each provider must keep these rules:

- The provider never tries a write again after an unknown result. It can
  try a write again only after an answer that says that no write happened:
  a rate limit that the provider knows is a rejection (spec 2 section 7.2;
  Gmail retries HTTP 429 and a rate-limit HTTP 403 of `batchModify` today)
  and HTTP 401 (the caller gets a new token). A call with one request (the
  send and the draft create) is not tried again, as today (send spec,
  section 5.2).
- After the provider sends the request of a write, each error that is not
  a definite rejection of the server is `Error::Transport` (unknown). This
  includes an answer that the provider cannot read after the server
  accepted the call. `Error::Decode` is only for a read, or for a write
  that the provider did not send. Gmail does this today (`Gmail::write`).
- `modify` is all or nothing for the caller. If the provider splits it into
  parts and a part fails after another part ran, the result is unknown
  (`Error::Transport`), so that the apply reads the labels and never calls
  again.
- `send_draft` sends exactly the bytes `raw`, never the content of the
  draft at the provider. The person can change the draft at the provider
  after the check of the send (send spec, section 5), so a send of the draft
  by its ID is not allowed.
  - Gmail: `drafts.send` with `raw` as the message of the draft, as today.
  - Graph: `sendMail` with the MIME content `raw` (base64, `Content-Type:
    text/plain`) and `saveToSentItems`. Graph gives no message ID for this
    call, so the provider finds the sent copy with `messages_with_id`. If it
    does not find it, it gives `Error::Transport` (unknown), and the send
    recovery finds the copy later. The draft at Graph stays after
    `sendMail`, and the person can think that the mail did not leave. So
    after the send, the provider deletes the draft one time, with the
    condition `If-Match` and the version of the draft that the send check
    read. An edit of the draft after the check changes its version, so the
    delete never removes text that the person wrote after the check.
    - Success: the draft is gone.
    - HTTP 412, another definite rejection, an unknown result or a crash
      before the delete: the mail left, so the send stays a success. The
      ledger entry of the send gets the note "The draft stays in Outlook.
      Delete it there." The person sees it in the history view (R2-07).
      After a crash, the send recovery writes the note when it completes
      the send.
    - No retry.

    R6-04 adds the signal to `Sent` and the note of the apply, in its own
    PR, before it turns on the Graph send. R6-03 uses the same signal.
  - IMAP: SMTP submission (RFC 6409) of `raw`, then an `APPEND` of `raw` to
    the `\Sent` folder only if the account says that Iris saves the copy.
    The account has one setting for this, `server` or `iris`, that the
    person chooses at sign-in (R6-03). The default is `server`. The provider
    never decides from a search after the send, because a server can save
    its copy later. With a wrong `server`, the send recovery finds no sent
    copy, and the action ends as `failed` with an unknown result after 24
    hours, with the claim kept: no second send. With a wrong `iris`, the
    mailbox has two sent copies. The provider never deletes the draft
    after the send: the apply gives the same note as Graph ("The draft
    stays in the Drafts folder. Delete it there."). Until the send card
    of IMAP, the IMAP provider gives `Api` 400 `notSupported` for each
    draft and send call (`docs/specs/2026-11-17-imap-provider.md`).
- A send has one result for all of its steps. Before the provider gives the
  bytes to the server, an error is the error of that step. After the server
  accepts the bytes (the SMTP `DATA` reply, the Graph `202`), each later
  failure (the `APPEND`, the read of the sent copy, the draft delete) gives
  `Error::Transport` or `Ok`, never a definite rejection. So the send claim
  stays, and Iris never sends the mail two times. The send recovery then
  finds the sent copy with `messages_with_id`. If no copy exists, the action
  ends as `failed` with an unknown result after 24 hours, and the claim
  stays (send spec, section 6, issue #280).

## Options not chosen

- Generic functions (`fn sync<P: Provider>`). Each caller would be compiled
  one time for each provider, and the engine could not choose the provider
  of an account when it runs.
- A `u64` cursor. IMAP and Graph keep a state for each folder, which does not
  fit in one number.
- One trait for each part (a read trait, a write trait, a send trait). The
  three providers have all parts, and three traits add three constructions in
  the engine for no caller.
- A folder model in place of labels. It would change the store, the forms,
  the policy and each verb, and Gmail has no exclusive folders.
- A public library for the trait. The trait is the internal contract of Iris.
  The provider cards choose the protocol libraries (for example `async-imap`
  or `imap` for R6-03).

## Failure list

The trait adds no input path. The supported inputs and the failure modes of
the Gmail answers stay as in spec 1 section 4 and in `iris-gmail`. A
provider that cannot map the answer of a read to the types gives
`Error::Decode`, and the caller handles it as today (a per-message failure
in the sync, a failed read in the apply). An answer of a write that the
provider cannot map gives `Error::Transport` (section 6), so the write is
never sent again. This is the safe result for all other input.

## Impact

- New crate `crates/iris-provider`.
- `crates/iris-gmail`: the types move out and are re-exported; `impl Provider
  for Gmail`. The inherent methods stay for the tests of the client.
- `crates/iris-sync`, `crates/iris-apply`: `&dyn Provider` in place of
  `&Gmail`; the cursor as `String`; the error variant `Error::Gmail` becomes
  `Error::Provider`.
- `crates/iris`: the provider construction in `engine.rs` and the verify
  command in `lib.rs`.
- No change to the store, the API, the web client or a data format.

## Assumptions

1. No code compares two history IDs as numbers. Evidence: `grep -rn
   "history_id" crates/iris-sync crates/iris-apply crates/iris` shows only
   parse, store and print uses.
2. `account.history_id` and `account.sync_start` are `TEXT`. Evidence:
   `crates/iris-store/src/schema_1.sql`.
3. The send recovery searches only by `Message-ID`. Evidence: the two
   `rfc822msgid:` strings in `crates/iris-apply/src/send.rs`.
4. The sync always lists with the spam and the trash, and always reads the
   four history types. Evidence: each call of `Gmail::messages` passes
   `true`, and each call of `Gmail::history` passes `HistoryType::ALL`.
5. IMAP and Graph can give each call of the trait. Evidence: RFC 9051,
   RFC 7162, RFC 6154, RFC 6851, RFC 8474 and the Graph mail API (message,
   mailFolder, delta, `$value`, `move`, `send`). Status `pending` until
   R6-03 and R6-04 build them. If a call does not fit, the provider card
   changes this spec and the trait in its own PR.

## External writes

None new. The writes of the trait are the Gmail writes of today, with the
same results on success, on a definite rejection, on an unknown result and on
retry (spec 2 section 7, send spec section 5). Section 6 gives the rules that
each new provider must keep.

## Open questions

- R6-04 changes the trait in its own PR for the Graph model: a check of
  each provider that a draft did not change (Gmail keeps the hash of the
  raw bytes, Graph the version of the create), `If-Match` on category
  writes with HTTP 412 as a definite rejection, and a compare of the
  content in place of the raw bytes in verify, because Graph builds the
  MIME text again at each read.

- R6-03: the IMAP provider keeps one connection behind a lock and
  reconnects after an error. The trait allows this: a provider can run its
  calls one at a time. The sync runs at most `MAX_GETS` reads at the same
  time, and they then wait for the lock.

## Acceptance criteria

1. `iris-sync` and `iris-apply` do not depend on `iris-gmail` outside their
   tests. Red if `cargo tree -p iris-sync -e normal` or `cargo tree -p
   iris-apply -e normal` lists `iris-gmail`.
2. Each test of the workspace passes with the Gmail provider and the fake
   Gmail server. Red if a test fails.
3. The public functions of `iris-sync` and `iris-apply` take
   `&dyn Provider`. Red if criterion 1 is red, because the type `Gmail`
   needs `iris-gmail`.

  revert the PR. No data format changes.
