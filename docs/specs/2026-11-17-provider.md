# Spec: one mail provider interface

- Date: 2026-11-17
- Card: R6-10
- Status: Agreed

## Problem

The sync (`iris-sync`), the verify of the mirror (`iris-sync` verify), the
apply and the send (`iris-apply`) and the engine (`crates/iris`) call the
Gmail client (`iris-gmail`) directly. Cards R6-03 (IMAP) and R6-04 (Outlook
through Microsoft Graph) add two more mail providers. Without one interface,
each provider needs its own copy of the sync and of the apply, and the three
copies drift.

## Goal

1. One Rust trait, `Provider`, in a new crate `iris-provider`. The trait has
   each call that the sync, the verify, the apply and the send make: the
   profile, the labels, the list of messages, the changes after a cursor, the
   read of one message (labels, headers or raw data), the label changes, the
   trash, the drafts and the send.
2. `iris_gmail::Gmail` implements the trait. It is the first provider.
3. `iris-sync` and `iris-apply` take `&dyn Provider`, not `&Gmail`. The
   engine makes the Gmail provider and gives it to them.
4. The behavior does not change. Each test passes with the Gmail provider and
   the fake Gmail server (`iris-fakegmail`).
5. The trait has a documented mapping for IMAP and for Microsoft Graph, so
   that R6-03 and R6-04 implement it with no change to the sync or the apply.

## Not in scope

- The IMAP provider and the Graph provider. R6-03 and R6-04 build them.
- More than one account (R6-02), and a choice of the provider for each
  account. The account row gets its provider kind in R6-02 or R6-03, when a
  second kind exists.
- Sign-in. `iris-auth` stays Google only. Each provider gives the access
  token (or the password) to the trait as the `token` string.
- A change to the store schema. The mirror keeps the label model of today.
- New words in the user texts. The texts of the apply and the send that name
  Gmail stay. The provider cards change them when a second provider can run.

## Design

### 1. The crate `iris-provider`

The crate holds the trait, the shared types, the shared error and two shared
limits. It has no HTTP client and no provider code. It depends only on the
standard library.

The types move from `iris-gmail` to `iris-provider` with the same fields,
except the cursor (section 3). `iris-gmail` re-exports them, so that the old
paths (`iris_gmail::Label`, `iris_gmail::Error`) still compile.

| Type | Content |
|---|---|
| `Profile` | The mailbox address (`email_address`) and the cursor of now. |
| `Label` | ID, name, kind (`system` or `user`). |
| `MessageRef`, `MessagePage` | The message ID and the thread ID; one page of them and the next page token. |
| `Minimal` | The message ID and its label IDs. |
| `Metadata`, `Header` | The message ID, its label IDs and the named headers. |
| `RawMessage` | The fields of a raw read. The data went to the sink. |
| `HistoryMessage`, `Change`, `History`, `HistoryPage` | The change records after a cursor, and the new cursor. |
| `Sent`, `Draft`, `DraftRaw` | The answers of the send and of the drafts. |
| `Error`, `Result` | The shared error (section 5). |

Shared limits:

- `BATCH_LIMIT` (1,000): the most message IDs in one `modify` call. A
  provider with a lower limit splits the call. It must then apply all parts
  or give an unknown result (section 6).
- `MAX_GETS` (8): the most reads of messages that the sync runs at the same
  time.

### 2. The trait

```rust
pub trait Provider: Send + Sync {
    fn profile(&self, token: &str) -> Result<Profile>;
    fn labels(&self, token: &str) -> Result<Vec<Label>>;
    fn messages(&self, token: &str, label: Option<&str>, page: Option<&str>) -> Result<MessagePage>;
    fn changes(&self, token: &str, from: &str, page: Option<&str>) -> Result<HistoryPage>;
    fn minimal(&self, token: &str, id: &str) -> Result<Minimal>;
    fn metadata(&self, token: &str, id: &str, headers: &[&str]) -> Result<Metadata>;
    fn raw(&self, token: &str, id: &str, sink: &mut dyn Write) -> Result<RawMessage>;
    fn messages_with_id(&self, token: &str, message_id: &str) -> Result<Vec<MessageRef>>;
    fn modify(&self, token: &str, ids: &[&str], add: &[&str], remove: &[&str]) -> Result<()>;
    fn trash(&self, token: &str, id: &str) -> Result<Minimal>;
    fn untrash(&self, token: &str, id: &str) -> Result<Minimal>;
    fn create_label(&self, token: &str, name: &str) -> Result<Label>;
    fn drafts_with_id(&self, token: &str, message_id: &str) -> Result<Vec<Draft>>;
    fn draft_raw(&self, token: &str, id: &str) -> Result<DraftRaw>;
    fn create_draft(&self, token: &str, raw: &[u8], thread: Option<&str>) -> Result<Draft>;
    fn send_draft(&self, token: &str, id: &str, raw: &[u8], thread: Option<&str>) -> Result<Sent>;
}
```

The rules of each call:

- `messages`: all mail, spam and trash included, newest first. With
  `label`, only the messages with that label. One page for each call.
- `changes`: the change records after the cursor `from`, in order, one page
  for each call. The last page gives the new cursor. `Error::HistoryExpired`
  means that the provider cannot give the changes from `from`: the sync does
  a full resync.
- `raw`: streams the RFC 5322 data of the message into `sink`. The provider
  never holds the full message in memory (spec 1 section 9).
- `messages_with_id` and `drafts_with_id`: the messages and the drafts whose
  `Message-ID` header is `message_id`. The send recovery uses them (send
  spec, section 6). They replace the Gmail search strings
  (`rfc822msgid:<id>`), which are not portable.
- `modify`: adds the labels `add` to each message of `ids` and removes the
  labels `remove`.

`token` is the secret that the provider needs for the call: an OAuth access
token for Gmail and Graph, an OAuth token or a password for IMAP. The trait
does not store it. `Error::Unauthorized` tells the caller to get a new
`token` one time, as today.

The trait is object safe (`&dyn Provider`), so that the engine can choose the
provider of each account when it runs. The cost is one indirect call for each
network call, which is small compared to the network time.

### 3. The cursor

The cursor is an opaque string. The caller stores it and gives it back. It
never reads it, and never compares two cursors.

- Gmail: the history ID, as its decimal text. The column
  `account.history_id` is `TEXT` already (schema 1), so the stored values do
  not change.
- IMAP: the provider encodes its state in the string, for example the
  `UIDVALIDITY`, the `HIGHESTMODSEQ` (RFC 7162) and the highest UID of each
  folder.
- Graph: the provider encodes the delta link of each mail folder.

Today the code reads the history ID as `u64`. After this card, the sync and
the verify keep it as `String`. `Profile`, `HistoryPage` and `RawMessage`
carry `cursor: String` in place of `history_id: u64`.

### 4. The label model

The mirror stores labels. Each provider maps its own model to labels, so that
the store, the forms, the policy and the verbs stay the same.

The system labels have the Gmail IDs: `INBOX`, `UNREAD`, `STARRED`, `SENT`,
`DRAFT`, `SPAM` and `TRASH`. Each other label is a user label, with an ID
that the provider gives and that does not change.

| Iris label | Gmail | IMAP | Graph |
|---|---|---|---|
| `INBOX` | `INBOX` | Folder `INBOX` | Well-known folder `inbox` |
| `UNREAD` | `UNREAD` | No `\Seen` flag | `isRead` is false |
| `STARRED` | `STARRED` | `\Flagged` flag | `flag.flagStatus` is `flagged` |
| `SENT` | `SENT` | Folder with `\Sent` (RFC 6154) | Well-known folder `sentitems` |
| `DRAFT` | `DRAFT` | Folder with `\Drafts`, or the `\Draft` flag | Well-known folder `drafts` |
| `SPAM` | `SPAM` | Folder with `\Junk` | Well-known folder `junkemail` |
| `TRASH` | `TRASH` | Folder with `\Trash` | Well-known folder `deleteditems` |
| User label | User label | Other folder, or a keyword | Other folder, or a category |

The verbs map as follows. The apply sends the same `modify` call for each
provider. The provider makes the calls of its own model.

| Verb | Trait call | IMAP | Graph |
|---|---|---|---|
| `archive` | `modify(remove: INBOX)` | `MOVE` (RFC 6851) to the `\Archive` folder | `move` to the well-known folder `archive` |
| `inbox` | `modify(add: INBOX)` | `MOVE` to `INBOX` | `move` to `inbox` |
| `read`, `unread` | `modify(remove or add: UNREAD)` | `STORE` of `\Seen` | `PATCH` of `isRead` |
| `label`, `unlabel` | `modify(add or remove: <label>)` | A folder: `MOVE`. A keyword: `STORE` | A folder: `move`. A category: `PATCH` of `categories` |
| `trash` | `trash` | `MOVE` to the `\Trash` folder | `move` to `deleteditems` |

A folder is exclusive: a message is in one folder. On a folder provider, a
`modify` that adds two folder labels to one message is a definite rejection
(`Error::Api` with status 400). The apply records it as `failed`, as it does
today for a refused call.

The message ID must not change for the life of the message. IMAP gives this
with `OBJECTID` (RFC 8474, `EMAILID`). Graph gives this with immutable IDs
(`Prefer: IdType="ImmutableId"`). Where the server has neither, the provider
reports a move as a delete and an add. The mirror then marks the old message
gone and fetches the new one. The forms of the old message stay on the gone
row (spec 1 section 7). R6-03 and R6-04 state their own choice.

The thread ID comes from the provider: Gmail `threadId`, IMAP `THREADID`
(RFC 8474) or a thread from the `References` and `In-Reply-To` headers, Graph
`conversationId`.

### 5. The error

`Error` keeps the variants of today: `Unauthorized`, `NotFound`,
`HistoryExpired`, `Api { status, reason, message }`, `Transport`, `Decode`
and `Sink`. `Error::write_result_unknown` keeps its rule. A provider that is
not HTTP maps its answers to these variants:

| Answer | Variant |
|---|---|
| The secret is refused (HTTP 401, IMAP `AUTHENTICATIONFAILED`) | `Unauthorized` |
| The message, the label or the draft is not there | `NotFound` |
| The cursor is too old (Gmail HTTP 404, IMAP `UIDVALIDITY` change, Graph HTTP 410 of a delta link) | `HistoryExpired` |
| A definite rejection (HTTP 4xx, IMAP `NO` or `BAD` of a write) | `Api` with a 4xx status |
| A rate limit (HTTP 429) | `Api` with status 429 |
| A server error (HTTP 5xx, IMAP `BYE` during a call) | `Api` with a 5xx status, or `Transport` |
| A lost connection, a time-out | `Transport` |

The display texts of the error stop naming Gmail, because the type is
shared. No code and no test reads these texts (`grep` of the texts in
`crates/` and `client/`).

### 6. The writes of the trait

The trait adds no new write. The apply and the send keep their rules
(spec 2 section 7, send spec section 5). Each provider must keep these rules:

- A write call is made one time. The provider does not try a write again
  after an unknown result.
- `modify` is all or nothing for the caller. If the provider splits it into
  parts and a part fails after another part ran, the result is unknown
  (`Error::Transport`), so that the apply reads the labels and never calls
  again.
- `send_draft` sends the stored `raw` bytes. The IMAP provider sends through
  SMTP submission (RFC 6409) and appends the copy to the `\Sent` folder.
  Graph sends the draft with `send`.

## Options not chosen

- Generic functions (`fn sync<P: Provider>`). Each caller would be compiled
  one time for each provider, and the engine could not choose the provider
  of an account when it runs.
- A `u64` cursor. IMAP and Graph keep a state for each folder, which does not
  fit in one number.
- One trait for each part (a read trait, a write trait, a send trait). The
  three providers have all parts, and three traits add three constructions in
  the engine for no caller.
- A folder model in place of labels. It would change the store, the forms,
  the policy and each verb, and Gmail has no exclusive folders.
- A public library for the trait. The trait is the internal contract of Iris.
  The provider cards choose the protocol libraries (for example `async-imap`
  or `imap` for R6-03).

## Failure list

The trait adds no input path. The supported inputs and the failure modes of
the Gmail answers stay as in spec 1 section 4 and in `iris-gmail`. A
provider that cannot map an answer to the types gives `Error::Decode`, and the
caller handles it as today (a per-message failure in the sync, a failed read
in the apply). This is the safe result for all other input.

## Impact

- New crate `crates/iris-provider`.
- `crates/iris-gmail`: the types move out and are re-exported; `impl Provider
  for Gmail`. The inherent methods stay for the tests of the client.
- `crates/iris-sync`, `crates/iris-apply`: `&dyn Provider` in place of
  `&Gmail`; the cursor as `String`; the error variant `Error::Gmail` becomes
  `Error::Provider`.
- `crates/iris`: the provider construction in `engine.rs` and the verify
  command in `lib.rs`.
- No change to the store, the API, the web client or a data format.

## Assumptions

1. No code compares two history IDs as numbers. Evidence: `grep -rn
   "history_id" crates/iris-sync crates/iris-apply crates/iris` shows only
   parse, store and print uses.
2. `account.history_id` and `account.sync_start` are `TEXT`. Evidence:
   `crates/iris-store/src/schema_1.sql`.
3. The send recovery searches only by `Message-ID`. Evidence: the two
   `rfc822msgid:` strings in `crates/iris-apply/src/send.rs`.
4. The sync always lists with the spam and the trash, and always reads the
   four history types. Evidence: each call of `Gmail::messages` passes
   `true`, and each call of `Gmail::history` passes `HistoryType::ALL`.
5. IMAP and Graph can give each call of the trait. Evidence: RFC 9051,
   RFC 7162, RFC 6154, RFC 6851, RFC 8474 and the Graph mail API (message,
   mailFolder, delta, `$value`, `move`, `send`). Status `pending` until
   R6-03 and R6-04 build them. If a call does not fit, the provider card
   changes this spec and the trait in its own PR.

## External writes

None new. The writes of the trait are the Gmail writes of today, with the
same results on success, on a definite rejection, on an unknown result and on
retry (spec 2 section 7, send spec section 5). Section 6 gives the rules that
each new provider must keep.

## Open questions

- R6-03: the IMAP provider needs a connection for each call or a pool. The
  trait allows both, because it is `Send + Sync` and stores no session state
  for the caller.

## Acceptance criteria

1. `iris-sync` and `iris-apply` do not depend on `iris-gmail` outside their
   tests. Red if `cargo tree -p iris-sync -e normal` or `cargo tree -p
   iris-apply -e normal` lists `iris-gmail`.
2. Each test of the workspace passes with the Gmail provider and the fake
   Gmail server. Red if a test fails.
3. A test calls the sync, the verify and the apply through a `&dyn Provider`
   that is not `Gmail` (a wrapper that counts calls). Red if a caller still
   needs the type `Gmail`.

## Verify

```bash
cargo test --workspace
cargo tree -p iris-sync -e normal | grep iris-gmail   # no output
cargo tree -p iris-apply -e normal | grep iris-gmail  # no output
```

## Rollout

None. The stored cursor values do not change.

## Risks

- A behavior change hides in the move. The full test set of the sync, the
  verify, the apply and the send runs against the fake Gmail server. Rollback:
  revert the PR. No data format changes.
