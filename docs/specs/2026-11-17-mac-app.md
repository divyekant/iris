# Spec: the Mac app

- Date: 2026-11-17
- Card: R6-06
- Status: Draft

## Problem

On a Mac, the engine runs as a background service (`iris service install`).
To use the web client, the person must find the one-time sign-in address in
the log of the service. The address works one time for each start of the
engine. After the first use, the person cannot sign in again from a new tab
until the engine starts again.

The system notices of the engine (card R5-08) come through `osascript`. On
macOS they show as notices of Script Editor, with its icon. A click on the
notice opens Script Editor, not the mail.

The card asks for "a small Mac app that opens the web client of the local
engine and shows system notices".

## Goal

- `iris open` gives a new one-time sign-in address of the running engine, and
  opens it in the browser. A person can sign in again at any time, with no
  restart of the engine.
- A Mac app, `Iris.app`, opens the web client of the running engine in its
  own window, with no step from the person.
- The app shows each new notice as a notice of Iris. A click on the notice
  opens the mail in the app.
- While the app shows the notices, the engine does not show the same notice
  through `osascript`.
- When the window is closed, the app keeps no web view in memory.

## Not in scope

- An engine inside the app. The app uses the engine of the service, and never
  starts a second engine on the same data folder (the engine lock refuses it).
- A data folder other than the default (`~/Library/Application Support/iris`).
  The app reads no environment of a shell.
- Signing with a Developer ID certificate, notarization and automatic update.
  The build makes an ad-hoc signed app on the owner's Mac.
- A Windows or Linux app. Linux has the web client and `notify-send`.
- A macOS CI job (decision of the owner). CI tests the parts of the app that
  are not macOS code.

## Design

The owner picks the shape of the app on an option page (A: window and menu
bar, B: menu bar panel, C: plain window). This section gives shape A, the
recommendation. Shape B changes only the window part. Shape C drops the menu
bar icon and the notices of the app.

### Part 1: a new sign-in code on request (engine)

`iris_api::Auth` keeps a list of one-time codes in place of one code:

- The code of the start (printed by `iris serve`, as now) has no expiry.
- `Auth::sign_in()` makes a new random code of 16 bytes, with an expiry of
  2 minutes, and gives the address `http://<addr>/#code=<code>`.
- At most 8 codes wait at the same time. A new code removes the oldest code
  when 8 wait.
- `POST /api/session` accepts a code one time, before its expiry. Each check
  removes the expired codes.
- The web secret does not change. Each sign-in gets the same secret, as now.

The engine socket (`docs/specs/2026-11-16-engine-socket.md`) gets the verb
`sign-in` with no arguments. The answer is `{"url": "<address>"}`. In
session mode the verb is refused with code 3 (denied).

`iris open` sends `sign-in` and opens the address with `open` (macOS) or
`xdg-open` (Linux). `iris open --print` prints the address and opens
nothing. If no engine runs, the command fails with the code 4 (unreachable)
of specification 2, section 8.4.

### Part 2: notices for the app (engine)

The engine socket gets the verb `app.notices`, args `{"after": <n>?}`:

- With no `after`, the answer is `{"notices": [], "last": <n>, "open": <k>}`.
  `last` is the largest notice row ID that is not done, or 0. `open` is the
  count of notices that are not done.
- With `after`, `notices` holds each notice that is not done and has a row ID
  larger than `after`, oldest first, with the fields of `/api/notices` (`id`,
  `rule_name`, `title`, `text`, `created`, `message`). `last` is the largest
  row ID in the answer, or `after`.
- Each call records the time of the call in the engine (in memory only).
- In session mode the verb is refused with code 3.

`notify::show` does not run `osascript` when an `app.notices` call came 30
seconds or less before. The app calls each 10 seconds, so the engine shows
the notice itself when the app is not running, or stopped 30 seconds before.

### Part 3: the app (`apps/mac/`)

A Tauri 2 app, outside the Cargo workspace of the engine (its own
`Cargo.lock`). It has two parts:

- `src/engine.rs`: the socket client of the app (one JSON line to
  `iris.sock`, one line back), the data folder, and the state of the
  notices. Standard library and `serde_json` only. CI tests it on Linux.
- `src/mac.rs`: the window, the menu bar icon and the notices. It compiles on
  macOS only.

The window:

- One window of 1100 by 760 points, with the title bar style `Overlay` and
  no title. The window buttons sit inside the top bar of the client.
- The web view loads the address of `sign-in`. The client exchanges the code
  as in a browser, and keeps the token in its session storage.
- An initialization script sets `data-shell="mac"` on the root element. The
  client then adds space for the window buttons at the left of its top bar,
  and marks the top bar as the drag area of the window
  (`data-tauri-drag-region`).
- The page of the engine gets one permission of Tauri only:
  `core:window:allow-start-dragging`, for the origin of the engine. No other
  command of Tauri is open to the page. Mail text is data: the page has no
  path to a command that runs on the Mac.
- A link to another origin opens in the default browser, not in the web
  view.
- When the engine does not answer, the window shows a local page of the app:
  "Iris is not running", with the button "Start Iris". The button runs
  `iris service install` (safe to repeat, card R1-24), then tries again.
- Close the window: the window and its web view end. The app stays in the
  menu bar, and leaves the Dock.

The menu bar icon:

- A template image of the Iris mark, so macOS draws it in the color of the
  menu bar. A dot shows when one or more notices are not done.
- The menu: "Open Iris", "Notices" (with the count), "Quit Iris".
- A click on the icon opens the window, or brings it to the front.

The notices:

- A thread of the app calls `app.notices` each 10 seconds.
- For each new notice, the app shows a system notice with the title
  `rule_name` and the text `title: text`, from the bundle ID
  `io.github.divyekant.iris.app`.
- A click on the notice opens the window at `#/mail/<message id>`, or at
  `#/notices` when the mail left the mailbox.

### Memory

The engine part adds a list of at most 8 codes (under 1 KB) and one time
value. The app has two processes on macOS: the app and the web content
process of WebKit. With the window closed, only the app process runs. The
PR of part 3 gives the resident memory of both processes, measured on the
owner's Mac, with the window open and closed.

## Options not chosen

- An engine inside the app (a sidecar). Two engines would fight for the
  engine lock, and the sync would stop when the person quits the app.
- A socket verb that gives the web secret. A one-time code with an expiry
  keeps the secret out of process arguments and logs.
- The Notification API of the browser in the web view. It needs a Tauri
  command open to the page, and works only while the window is open.
- `tauri-plugin-notification`. On desktop it shows a notice but gives no
  click event. `mac-notification-sys` (the crate under `notify-rust`) gives the
  click.
- A native Swift app. The base decision of Iris names Tauri, and a Swift app
  needs Xcode on each build machine.
- HTTP polling of `/api/notices` by the app. It needs the web secret in the
  app process; the socket is already open to the same OS user only.

## Failure list

| Input or event | Result | Test |
|---|---|---|
| `POST /api/session` with a code that expired, was used, or is not in the list | 403, as now. | A unit test of `Auth` with a clock. |
| More than 8 calls of `sign-in` | The oldest waiting code ends. The newest 8 work. | A unit test. |
| `sign-in` or `app.notices` from a session | Code 3. No code is made, no time is recorded. | A socket test in session mode. |
| `app.notices` with `after` that is not a whole number 0 or more, or an unknown argument | Code 2. | A socket test. |
| `iris open` with no engine | Code 4, the reason on standard error. | A command test. |
| The app with no engine | The local page "Iris is not running". | Manual, on the Mac. |
| The engine stops while the window is open | The client shows its access notice (as in a browser). The notice poll fails silently and tries again in 10 seconds. | `engine.rs` test with no socket. |
| An answer line on the socket that is not valid JSON or has the wrong fields | The app skips that poll. | `engine.rs` test. |
| A notice title or text with any characters | The text goes to the notice API as a string. No script, no shell. | `engine.rs` test of the notice words. |
| The app stops between two polls | The engine shows the notices through `osascript` again 30 seconds after the last poll. A notice in those 30 seconds shows in the web client only. | A unit test of the time rule. |

All other input on the socket gets code 2, as the socket spec says.

## Impact

- `crates/iris-api/src/auth.rs`: the list of codes, `Auth::sign_in()`.
- `crates/iris/src/socket.rs`: the verbs `sign-in` and `app.notices`.
- `crates/iris/src/notify.rs`: the time rule of the app.
- `crates/iris/src/lib.rs`: `iris open`.
- `client/src/App.svelte`: the space for the window buttons and the drag area
  under `data-shell="mac"`. `docs/DESIGN.md` gets the rule.
- `apps/mac/**`: the app. `starter.json` gets the area `mac`.
- `docs/DEVELOPMENT.md` and `README.md`: build and install the app.

## Assumptions

- WKWebView loads `http://127.0.0.1:4800` with no App Transport Security
  exception, because ATS does not apply to loopback addresses. Pending: check
  on the owner's Mac. If it is wrong, the app adds
  `NSAllowsLocalNetworking` to its `Info.plist`.
- `mac-notification-sys` 0.6 shows a notice from an ad-hoc signed app and
  gives the click. Pending: check on the owner's Mac. If it is wrong, the app
  shows the notice with no click action, and an issue records the limit.
- The initialization script of Tauri runs on a remote page. Evidence: the
  Tauri 2 `WebviewWindowBuilder::initialization_script` documentation.
- A session cannot reach `iris.sock` (spec 2, section 8.6; the sandbox spec
  `docs/specs/2026-11-17-session-sandbox.md`). So `sign-in` from the socket
  gives no new path to an agent in a sandbox. A process of the same OS user
  outside a sandbox can read the log of the service today, so it gains
  nothing new.

## External writes

None. `iris service install` writes the launchd agent of the person, as the
command does today.

## Open questions

- The size of the app bundle, and the memory of the web content process.
  The build answers them.

## Acceptance criteria

1. `iris open --print` twice gives two addresses, and each address signs in
   one time. Red if the second address is refused.
2. A sign-in code is refused after 2 minutes. Red if a unit test with the
   clock at 121 seconds signs in.
3. `sign-in` and `app.notices` from a session give code 3. Red if a session
   test gets a URL.
4. With an `app.notices` call 10 seconds before, `notify::show` does not run
   the command. With the last call 31 seconds before, it runs. Red if a unit
   test of the rule fails.
5. On the owner's Mac: the app opens the brief with no sign-in step, a new
   notice shows from Iris, and a click opens the mail. Red if any step needs
   the log or a terminal.
6. On the owner's Mac: with the window closed, no WebKit web content process
   of the app runs. Red if `ps` shows one.

## Verify

- `cargo test --workspace` (criteria 1 to 4).
- `cd apps/mac && cargo test` (the app logic).
- On the Mac: `cd apps/mac && cargo tauri build`, open the app, and check
  criteria 5 and 6 with `ps -o rss=,command= -ax | grep -i iris`.

## Rollout

1. The engine PR (parts 1 and 2). It works with no app.
2. The client PR for the top bar (with a before/after page).
3. The app PR (part 3), with the memory numbers from the Mac.

## Risks

- A wrong expiry or list rule could lock the person out. The code of the
  start keeps its old behavior, so `iris serve` in a terminal works as now.
  Rollback: revert the engine PR.
- The deprecated macOS notice API behind `mac-notification-sys` could stop in
  a later macOS. The engine then shows the notices again when the app stops
  its poll; the app can move to `UNUserNotificationCenter`.

## Spec checks

- [x] Each assumption holds with a second caller, worker or tab: each
  sign-in gets its own code; 8 can wait.
- [x] Each assumption holds when an outcome is unknown: a lost `sign-in`
  answer leaves one code that expires in 2 minutes.
- [x] Each dropped mechanism was dropped for a reason that makes it
  unnecessary.
- [x] Each "idempotent" step is not check-then-act: `take_code` checks and
  removes under one lock.
- [x] Each property that the design depends on has a test or a command that
  shows it.
- [x] The spec addresses the hardest problem of the change: a sign-in with no
  log and no restart, and no second engine.
- [x] Each acceptance criterion can go red.
- [x] The assumptions do not contradict each other.
- [x] The failure list names the supported inputs and the safe result for all
  other input.
