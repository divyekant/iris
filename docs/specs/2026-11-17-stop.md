# Spec: one Stop for all agent work

- Date: 2026-11-17
- Card: R4-11
- Status: Agreed

## Problem

Agents run sessions on jobs (R4-04), and approved actions apply to Gmail
(R2-02). Sends leave through the held outbox (R3-02). The person has two
separate brakes: `iris job stop` for one job, and `iris sending off` for
sends. No one control halts all agent work at once. If an agent acts
wrong, the person must find each job, stop it, and turn sending off. Mail
can leave while they do this.

## Goal

1. One Stop halts all agent work: each open session ends, no approved
   action applies, and no held send leaves.
2. The stop stays until the person resumes. It stays after an engine
   restart and after a crash.
3. Stop answers what it cannot know: a Gmail call that started before the
   stop has a result that only the ledger shows.
4. The person can stop from the command line and from the web client.

The card is done when the board `doneWhen` holds: after Stop, no session
runs, no action applies and no mail leaves until the person resumes.

## Not in scope

- A stop of the sync and of the understanding runs. They read mail and
  call the model. They do not change the mailbox, and no mail leaves.
- A restart of the stopped sessions at resume. A stopped session ends.
  The person runs `iris job run` again. A later wake (R5-04) starts a
  waiting job again by its own rule.
- A stop for one account. Stop is for the whole engine.

## Design

### 1. The stop switch

Migration 33 adds one row:

```sql
CREATE TABLE stop_switch (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  stopped_at INTEGER,  -- NULL while Iris runs
  changed_at INTEGER NOT NULL
);
```

`iris_store::stopped(&Connection)` reads `stopped_at`. Each check below
reads it inside the transaction that it guards.

### 2. Stop

`iris_apply::stop(store)` does these steps:

1. One write transaction: set `stopped_at` (keep an earlier value), and
   end each open session (`job_session` with no `ended_at`) with the
   reason `stop`.
2. Wait up to 20 seconds, in total, for two things:
   - The apply lock. The apply and the release hold the lock from the
     claim to the end of the last Gmail call. When Stop gets the lock, no
     Gmail write call runs, and each later claim reads the switch.
   - The reap of each session that it ended (`reaped_at` set). The
     supervisor of the engine sees each ended session at its next turn
     (1 second), and the helper stops the agent process group, as for
     `iris job stop`. Only the reap check confirms that no process of the
     session runs.
3. Give the number of sessions that it ended, the number of all sessions
   that are not reaped at the end of the wait (`live`, also sessions that
   an earlier stop ended), and whether a Gmail call was still in progress
   (`busy`).

Step 1 always commits first, so a busy apply lock or a slow reap never
delays the switch or the end of the sessions in the store.

Stop is complete only when `live` is 0 and `busy` is false. Otherwise the
answer says that the stop is not complete, names the sessions that still
run (`iris job session <j-id>` shows each), and says that the person can
press Stop again. A second Stop waits again for the same sessions.

If the supervisor does not act (the engine hangs), an agent process can
run after Stop returns, and `live` is not 0. The agent cannot change
anything through Iris: the session socket refuses each request of an ended
session ("the session ended"), and no claim and no register pass the
switch. If the engine is down, the helper stops the agent when its pipe
to the engine closes, and the next engine start ends each open session
(R4-04e). On Linux no agent process then runs. On macOS a process that
escaped the stop of the helper can run while the engine is down and until
a later `stop` catches it (macOS sandbox spec, "The change of the lifetime
rule"). It cannot change anything through Iris for the reasons above, its
Seatbelt profile keeps it away from the data folder and other sessions,
and its proxy closes with the engine. Stop reports such a session in
`live` until the reap, so the person sees that it still runs.

### 3. Resume

`iris_apply::resume(store)`: one write transaction. It sets `stopped_at`
to NULL only if it is set. Only in that case, and only if sending is on,
it sets `send_switch.on_at` to the time of the resume. A resume while Iris
runs changes nothing, so a repeated resume does not move a hold. A held send waits for `max(decided_at, on_at) + HOLD_MS` (R3-02),
so each held send gets its full hold of 60 seconds after the resume. The
person can cancel it in that time. The claim of the release reads `on_at`
and the hold again in its transaction. So a stop and a resume during the
read of the draft at Gmail, after the first hold check, also restart the
hold.

### 4. The checks while stopped

| Path | Check | Result while stopped |
|---|---|---|
| Register of a session (`iris_job::register_in`) | Trigger `job_session_stop` on INSERT | Refused: "Iris is stopped." No session row. |
| Claim of an apply and of a release (`gate` in `iris-apply`) | `stopped()` in the claim transaction | `Outcome::Stopped`. The action stays `approved` or `held`. |
| Each later call of a claimed apply (the cutoff of a revoke) | `stopped()` in the cutoff transaction | The calls that ran stay done. The action ends `failed` with the reason "You pressed Stop." |
| Apply of a state verb (`apply_in`) | `stopped()` in its transaction | `Outcome::Stopped`, unless the author of the changeset is the person. |
| New ledger row in `writing` | Trigger `ledger_stop` on INSERT | Refused, unless the action is a state verb of a person. |
| Apply step of the engine | `stopped()` at the start of steps 2 and 4 | The step skips the apply and the release. The recovery (step 1) runs. |

The two triggers are the backstop: no code path can claim an action or
register a session while stopped, also a path that a later card adds.

The direct verbs of the person (close, decline, defer, correct, skip,
mute, dismiss, restore) still apply. They change only the items in the
store, and the person does them.

The recovery still runs, because it only reads Gmail. It moves a ledger
row in `writing` to its true state, so the ledger shows the result of a
call that started before the stop.

### 5. Commands and API

| Surface | Stop | Resume | State |
|---|---|---|---|
| Command | `iris stop` | `iris resume` | `iris stop --show` |
| API | `POST /api/stop` | `POST /api/resume` | `GET /api/stop` |

The answer of each is `{"stopped": bool, "since": time|null, "sessions": n,
"live": n, "busy": bool}`. `sessions` comes only from Stop. Each state
read measures `live` and `busy` again, with no wait: the switch alone never
says that a stop is complete. Only a complete stop says that no mail
leaves.

The commands write the store, so the switch and the end of the sessions
also work with no engine. A session
cannot run them: the session mode refuses each command that is not a
session verb (R4-04i), and the sandbox has no data folder (R4-05). They
are not MCP tools (`NOT_TOOLS`).

### 6. The client

A Stop control in the top bar of each view. While stopped, a band at the
top says that Iris is stopped and since when, with a Resume button. The
layout goes to the owner on a before/after page. It is a separate PR.

## Options not chosen

- Stop through the engine socket only: the switch must work when the
  engine is down or hangs. A store write works in both cases. The reap
  still needs the supervisor, so the answer reports `live`.
- Turn sending off at Stop: a resume must then turn sending on, which needs
  a typed "yes" at a terminal (R3-02). Stop is a separate switch.
- Keep a stopped session paused: the hold helper has no pause, and a paused
  agent holds its model egress. An end is clean and visible.

## Failure list

| Case | Result | Test |
|---|---|---|
| Stop during a launch, before the register | The trigger refuses the register. The launch ends with no session. | `stop_ends_each_session_and_refuses_a_register` |
| Stop during a launch, after the register | Step 1 ends the session. The gate of the launch reads the end and does not start the agent. | `a_stop_during_the_launch_cancels_it_with_no_retry` (R4-04h): the gate refuses an ended session |
| The supervisor does not reap in 20 seconds | Stop answers `live` > 0: not complete. The session socket refuses each request of the session. | `stop_ends_each_session_and_refuses_a_register` (`live` 1) |
| Stop during an apply of one call | The call ends. Its result goes to the ledger. Stop waits for the lock, or answers `busy`. | `stop_waits_for_the_apply_lock` |
| Stop during an apply of many calls | The next call does not start. The action ends `failed`, and the ledger lists the changed messages. Undo works for them. | `a_stop_between_two_calls_stops_the_later_calls` |
| Stop after the check and before the claim (a label create ran) | The claim refuses. The action stays `approved`. The new label stays, with no message. | `no_action_applies_while_stopped`: the claim and the check use the same `gate` |
| Stop and resume during the read of the draft by a release | The claim reads the new `on_at`. The send stays `held` for a full hold. | `a_stop_and_resume_during_the_release_restart_the_hold` |
| Stop during a send | The `drafts.send` call ends. If its answer comes, the ledger shows `applied` or `failed`. If the answer is lost, the row stays in `writing`, and the recovery reads Gmail and decides. Stop answers `busy` while the call runs. | `no_send_leaves_while_stopped_and_resume_gets_a_full_hold`, `the_step_recovers_a_lost_send_while_stopped` |
| Crash or engine restart while stopped | The switch is in the store. Each check reads it, so nothing applies after the restart. | `no_action_applies_while_stopped` (a new connection) |
| Crash during Stop step 1 | The transaction rolls back. Nothing changed. The person presses Stop again. | none (SQLite atomic commit) |
| Two Stops | The second keeps the first time. It ends any new open session. | `stop_ends_each_session_and_refuses_a_register` |
| Resume while not stopped | No change: the switch and `send_switch.on_at` stay. | `no_send_leaves_while_stopped_and_resume_gets_a_full_hold` |
| Any other input to the API (a body, a bad method) | 400 or 405. The switch does not change. | `other_input_changes_nothing` |

## Impact

- `crates/iris-store`: migration, `stopped()`.
- `crates/iris-apply`: `stop`, `resume`, the checks, `Outcome::Stopped`.
- `crates/iris`: the commands, `NOT_TOOLS`, the engine report of
  `Outcome::Stopped`.
- `crates/iris-api`: the three routes.
- `client/`: the control (separate PR).

## Assumptions

- The apply and the release hold the apply lock from the claim to the end
  of their last call. Evidence: `crates/iris-apply/src/send.rs`, the
  comment in `claim`, and `set_sending`.
- The supervisor ends the agent of a session that ended in the store, and
  sets `reaped_at` after the reap check. Evidence:
  `crates/iris/src/sessions.rs`, the supervisor turn and `reap_one`.
- The session socket refuses each request of an ended session. Evidence:
  `crates/iris/src/session_socket.rs` ("the session ended") and its test
  `a_request_of_an_ended_session_gets_code_3`.
- The recovery makes no write call. Evidence: `crates/iris-apply/src/lib.rs`,
  `Run::recover` ("read, never call again").

## External writes

Stop and resume make no external call. They stop the external writes of
the apply and the release. The table of the failure list gives the result
of a write that started before the stop.

## Open questions

None.

## Acceptance criteria

1. After Stop, a register of a session fails. Red if the trigger is gone.
2. After Stop, an approved action does not apply, and a held send does not
   leave. Red if `gate` does not read the switch.
3. After Stop and a reopen of the store, criterion 2 still holds.
4. After resume, a held send waits a full hold. Red if resume does not move
   `on_at`. A second resume does not move `on_at`. Red if it does.
5. Stop with an ended session that is not reaped answers `live` 1. Red if
   Stop counts only `ended_at`.
6. The person can close an item while stopped.

## Rollout

The migration adds the switch in the state "running". No config.

## Risks

A Stop that the person forgets keeps all agent work halted. The client
shows the band on each view, so the state is visible.

Rollback: the migration raises the schema version, and an older program
refuses a newer store (`UnknownSchema`). So a revert of the code cannot
open the store. Do one of these:

- A forward fix: a new PR that changes the code. The switch row stays.
- A restore of the backup that the person made before the update
  (`iris backup`). Each change after the backup is lost: new mail syncs
  again, but decisions, ledger entries and items after the backup are
  gone.
