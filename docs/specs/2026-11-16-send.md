# Spec: send through Gmail

- Date: 2026-11-16
- Card: R3-01 (send through Gmail: replies and new mail, with correct
  threads)
- Status: Draft

## Problem

Iris can read, sort and label mail, but it cannot write mail. Release 3
adds the verbs `draft` and `send` (spec 2, section 4). Spec 2, section 7.5
gives the constraints of these verbs and leaves the design to a later
specification. This spec is that design for the draft and the send
itself. A send is the most dangerous write of Iris: it cannot be undone,
and a second send of the same mail is visible to other people.

## Goal

1. An author makes an Iris draft at Gmail with a `draft` action: a new
   mail, or a reply in a thread. An approved `draft` action creates the
   draft at Gmail.
2. An approved `send` action of an Iris draft sends it with
   `drafts.send`. A reply goes into the correct Gmail thread.
3. Iris never makes the `drafts.send` call of an action two times. Iris
   never sends one draft two times.
4. Each `draft` and `send` action has its ledger entry (spec 2, section
   7.1) and a crash test.

## Not in scope

- The state `held`, the outbox view and the cancel button (R3-02). This
  card gives the release step for an `approved` send only. The release
  step keeps the hold delay itself (section 5, step 1), so no caller can
  send at once (spec 2, C4). R3-02 moves a send to `held` and changes the
  gate and the triggers (section 5.1).
- The checks before the send and the flags `new_recipient`, `money`,
  `date`, `untrusted_content` and `outside_thread` (R3-03). R3-03 adds
  them at submit and at the release. In this card, each `draft` and
  `send` action goes to review.
- An engine path that calls the release. No engine path, command or API
  calls the release step until R3-02 and R3-03 are both done and the
  owner checked assumption 6. On the board, R3-02 depends on R3-03 for
  this reason. Until then, an approved `send` waits, and a withdraw
  cancels it. Only the tests call the release step.
- A change of a draft (a `draft` action with a draft target). Spec 2,
  section 7.5 needs an undo that restores the old content of a changed
  draft. A later card (R3-04, the write view) adds the change and its
  undo together. In this card, a new content is a new draft.
- The write view and the reply from a conversation (R3-04, R3-10).
- `nudge` (R3-07), drafts in your voice (R3-05).
- The undo of a draft create. A create has no old content to restore,
  and Iris never deletes a draft at Gmail (spec 2, section 7.5), so the
  ledger `undo` of a create is `none`. The person deletes an unwanted
  draft in Gmail.
- HTML bodies and send-as aliases. Each one gets a limit issue.
  Attachments, `Bcc` and the display name of `From` are in
  `docs/specs/2026-11-24-send-content.md`, which changes sections 1, 2
  and 6 of this spec.
- Policy rules for `draft` and `send`. The policy file refuses a rule with
  these verbs, so no rule can allow a send. Spec 2, section 6.2 says
  this for the field `verbs`.

## Design

### 1. The draft content

A draft has this content, as JSON:

```json
{"to": ["priya@example.com"], "cc": [], "subject": "Q4 numbers",
 "body": "Hi Priya,\n\nThe numbers are attached.\n"}
```

- `to`: 1 to 50 addresses. `cc`: 0 to 50 addresses. The sum is 50 or
  fewer. Each address is `local@domain`, ASCII, with no space, no control
  character and none of `<>()[],;:"\`. Iris compares addresses in lower
  case and removes duplicates.
- `subject`: 1 to 998 characters, with no control character. A subject
  with `=?` goes out as RFC 2047 encoded words (`=?utf-8?B?...?=`), because
  a reader decodes `=?..?=` in plain text as an encoded word (#270). The
  normal form has no
  space at the ends and one space for each run of white space. For a
  reply, Iris sets the subject (section 3), and the author gives none.
- `body`: UTF-8 text, 256 KiB or less, with no NUL character, and with
  one or more characters that are not white space (issue #741). Iris sends
  it as `text/plain; charset=utf-8`. The normal form has LF line ends.

The content hash is the SHA-256 (hex) of the canonical JSON of the
content, plus `in_reply_to` and `references` for a reply. The canonical
JSON has sorted keys and no spaces. The approval of a `send` binds to this
hash (spec 2, section 7.5).

A read back (section 2) gives a content only for a message that has
exactly the form that Iris writes: one `text/plain` part and only the
headers `From`, `To`, `Cc`, `Subject`, `Date`, `Message-ID`,
`In-Reply-To`, `References`, `MIME-Version`, `Content-Type` and
`Content-Transfer-Encoding`. `From` must be one mailbox with the account
address. Iris checks `From` by address only: a display name on `From` is
allowed, because Gmail can add the display name of the account to a draft
or to a sent copy (pending: the owner check of #302). A display name does
not change the recipients or the content. A `Received` header, at any
count, is ignored: Gmail adds one to each draft (assumption 3), and it
does not change the recipients or the content. Any other
header (for example `Bcc`, `Reply-To` or `Sender`), any other part or
attachment, or another `From` gives no content. The content read back
must also pass the checks of a new draft (section 1, for example at most
50 recipients and a 256 KiB body) with no change: a duplicate address or
an address in upper case gives no content, because the hash cannot hold
it. The
`To`, `Cc`, `Subject`, `Message-ID`, `In-Reply-To` and `References` headers, as
`mail-parser` reads them, must be the same as in the message that Iris
writes for the content read back: a display name, a group, a comment or
a change of the white space in the subject gives no content. An
`In-Reply-To` or `References` header that the content does not hold
(for example `References` with no `In-Reply-To`) gives no content. A
draft with no content never agrees with an approved hash.

### 2. The message

`iris-compose` (a new crate, pure functions) makes the RFC 5322 message
with `mail-builder`:

- `From`: the address of the account.
- `To`, `Cc`, `Subject`, `Date`.
- `Message-ID`: `<iris.<32 random hex>@<domain of the account>>`. Iris
  makes it once for each draft, before the create. Gmail replaces it
  with its own ID (assumption 3), so after the create the `draft` row
  keeps the ID of Gmail (section 4, step 3).
- For a reply: `In-Reply-To` and `References` (section 3).
- The body as `text/plain; charset=utf-8`.

The `draft` row keeps the exact bytes of the message that Iris wrote
(`raw`). The release sends these bytes (section 5), not the text that
Gmail has.

`iris-compose` also reads a raw message back (`mail-parser`) to the
content, so the engine can compute the hash of a draft as Gmail has it.

### 3. Replies and threads

Gmail puts a draft or a message into a thread when the call gives the
`threadId`, the `References` and `In-Reply-To` headers agree with RFC 2822,
and the subjects agree. For a reply in the thread `t-N`:

- Submit chooses the parent: the newest message of the thread in the
  mirror, by internal date, that has no `DRAFT` label, is not gone and
  is not in `SPAM` or `TRASH`. Submit resolves the thread target to this
  one message (`resolved`, spec 2, section 5.1), so the action hash
  covers it and the review shows it. The apply uses only this message.
  It never chooses again: a message that comes into the thread after the
  submit is never the parent. If the parent is gone at the apply, the
  apply denies the action ("the parent message is gone"), and the author
  makes a new `draft` action.
- The hostile check of spec 2, section 6.5 reads each message of the
  thread, not only the parent, at submit and again at the apply. A gone
  message counts too. A gone message with no header (after the content
  cleanup) counts as hostile, because its sender is no longer known.
- `In-Reply-To`: the `Message-ID` of the parent.
- `References`: the `References` of the parent (a `messages.get` of the
  parent with `format=metadata`, at the apply), then
  the `Message-ID` of the parent. If the parent has no `References`, its
  `In-Reply-To`, then its `Message-ID`.
- `Subject`: the subject of the parent with `Re: ` in front. If the
  subject starts with `Re:` in any case, it stays the same.
- The `drafts.create` call gives the Gmail thread ID of the thread.

`iris-compose` takes each ID of these header values: each `<...>` is
one ID. An ID with white space or a character that is not printable
ASCII is dropped. If the parent `Message-ID` does not give exactly one
ID, the apply denies the `draft` action: Gmail cannot thread the reply. The `draft` row keeps the reply headers in
its content, so a send uses the headers of the create.

### 4. The `draft` verb

| Target | Meaning | Args |
|---|---|---|
| `{"accounts": ["a-N"]}` | A new mail from the account | `to`, `cc`, `subject`, `body` |
| `{"threads": ["t-N"]}` | A reply in the thread | `to`, `cc`, `body` |

Each `draft` action has exactly one target. A draft target (`d-N`) is
not valid for `draft` in this card (see Not in scope): submit denies it. The ID kind `a` names an
account row (`a-N`), and `d` names a draft row (`d-N`). Spec 2, section
4 and the open model schema get the target groups `accounts` and
`drafts`.

Submit checks the args (section 1) and denies an action that breaks a
rule, with the reason. For a reply, the hostile check of spec 2, section
6.5 applies to the thread (section 3): an author other than `person`
cannot draft a reply in a thread with hostile mail.

The apply of an approved `draft` action:

1. Gate: as for the other verbs (expiry, observe mode, only person
   approvals apply, the action hash). For a reply, the parent of
   section 3.
2. Claim: in one transaction, the ledger row in `writing`, with `ops`:
   the call `drafts.create`, the `Message-ID`, the `Date` of the message
   (seconds) and the content hash. `post`: the content with its reply
   headers. Iris saves the `Message-ID` before the call (spec 2, section
   7.5). The message is `compose(account, Message-ID, post, Date)`: the
   same input gives the same bytes, so recovery can make the bytes again.
3. Call `drafts.create` one time (section 5.2). On success, read the
   draft back (`drafts.get`, `format=raw`). If it reads back (section 1)
   with the content hash of the claim, its `Message-ID` is the ID of
   Gmail (assumption 3). Then, in one transaction: insert the row of the
   `draft` table (content, hash, Gmail draft ID, the `Message-ID` and the
   raw bytes that `compose` makes with that `Message-ID`), and set the
   ledger row `applied`, with `undo` `none`. If the read fails or gives
   other content, the row keeps the ID of Iris and the bytes of the
   claim. The release check (section 5, step 2) always compares with the
   `Message-ID` of the row, so this fallback fails the check. Then the first release denies the send and refreshes the row
   (section 4.1), and the person approves the send again.

### 4.1 A draft that the person changed at Gmail

The person can change an Iris draft in Gmail. When the release reads the
draft at Gmail and its read back hash is not the hash of the `draft` row,
the engine refreshes the row in the same transaction as the denial:

- If the Gmail draft reads back (section 1), the row gets its content,
  its hash, its reply headers, its `Message-ID` and its exact bytes. The
  `Message-ID` can differ from the ID of the row (assumption 3). It is
  not in the content hash, so it does not change who gets the mail. Only
  a provider that sets its own ID on a draft (Gmail) takes another ID
  here, and only Gmail gets the read back of section 4, step 3. For
  Outlook, another ID means another client changed the draft: the row
  gets `foreign_at` (Outlook spec, section 5). This is a copy of
  Gmail state into the store, as the mirror does, not a write to Gmail.
  A new `send` action then binds to the content that the person wrote,
  and the review shows it.
- If it does not read back (for example, the person added an attachment
  or a `Bcc`), the row gets `foreign_at` (the time). Iris can no longer
  send the draft: submit denies a `send` action of it, and the person
  sends it from Gmail. This is a known limit with its own issue.

### 5. The `send` verb

The target is one Iris draft: `{"drafts": ["d-N"]}`. Args: `{}`. Submit
denies a send of a draft that is not in the `draft` table, of a draft
with another open send (`proposed`, `in_review`, `approved` or `held`),
and of a draft with a `ledger_send` row (section 7).

The action hash of an action with a draft target (`action_draft`) also
covers the `hash` of the `draft` row, after the message IDs. So the
approval of a send binds to the content, and the hash check of the apply
and the release (spec 2, section 5.5) refuses the action if the draft row
changed after the approval. Spec 2 gets this rule for `actions[].hash`.

`iris_apply::apply` does nothing for a `send` action: the action stays
`approved`. The release step `iris_apply::release` sends it:

1. Gate: the action is `approved` by a person, not expired, and its
   approval (`decided_at`) is 60 seconds old or more
   (the hold delay of spec 2, section 7.5). The approval time is stored,
   so the hold survives a restart. The token is of the account. The
   action hash still agrees with its rows, so the `draft` row has the
   approved content hash.
2. Read the draft at Gmail (`drafts.get`, `format=raw`). If Gmail does not
   have it (HTTP 404), the engine denies the action (`denied` by
   `engine`, "the draft is gone at Gmail"): no call went out, so the
   action has no ledger entry. If the read back gives no content, or its
   `Message-ID` is not the `Message-ID` of the `draft` row, or its hash
   is not the
   approved hash, the engine denies the action with the reason "the
   draft changed at Gmail after the approval", and refreshes the draft
   (section 4.1). The author or the person makes a new `send` action of
   the draft, with the new hash, and it goes to review. A denial, not a
   move back to `in_review`, because the approval hash of an action does
   not change after its submit.
3. Claim: in one transaction, the ledger row in `writing`, with `ops`:
   `drafts.send`, the Gmail draft ID, the `Message-ID`, the hash, and
   `call` 1, and the `ledger_send` row of the draft. The primary key of
   `ledger_send` is the draft, so only one claim of a draft can commit,
   for each writer.
4. Call `drafts.send` one time (section 5.2), with the draft ID and, as
   the message of the draft, the `raw` bytes of the `draft` row and the
   thread ID. Gmail sends the message of the request, so an edit at Gmail
   between step 2 and this call does not change what goes out
   (assumption 6).
   - Success: the ledger row stays in `writing`, and the completion of
     section 6 runs with the sent message ID of the answer.
   - A definite rejection (HTTP 4xx, except the rate limits of section
     5.2): the ledger row becomes `failed`, with the reason of Gmail, and
     the transaction deletes the `ledger_send` row. The draft stays, and
     the person can approve a new send.
   - An unknown result (a rate limit, HTTP 5xx, a network error, an
     answer that cannot be read, a crash): the ledger row stays in
     `writing`. Recovery decides.

### 5.1 What R3-02 changes

R3-02 adds the state `held` to the release. This card does not build
it, but R3-02 must make these changes, so that a held send can claim and
finish its ledger entry:

- The trigger `ledger_insert` accepts an action in `held` for the verb
  `send`, in addition to `approved`.
- The trigger `action_state` accepts the moves `held` to `applied`,
  `failed` and `denied` (by `engine`), in addition to `held` to
  `cancelled`. The move `held` to `denied` is for a draft that changed
  or is gone at Gmail (section 5, step 2).
- The gate of the release accepts `held` in place of `approved`, and the
  claim moves the action only if it is still `held`
  (`UPDATE ... WHERE state = 'held'` in the claim transaction). A cancel
  moves the action only if it is still `held`. Both run on the one write
  connection, so only one of the two commits.

### 5.2 One request for each write call

The Gmail client tries a call again after a rate limit (HTTP 429, or
HTTP 403 `rateLimitExceeded` or `userRateLimitExceeded`). The calls
`drafts.create` and `drafts.send` use a write path that never tries
again: the client sends one request and gives each status to the caller.
The engine reads a rate limit as an unknown result, not as a rejection,
so recovery decides with a search at Gmail and never with a second call.

### 6. Completion and recovery of a send

The completion of a sent message: read the sent message
(`messages.get`, `format=raw`), then in one transaction set the draft
`sent_at` and `sent_message` (the Gmail message ID), and set the ledger
row `applied`. The check of the sent message is not the read back of
section 1, because Gmail can add transport headers (for example
`Received` or `X-Gm-*`) to the sent copy. It reads only the fields of
the content hash: `To`, `Cc`, `Subject`, the body of the one
`text/plain` part, `In-Reply-To` and `References`, and it ignores each
other header, except the headers that change who gets the message or
the answer: `Bcc`, `Reply-To`, `Sender` and each `Resent-` header. A
sent message with one of these headers, with a `From` that is not the
one account address, with no `Message-ID`, with no `text/plain` part,
with other parts, or with an attachment gives no content. A known header
(for example `To`) two times also gives no content. If the hash of these
fields is not the approved hash, or there is no content, the same update writes the error "Gmail sent other content
than the approved content" (the ledger allows an error only in
`writing`, so it goes in the same update as the state). A ledger send row
with this error stops each later release until the owner checks
assumption 6. If the read fails, the row stays in `writing`, and
recovery completes it. The ledger `post` stays as the claim wrote it:
the sent message ID goes into the `draft` row.

Recovery runs for each ledger row of the account in `writing`, before
each apply and each release (as in R2-03). For a `drafts.send` row, it
never calls `drafts.send`. It does these steps:

1. Search at Gmail, not in the mirror: `messages.list` with
   `q=rfc822msgid:<Message-ID>` and `includeSpamTrash`. If Gmail gives a
   message with the label `SENT`, run the completion with it.
2. Else, if the claim (ledger `at`) is 24 hours old or more, the row
   becomes `failed`, with the error "unknown: Gmail shows no sent
   message". The `ledger_send` row stays, so Iris never sends the draft
   again (section 5).
3. Else the row stays in `writing`. The draft has no new send while the
   row is in `writing`.

Only a definite rejection (section 5, step 4) deletes the `ledger_send`
row. An unknown result never does: a draft that is still at Gmail, or
the time that passed, does not prove that Gmail did not run the
request, and Gmail can still finish it. After an unknown result, the
person resolves the draft in Gmail: the person sends it there, or
deletes it. A new mail from Iris is a new draft. This is a known limit
with its own issue.

A `drafts.create` row in `writing` searches `drafts.list` with
`q=rfc822msgid:<Message-ID>`, with the ID of the claim. A found draft
becomes the `draft` row as in section 4, step 3, and the ledger row
becomes `applied`, in one transaction. Else the row becomes `failed`.
Gmail replaces the ID of the claim (assumption 3), so on real Gmail the
search finds nothing, and an unknown create becomes `failed`. Gmail can
still have made the draft, but a draft at Gmail is not a send: the
person can delete it. This is a known limit with its own issue.

### 7. Store (migration 18)

```sql
CREATE TABLE draft (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id INTEGER NOT NULL REFERENCES account(id),
  thread_id INTEGER REFERENCES thread(id),   -- NULL for a new mail
  provider_id TEXT NOT NULL,                 -- the Gmail draft ID
  message_id_hdr TEXT NOT NULL UNIQUE,       -- the Message-ID of the draft at Gmail (section 4, step 3)
  content TEXT NOT NULL CHECK (json_valid(content)),
  hash TEXT NOT NULL,
  raw BLOB NOT NULL,                         -- the message that Iris wrote
  action_id INTEGER NOT NULL UNIQUE,         -- the draft action that made it
  sent_message TEXT,                         -- the Gmail ID of the sent message
  foreign_at INTEGER,                        -- Gmail has a form that Iris does not write
  sent_at INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE (account_id, provider_id)
);
-- The one send of each draft that can have gone out. A send that Gmail
-- did not do (a definite rejection only) deletes its row.
CREATE TABLE ledger_send (
  draft_id INTEGER PRIMARY KEY REFERENCES draft(id),
  ledger_id INTEGER NOT NULL UNIQUE REFERENCES ledger(id)
);
CREATE TABLE action_draft (
  action_id INTEGER PRIMARY KEY REFERENCES changeset_action(id),
  draft_id INTEGER NOT NULL REFERENCES draft(id)
);
```

The migration also adds `draft` and `send` to the verb `CHECK` of
`changeset_action`. SQLite cannot change a `CHECK` in place, so the
migration uses the documented SQLite procedure for a schema change that
does not change stored rows (`PRAGMA writable_schema`, in one
transaction, with `integrity_check` after). The ID kinds `a` (account) and `d` (draft) are new. The open model schema (`changeset.schema.json`) gets the verbs
and the target groups `accounts` and `drafts`.

## Options not chosen

- Keep drafts only in Iris and send with `messages.send`: spec 2, section
  7.5 needs the draft at Gmail, so that the person sees it on each device
  and the release reads it again.
- Write the RFC 5322 text by hand: `mail-builder` (Stalwart, the authors
  of `mail-parser`, which Iris uses) encodes headers and bodies and is
  maintained (2.0.1, 2026-11-02). `lettre` also builds messages, but it
  brings an SMTP client that Iris does not need.
- A new table copy for the `CHECK` change: it must copy and make again
  each trigger and index of `changeset_action` (migrations 7 to 11). The
  `writable_schema` procedure changes only the table text.
- Send again after an unknown result: it can send two times. Spec 2 forbids
  it.

## Failure list

Supported input: the draft content of section 1, a thread of the mirror
with a parent `Message-ID`, an Iris draft.

| Input or event | Result | Test |
|---|---|---|
| An address with a space, CR, LF, `<`, `>`, `,` or non-ASCII | Submit denies the action | property test of the address check |
| A subject with CR or LF | Submit denies the action | property test |
| Any content that passes the checks | Compose, then parse, gives the same content and hash, and no other header | property test (`proptest`) |
| More than 50 recipients, a body over 256 KiB | Submit denies the action | unit test |
| A body that is empty or only white space | Submit denies the action ("a draft needs a body"). A draft with no text that an older build saved does not read back, so its send is denied | unit test of the check; changeset submit test |
| A reply whose parent has no `Message-ID`, or not exactly one ID in it | The apply denies the action (it reads the header at Gmail, because sync does not store it) | test of the draft apply |
| The person changes the draft at Gmail after the approval | The release denies the action, and sends nothing | fake Gmail test |
| Gmail sets its own `Message-ID` and `Date` on a new draft, and adds a `Received` header | The read back ignores `Received`; the `draft` row keeps the ID of Gmail; the release sends | unit test with the real raw shape; the fake Gmail makes this shape for each draft |
| The read back after the create fails | The row keeps the ID of Iris; the first release denies the send and refreshes the row with the ID of Gmail; a new approval sends | fake Gmail test with a 404 on the read |
| The person adds a `Bcc`, a `Reply-To`, an attachment or HTML at Gmail, and keeps the rest | No read back content: the release denies the action | fake Gmail test with a `Bcc` header |
| The person changes the draft between the read and the send call | Gmail sends the `raw` of the request (assumption 6) | fake Gmail test: the fake edits the draft before the send |
| The person deletes the draft at Gmail | The release denies the action, and sends nothing | fake Gmail test |
| HTTP 5xx or a lost answer of `drafts.send`, the mail went out | Recovery finds it by `rfc822msgid`, `applied` | fake Gmail `fail_next_write(applied=true)` |
| The same, the mail did not go out | The row stays in `writing`; after 24 hours, `failed`; the `ledger_send` row stays; no second call | fake Gmail test with a clock |
| A crash after the claim, before the call | As the line above | crash test |
| Two releases of one draft at the same time | One claim wins (`ledger_send` primary key); the other gets `Busy` or a refusal, and makes no call | test with two connections |
| A `draft` action with a draft target | Submit denies it | unit test |
| A reply, and a new message comes into the thread after the submit | The apply uses the parent of the submit, not the new message | fake Gmail test |
| A reply whose parent is gone at the apply | The apply denies it, and makes no call | unit test |
| The person edits the draft at Gmail, then a release | The release denies it; the row gets the Gmail content; a new send binds to it | fake Gmail test |
| A release less than 60 seconds after the approval | The release refuses it and sends nothing | unit test with a clock |
| A rate limit answer of `drafts.send` | One request only; recovery decides | fake Gmail test with a 429 |
| The parent is gone at the apply, and the thread has an older message | The apply denies it, and never chooses the older message | unit test |
| The sent copy has a transport header (for example `Received`) | The completion ignores it, and the row becomes `applied` | unit test of the sent check |
| The sent copy has a `Bcc`, `Reply-To`, `Sender` or `Resent-` header, another `From`, or no `Message-ID` | No content: the error "Gmail sent other content than the approved content" | unit test and property test of the sent check |
| A lost answer of `drafts.send`, Gmail sent other content | Recovery writes the error, and later releases stop | fake Gmail test |
| Any other input | The engine denies the action or fails it, and sends nothing | |

- `crates/iris-gmail`: `drafts.create`, `drafts.get` (raw),
  `drafts.send`, `drafts.list` and `messages.list` with `q`, and the

- `crates/iris-policy`: refuses `draft` and `send` in a rule.

## Assumptions

1. Gmail threads a draft or a message when the call gives `threadId`, the
   `References` and `In-Reply-To` headers agree with RFC 2822, and the
   subjects agree. Evidence: Gmail API guide "Managing threads"
   (developers.google.com/gmail/api/guides/threads).
2. `drafts.send` sends the draft and removes it from the drafts. Evidence:
   Gmail API reference, `users.drafts.send`. A wrong assumption makes
   recovery wait 24 hours (step 3), not send two times.
3. Gmail does not keep the `Message-ID` that Iris sets in a draft. At
   `drafts.create`, Gmail sets its own `Message-ID`
   (`<CA...@mail.gmail.com>`), sets a new `Date` and adds a header
   `Received: from ... by gmailapi.google.com with HTTPREST`. Evidence:
   the send check on the owner's Mac (issue #302, draft d-1, 2026-11-18).
   So the engine reads each new draft back and keeps the ID of Gmail
   (section 4, step 3), and the read back of a draft ignores `Received`
   (section 1). The send carries the ID of Gmail in its bytes. `pending`:
   Gmail keeps that ID at `drafts.send` (owner's Mac, issue #302). If
   Gmail sets one more ID at the send, the search of the send recovery
   finds nothing, and an unknown send becomes `failed` after 24 hours with
   no second send. A send with a known result does not use the search.
4. `messages.list` and `drafts.list` take `q=rfc822msgid:<id>`. Evidence:
   Gmail search operators (support.google.com/mail/answer/7190). `pending`
   on the owner's Mac. If it fails, recovery of a create or a send becomes
   `failed`, with no second call, which is safe.
5. The scope `gmail.modify` allows `drafts.create` and `drafts.send` (spec 2, `## Assumptions`). Iris never calls `drafts.delete`.
6. `drafts.send` with a `message` in the request body sends that message,
   not the older message of the draft. Evidence: the request body of
   `users.drafts.send` is a Draft resource, with `message` (Gmail API
   reference). `pending`: verify on the owner's Mac. No engine path calls
   the release before this check (Not in scope). If Gmail sends the older message,
   the check after the send (section 5, step 4) finds the difference,
   and the engine stops each later release.

## Acceptance criteria

1. A reply that the release sends has the `threadId` of the thread, an
   `In-Reply-To` with the parent `Message-ID` and the `Re:` subject at
   fake Gmail. Red if the composer drops a header or the call drops the
   thread ID.
2. With an unknown result of `drafts.send`, the fake Gmail gets exactly
   one `drafts/send` request, also after recovery runs many times. Red if
   any path calls again.
3. A change of the draft at Gmail after the approval (also a new `Bcc`
   only) denies the action, and no `drafts/send` request goes out. Red if
   the release skips the read, the hash or the header check.
4. The compose and parse property test passes for any content that the
   checks accept, and the checks refuse each header injection. Red if a
   CR or LF reaches a header.
5. On the owner's Mac (after R3-02 and R3-03 give a path to send): a
   reply sent from Iris shows in the same thread in Gmail. Red if Gmail
   starts a new thread.
6. With a rate limit answer of `drafts.send`, the fake Gmail gets one
   request only. Red if the client tries again.

## Risks

- A send to the wrong person cannot be undone. Each send goes to review in
  this card, and R3-02 adds the hold.
- Rollback: a migration goes forward only. An older program refuses a
  store of migration 18 (`UnknownSchema`), so a revert of the code alone
  does not start. Two ways back:
  1. Fix forward: a code change turns the verbs off (the command and
     submit refuse `draft` and `send`). No migration removes them: the
     verbs stay in the `CHECK`, and the stored actions, ledger rows and
     the three tables stay as history, so no stored row becomes
     invalid.
  2. Restore the backup copy that the store makes before each migration
     (`iris.db.v17.<time>-<hex>.bak`, spec 1, section 5.5) and run the
     older program. Each change after migration 18 (sync, triage,
     decisions and drafts) is lost from the store; the next sync copies
     the mail again from Gmail. A draft that Iris made at Gmail stays
     there as a normal Gmail draft.
