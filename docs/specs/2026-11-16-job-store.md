# Spec: the job store

- Date: 2026-11-16
- Card: R4-01 (job: data format, store, and the states works, waits for a
  reply, needs you, done)
- Status: Built

## Problem

Release 4 gives a goal to an agent. The manifesto calls this goal a job: "a
goal with limits, for example 'Get the signed contract from Dana before Nov
20.' A job can last minutes or weeks." The workspace builder (R4-02), the job
page (R4-09), the write verbs (R4-03), the wait verb (R5-04) and the ask verb
(R5-05) all read or move a job. Iris has no job yet: spec 2 names a job ID in
the changeset author (`author.job`) and in a policy rule (`job`), but no table
holds a job.

A job lasts longer than one session and longer than one run of the engine. If
the engine stops, the job must not lose its state.

## Goal

1. The store holds each job: the goal, the limits, the state and the history
   of each state change (the events).
2. A job has one of four states: `working`, `waiting` (waits for a reply or a
   date), `needs_you` (waits for an answer from the person) and `done`.
3. The store allows only the moves of the table in [Moves](#moves), with the
   actor that the table names. A move that the table does not allow fails,
   from each path that writes SQL, not only from the Rust API.
4. The state of a job always agrees with its newest event.
5. A job keeps its state, its wait, its question and its events after a
   restart of the engine.
6. One JSON document gives a job and its events, for the API and the open
   model (`docs/spec/schema/job.schema.json`).

## Not in scope

Each of these subjects has its own card:

- The verbs that start and move a job from a session (`iris wait`, `iris
  ask`, `iris done`) and from the web client: R4-03, R4-10, R5-04, R5-05.
  This card gives the store functions that they call.
- The wake: the engine that finds the reply on the wait thread, or the end
  of the wait, and moves the job to `working` (R5-04). This card gives the
  move and the data that the wake reads (`wait_thread`, `wait_until`).
- The sessions of a job and the session socket (R4-04, spec 2 section 8.4).
- The workspace folder (R4-02) and the notes of a job (R5-06).
- The grant inside one job: a policy rule with `job` (spec 2 section 6). The
  policy already reads the job ID from the author.
- The timeline of mail and changesets on the job page (R4-09). The page joins
  the changesets by `changeset.author_job`. This card gives the state events.

## Design

### Data

Migration 14 adds two tables (12 and 13 went to other cards). If another migration merges first, this one
takes the next free number.

`job`: one row for each job.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | The row ID. The engine never uses an ID again (spec 1, 5.7). The short ID is `j-<id>`. |
| `goal` | TEXT NOT NULL | The goal, 1 to 2,000 characters. It does not change. |
| `due_at` | INTEGER | The limit date of the goal, in milliseconds, or NULL. It does not change. |
| `created_at` | INTEGER NOT NULL | Milliseconds. |
| `state` | TEXT NOT NULL | `working`, `waiting`, `needs_you` or `done`. |
| `wait_thread` | INTEGER | The thread of the wait. Only in `waiting`, and optional there. |
| `wait_until` | INTEGER | The end of the wait, in milliseconds. In `waiting` only, and required there. |
| `question` | TEXT | The question to the person. In `needs_you` only, and required there. |
| `end_kind` | TEXT | `complete` or `cancel`. In `done` only, and required there. (`END` is an SQL keyword.) |
| `updated_at` | INTEGER NOT NULL | The time of the newest event. |

`job_event`: one row for each state change. A job has one or more events.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | The order of the events. |
| `job_id` | INTEGER NOT NULL | The job. |
| `at` | INTEGER NOT NULL | Milliseconds. |
| `state` | TEXT NOT NULL | The state after the event. |
| `by` | TEXT NOT NULL | `person`, `agent` or `engine`. |
| `wait_thread`, `wait_until`, `question`, `end_kind` | | The same values as the job row gets. |
| `answer` | TEXT | The answer of the person, on the move from `needs_you` to `working` only. 1 to 10,000 characters. |
| `why` | TEXT | The reason of the move, or NULL. 1 to 2,000 characters. |

The text limits keep a job row small, because a session of an agent writes
the question and the reason. The limits count characters, as SQLite
`length()` does.

A wait thread has no foreign key, because the cleanup of gone mail can delete
a thread row (as `ledger_message`). The wake (R5-04) treats a missing thread
as a wait for the date only. Each wait has an end date, so no job waits
forever.

### Moves

The create is one `INSERT` into `job`. The row must have the state
`working`, no wait, no question, no end, and `updated_at` equal to
`created_at`. The trigger `job_create` then inserts the create event (the
state `working`, by the person, at `created_at`) in the same statement. So
no commit can hold a job with no event.

Each other move is one `INSERT` into `job_event`. The
trigger `job_event_move` checks the move against this table and refuses each
other move with the SQLite error `job: <reason>`. The trigger
`job_event_apply` then copies the state and its values to the job row. A
trigger on `job` refuses each other change of the row. So the state of the
job agrees with its newest event by construction.

| From | To | Who | Name | Values |
|---|---|---|---|---|
| (no job) | `working` | person | create | none (the trigger `job_create` writes the event) |
| `working` | `waiting` | agent | wait | `wait_until` later than `at`, `wait_thread` optional |
| `working` | `needs_you` | agent | ask | `question` |
| `waiting` | `working` | engine, person | wake | none |
| `needs_you` | `working` | person | answer | `answer` |
| `working` | `done` | agent, person | finish | `end` = `complete` |
| `waiting`, `needs_you` | `done` | person | finish | `end` = `complete` |
| `working`, `waiting`, `needs_you` | `done` | person | cancel | `end` = `cancel` |

`done` is final. A job and its events are never deleted and never changed
after the write: the triggers refuse an `UPDATE` or a `DELETE` of
`job_event`, a `DELETE` of `job`, and an `UPDATE` of `goal`, `due_at`,
`created_at` or `id`.

`why` is allowed on each move. The engine writes the reason of a wake in
`why` (for example `reply` or `time`).

The engine does not move a job on its due date. The due date is a limit that
the agent and the person read.

### Concurrency

Each move names the state that the caller read. The Rust API reads the state
and inserts the event in one write transaction, so two moves of the same job
cannot both start from the same state. SQLite has one writer at a time. The
second move reads the new state, and fails if the table does not allow the
move from there.

An answer is a special case: after an answer, the agent can ask again, and
the job is in `needs_you` again. A move table check alone then accepts an
old answer for the new question. So the web client sends the question and
the `updated` time that the person saw, and the answer compares both in the
same write transaction as the move (`POST /api/jobs/{id}/answer` gives 409
on a difference).

### Rust API

A new crate `crates/iris-job`, the same shape as `iris-changeset`:

- `create(store, goal, due, now) -> Result<i64>`: the job row. The trigger
  writes its create event. The actor is the person.
- `wait(store, job, thread, until, why, now)`, `ask(store, job, question,
  why, now)`: the agent moves.
- `wake(store, job, by, why, now)`: `by` is the engine or the person.
- `answer(store, job, text, asked, now)`: the person. `asked` is an
  `Option<Asked>`: the question and the `updated` time of the job document
  that the person saw (card R5-05). With `asked`, the move is refused
  (`Error::Refused`) if the job asks another question now, or asked again
  at another time. With no `asked` (the command `iris job answer`), the
  answer applies to the question that the job asks now.
- `finish(store, job, by, end, why, now)`.
- `get(store, job) -> Result<Job>` and `events(store, job)`.
- `list(store, state) -> Result<Vec<Job>>`: the jobs of one state, newest
  first. The wake (R5-04) reads the `waiting` jobs with this.
- `write_document(store, job, out)`: the JSON document.
- `format_job_id(row)` and `parse_job_id(text)`: `j-<row>`.
- `_in` variants of the moves take a `Connection`, for one transaction with
  other writes, as in `iris-changeset`.

A refusal of a trigger gives `Error::Refused(reason)`. An unknown job gives
`Error::NotFound`.

### The JSON document

`docs/spec/schema/job.schema.json`, `$id` `urn:iris:model:1:job` (version 1 since R6-07).

```json
{
  "model": "iris/1.0",
  "id": "j-142",
  "goal": "Get the signed contract from Dana before Nov 20.",
  "due": "2026-11-20T00:00:00Z",
  "created": "2026-11-16T09:00:00Z",
  "updated": "2026-11-16T09:20:00Z",
  "state": "waiting",
  "wait": { "thread": "t-8841", "until": "2026-11-18T09:00:00Z" },
  "events": [
    { "at": "2026-11-16T09:00:00Z", "state": "working", "by": "person" },
    {
      "at": "2026-11-16T09:20:00Z", "state": "waiting", "by": "agent",
      "wait": { "thread": "t-8841", "until": "2026-11-18T09:00:00Z" },
      "why": "Dana has the contract now."
    }
  ]
}
```

`wait` is present only in `waiting`, `question` only in `needs_you`, and
`end` only in `done`. An event has the same rule for its own state, and
`answer` only on an event of the state `working` that follows `needs_you`.
The schema cannot check the order of the events. The store checks it.

Memory: the events of one job stream from the store into the writer. No list
of events is in memory.

## Options not chosen

- The state in the job row only, with no events: the job page (R4-09) needs
  each step in order, and a state with no history cannot show who moved it.
- The events only, with the state as a query of the newest event: each list
  of jobs by state then needs a sub-query for each job. The copy in the row
  is cheap, and the trigger keeps it the same.
- The checks of the moves in Rust only: a second writer (the wake, the API, a
  later card) could make a move that the table does not allow. The triggers
  hold for each path, as the triggers of the changeset (migration 7) do. They
  are not a security boundary (issue #158): an agent session has no SQL
  access (spec 2 section 8.4).
- A state `stopped` for the Stop control (R4-11): Stop halts the sessions and
  freezes the outbox. It does not end the job. A person ends a job with
  `cancel`.
- `j` as a `Kind` of `iris_store::parse_id`: a job is not a row of `item`,
  and the changeset ID (`cs-`) uses its own parser too.

No parser, protocol client or security code is in this design. JSON output
uses `serde_json`, which the workspace has.

## Failure list

| Input or event | Result | Test |
|---|---|---|
| A move that the table does not allow (state or actor) | `Error::Refused`, no write | Property test: random moves from random states, through the API and through raw SQL |
| A move of a job in `done` | `Error::Refused` | Same property test |
| An `UPDATE` of `goal`, `due_at`, `created_at`, `id` or `state` of `job` with no event | Refused by the trigger | Unit test |
| An `UPDATE` or a `DELETE` of `job_event`, a `DELETE` of `job` | Refused by the trigger | Unit test |
| A raw `INSERT` into `job` | The trigger writes the create event. A row with another state or with a wait, a question or an end is refused | Unit test |
| A raw `INSERT` of a create event (`working` with no earlier event) into `job_event` | Refused: only `job_create` writes the first event | Property test |
| An empty or too long goal, question, answer or reason | Refused by a `CHECK` | Unit test |
| A value that does not fit the job document: a text with a NUL character (SQLite `length()` stops at a NUL), a blob, a time that is not an integer from 0 to the end of the year 9999 in milliseconds, an ID or a thread ID that is not positive | Refused by a `CHECK` | Unit test through raw SQL |
| Text that is not UTF-8, written by raw SQL. SQLite has no UTF-8 check, and the crate binds only Rust strings | The reader of the row (`get`, `list`, `events`, `write_document`) gives an error and no document. No reader stops the engine | Unit test through raw SQL |
| A wait with an end at or before the move | Refused | Unit test |
| An unknown job ID | `Error::NotFound` | Unit test |
| Two moves of one job at the same time | One succeeds. The other gets the new state, and fails if the table does not allow the move from there | Test with two threads |
| A crash during a move | The transaction rolls back. The job keeps its state before the move | SQLite atomic commit; the restart test reopens the store |
| A restart of the engine | Each job keeps its state, its values and its events | Restart test |

All other input fails closed: a refusal and no write.

## Impact

- `crates/iris-store/src/schema_12.sql` and the migration list in
  `crates/iris-store/src/lib.rs`.
- New crate `crates/iris-job`.
- `docs/spec/schema/job.schema.json` and samples in
  `docs/spec/schema/examples/`.
- No change to a screen, the API or the command. No change to a table that
  exists.

## Assumptions

- A job belongs to the one person of the engine, not to an account. Evidence:
  manifesto, "What Iris gives an agent": the goal names a person and a
  matter, not a mailbox. A job can read mail of more than one account.
- `changeset.author_job` holds the short ID `j-<id>` as text (spec 2 section
  5.1, sample `changeset.json`). This card does not check it. R4-03 checks it
  when a session submits.
- The person creates each job (manifesto: "Give a goal to an agent"). Evidence:
  R4-10 "Start a job from a commitment or a conversation". If an agent must
  start a job later, a new migration adds the row to the move table.

## External writes

None. The job store writes only the local store.

## Open questions

None. The build added the index `job_event(job_id, id)` for the events of
one job, in order.

## Acceptance criteria

1. A job keeps its state, its wait and its events after the store closes and
   opens again. Red if a column or an event is not stored.
2. Each move of the table succeeds with its actor, and each other move fails,
   through the API and through raw SQL. Red if a trigger allows one more move.
3. After each successful or refused move, and after a raw `INSERT` into
   `job`, each job has one or more events, and its state equals the state of
   its newest event. Red if the event and the row can differ, or if a job can
   have no event.
4. The document of each state passes `job.schema.json`. Red if the writer
   gives a field that the schema refuses.
5. The samples in `docs/spec/schema/examples/` pass, and the invalid samples
   fail.

## Verify

```bash
cargo test -p iris-job
cargo test -p iris-store
cargo test -p iris-spec
```

## Rollout

The migration runs at the first start of the new engine. It adds tables only.
The store makes a backup before each migration of a database that is not
empty (spec 1 section 5.1).

## Risks

- A later card needs a move that the table does not allow. Then a new
  migration replaces the trigger. The events stay valid.
- Rollback: an engine of an older build refuses a database of a newer schema
  (`Error::UnknownSchema`). Restore the backup that the migration made.
