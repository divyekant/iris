# Spec: the write verbs of a job session

- Date: 2026-11-17
- Card: R4-03
- Status: Draft

## Problem

A person gives a goal and a scope to a job (R4-01, R4-02). The agent of the
job reads the workspace, but it cannot propose a change: the engine socket
takes each request as the author `local` (`crates/iris/src/socket.rs`,
`local()`). Spec 2 (sections 8.1 and 8.2) and the workspace spec ("The verbs
in a session") give the rules of the verbs in session mode, but no code
applies them. Issue #247 says that nothing checks `changeset.author_job`.

## Goal

An agent session of a job can add actions to one draft changeset of its
job, submit it, see it and withdraw it. Each action is a line of the
changeset, and nothing leaves the engine before `submit` (the card). The
engine limits each action to the current grant of the job, at `submit` and
again before each change of a message or an item. The card is done when the
tests of "Acceptance criteria" pass.

## Not in scope

- The session socket `.iris/socket`, the `.iris/` folder, the session ID,
  the peer check and the mode detection of the command (R4-04). R4-04 calls
  the entry point of this card with the author of the session.
- The sandbox (R4-05) and the flags of hostile input (R4-06).
- `iris nudge` in host mode (R3-07). In a session, it is refused, as `draft`
  and `send` are.
- The grant of an account and of a job draft. Until a card defines it, a
  session cannot make a `draft` or a `send` action (spec 2, section 8.2).
- The session verbs `status` and the read verbs `search`, `show` (of a
  message or an item) and `list`. R4-04 answers
  `status` on the session socket, and refuses the read verbs with a known
  limit issue.
- The check that the session is the open session of its job (R4-04,
  `job_session`). The session socket answers only while its session is open.
- `iris wait` and `iris ask` (R5-04, R5-05).
- No migration, no new table, no change to a screen or to the local API.

## Design

### 1. The author of a session

The session socket (R4-04) gives the engine this author:

| Field | Value |
|---|---|
| `kind` | `agent` |
| `name` | The adapter name, for example `claude-code` |
| `session` | The session ID that R4-04 makes, `se-<id>` |
| `job` | `j-<id>`, the canonical job ID (`iris_job::format_job_id`) |

`crates/iris/src/socket.rs` gets one entry point for both sockets:
`answer_as(store, &Author, line, out)`. `answer(store, line, out)` stays,
and calls `answer_as` with `local()`. A request names no author: only the
socket that took the connection names it.

### 2. Checks of the author

`iris_changeset::create_in` and `check_author` apply these rules to an
author with a job (issue #247):

- `job` is a canonical job ID (`iris_job::parse_job_id`), and the job
  exists and is not `done`. Else the create is refused, and each change of
  a changeset by this author (add, revise, submit, withdraw) is refused
  with code 2: a done job changes nothing.
- `kind` is `agent`, and `session` is set. A person, `triage` or `local`
  author has no job.
- A changeset of a job belongs to the job, not to one session: a job runs
  one session at a time (R4-04), and a later session must continue the work
  of an earlier one (a revision after a review comment, spec 2 section 5.5).
  So for an author with a job, `check_author` compares `kind` and `job`
  only. For an author with no job, it compares `kind`, `name` and `session`
  as before. A session of one job cannot change a changeset of another job.
  Spec 2, section 5.5 gets this rule.

A job has at most one draft: one changeset of the job whose newest
revision is not submitted and that is not withdrawn. `create_in` and
`revise_in` refuse a job author with code 2 while the job has a draft
("submit or withdraw the draft cs-N first"). The check and the write are
in one write transaction, so two callers cannot make two drafts.

### 3. The verbs of a session

The engine answers these verbs for a session author. Each other verb of the
socket (`drafts`) is refused with code 2 in a session.

| Verb | In a session |
|---|---|
| `add` | Adds one action. With no `changeset`, it uses the draft of the job, or makes one. The verbs `draft`, `send` and `nudge` are refused with code 3 (denied). |
| `revise` | New verb, in both modes. Starts a new draft revision of a submitted changeset of the same author (`iris_changeset::revise_in`), and is refused while the job has another draft: after a review comment, the agent adds the actions of the new revision with `add` and the `changeset` ID, then submits. The submit replaces the open actions of the older revision (spec 2, section 5.5). R4-08 gives the comment to the agent as a file. |
| `submit` | Submits a changeset of the job, with the grant checks of section 4. In the same transaction, the policy decides each action with the author `agent` (spec 2, section 6.2), never `local`: the socket gives the policy the kind of the author of the request. Each other submit path keeps its author: the web client (`person`) and triage (`triage`). |
| `show` | Shows a changeset only if its `author_job` is the job of the session. Else "no changeset". |
| `withdraw` | Withdraws a changeset of the session. |

A session cannot read a changeset of another job, so a "no changeset"
answer is the same for a changeset that does not exist and for one of
another job.

### 4. The grant

One function gives the grant of a job, and the workspace build uses the
same function: `iris_workspace::grant_in(c, job) -> Grant`. `Grant` holds
the granted message IDs and the workspace item IDs, with the rules of the
workspace spec (each ref grants its list, clean mail only, an item only
when one grant holds all its sources, a commitment or a record only, a
`done` job grants nothing). The build then writes the files of this grant.
So the files and the checks cannot disagree.

The checks of an action of a changeset with a job author:

1. The verb is not `draft` or `send`.
2. Each resolved message of the action (`action_message`) is in
   `Grant.messages`. A thread target resolves at submit to each message of
   the thread that is not spam or trash (spec 2, section 4), so a thread
   with a message outside the grant fails the check.
3. Each item target is in `Grant.items`, and each of its source messages
   is in `Grant.messages`.
4. The job is not `done`.

The engine does the checks at these points:

| Point | Result of a failed check |
|---|---|
| `submit` (`iris_changeset::submit_in`, every path) | The submit fails with code 3 and the reason, and nothing changes. The changeset stays a draft. |
| The checks before the first provider call of a mailbox action (`iris_apply`, `check` and the claim transaction) | The action becomes `denied` by `engine`, with the reason. No provider call. |
| The write transaction before each provider call (`calls`, also after a recovery) | No more calls. The ledger entry becomes `failed` with the reason. The messages of the calls that ran stay `done`, and the undo of a failed entry covers them. |
| The transaction of a state action (`apply_state`) | The action becomes `denied` by `engine`, with the reason. No item changes. |
| The release of a `send` | The action becomes `denied`. A session send cannot pass the submit, so this is a second guard. |

The check of `label` runs before `labels.create` too, because it is part
of the checks before the first provider call. A revoke after that check
can leave a new label in Gmail with no message on it (workspace spec).

SQLite runs one write transaction at a time. A revoke that commits before
the transaction of a call stops the call. A revoke that commits after it
does not stop that call, and the ledger shows the call.

### 5. Cost of a check

`grant_in` reads the list of each active ref, and one message at a time
for the conversation rule (`iris_talk::message`). Memory holds the ID sets
of the scope, as the build does. The time grows with the size of the scope,
and a check runs before each provider call. This is a known limit, with a
GitHub issue: a later card can keep the grant in a table that the scope
and the store triggers keep current.

## Options not chosen

- Check the grant at `add`: the scope can change between `add` and
  `submit`, so the submit must check again. One check at submit is enough;
  the agent sees the result at submit.
- Deny only the actions outside the grant at submit, as other submit
  checks do: the workspace spec says that the submit fails with no change.
  A partial changeset can do a different thing than the agent planned.
- A second grant query only for checks, with no message bodies: two
  definitions of the grant can disagree. One function for the build and the
  checks is safer. The cost is a known limit (section 5).
- A `session` table in this card: R4-04 makes the session, so the session
  data belongs to it.

## Failure list

Supported input: a request line of the socket, from the author that the
socket names (section 1). All other input is refused with code 2, and
nothing changes.

| Input or event | Result | Test |
|---|---|---|
| A request with a target outside the grant | Submit fails with code 3, the changeset stays a draft | Unit test |
| A thread target with one message outside the grant | Submit fails | Unit test |
| An item target with a source outside the grant, or a feed, signal or conversation item | Submit fails | Unit test |
| `draft`, `send` or `nudge` from a session | Refused at `add` (code 3), and at submit for an action from another path | Unit test |
| `revise` or a new draft while the job has a draft | Refused with code 2, nothing changes | Unit test |
| A session submit and a policy rule with `author = "local"` | The rule does not match: the policy reads `agent` | Unit test |
| A changeset of another job, by ID | `show` and `withdraw` say "no changeset", `add`, `revise` and `submit` are refused | Unit test |
| A later session of the same job revises a submitted changeset after a comment | A new revision, and its submit replaces the open actions of the older revision | Unit test |
| A job author for a job that is `done`, or not canonical, or not there | Create refused | Unit test |
| A revoke after submit, before the apply | The action is `denied`, no provider call, no item change | Unit test on the fake Gmail |
| A revoke between two provider calls of one action | The later calls do not run, the entry is `failed` | Unit test on the fake Gmail, 2 calls |
| The job ends (`done`) before submit | Each change by its author is refused (code 2) | Unit test |
| The job ends (`done`) after submit | At the apply, as a revoke: the grant is empty | Unit test |
| A crash after a call, then recovery | The recovery reads, and the next call checks the grant first | Existing recovery tests, plus one with a revoke |

## Assumptions

- The session socket of R4-04 gives the engine the author of the session.
  Evidence: spec 2, section 8.1 ("The socket tells the engine who calls").
  If R4-04 gives the author another way, only the call of `answer_as`
  changes.
- `changeset.author_job` holds `j-<id>`. Evidence: the job store spec,
  "Assumptions", and `iris_job::format_job_id`.
- The policy gives a session changeset no automatic apply that skips the
  checks of the apply: each mailbox action goes through `iris_apply::apply`
  and each state action through `apply_state`. Evidence: `crates/iris/src/engine.rs`,
  the tick.

## External writes

The Gmail calls of `iris_apply` (`labels.create`, `messages.batchModify`,
`messages.trash`). This card adds a check before them, and adds no call.

- Success: as today.
- Definite rejection: as today.
- Unknown result: as today (recovery). The recovery makes no write call.
  The next write call of the action checks the grant first.
- Retry: no call runs two times (spec 2, section 7.2). A call that the
  grant check stops is not a call.

## Acceptance criteria

1. A session adds `archive`, `label`, `close` and `defer` actions to one
   draft changeset. `add` changes only the draft changeset: no action
   state, item state, ledger entry or Gmail state changes before `submit`.
   Red if an `add` makes a second changeset, an action state or a ledger
   row.
2. A submit with a target outside the grant fails, and the changeset stays
   a draft. Red if any action gets a state.
3. A revoke after submit makes the action `denied` before any provider
   call. Red if the fake Gmail gets a call.
4. A session cannot add `draft`, `send` or `nudge`. Red if one is added.
5. A session sees only the changesets of its job. Red if `show` gives
   another job's changeset.
6. A later session of the job revises a submitted changeset, and the
   submit replaces the open actions of the older revision. Red if the old
   actions stay open.
7. A job author for a `done` job cannot make a changeset (#247). Red if the
   create succeeds.

## Rollout

None. No migration. Nothing calls `answer_as` with a session author until
R4-04.

## Risks

- A grant check that is wrong can refuse a good action. The result is a
  refusal with the reason, not a wrong change. Rollback: revert the PR.
- The check time grows with the scope (section 5).
