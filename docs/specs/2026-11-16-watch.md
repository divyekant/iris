# Spec: Watch for a named mail

- Date: 2026-11-16
- Card: R5-07
- Status: Built

## Problem

A person waits for one mail: a visa decision, a contract, a reply from a
bank. Today the person must look for it again and again. The manifesto gives
Iris the job "It watches for an event that you name".

## Goal

A watch gives one notice when the mail arrives. The person and an agent can
start, read and remove a watch with the `iris` command and the local API.

## Not in scope

- Browser and system notices. Card R5-08 does notices by rule.
- A watch that matches more than one time.
- A watch that a model reads. dk chose search words (decision of 2026-11-16).

## Design

A watch is a search text in the syntax of specification 1, section 5.6. The
person tests the text with `iris search` first.

Data: migration 12 adds the table `watch` with `id`, `text`, `created_at`,
`after_message`, `message_id` and `arrived_at`. `after_message` is the
largest message row ID when the watch starts. The ID of a watch is `w-<row>`.

A message is a new arrival for a watch when all of these are true:

1. It matches the search text, and it is not gone.
2. Its row ID is larger than `after_message`. Message row IDs only go up
   (AUTOINCREMENT), so the message came into the mirror after the watch.
3. Its date is at most 1 hour before the watch. So the old mail of a first
   sync or of a full resync cannot match.
4. It has a `body` row, and no `link_check` row. The understanding step
   writes the body, the header and the hostile marks in one write. The link
   check of spec 1 section 6.7 removes the `link_check` row (migration 18:
   mail saved before the mark `link`, new content, and mail that loses the
   label `SENT` or `DRAFT`). So the hostile checks ran. These steps run with
   no model.
5. It has no hostile mark, and its sender row is not `hostile`.
6. It has no label `SENT` or `DRAFT`. A watch is for mail that you get.

The engine tick (each minute) calls `Store::check_watches`. For each watch
that waits, one transaction finds the lowest row ID that is a new arrival and
sets `message_id` and `arrived_at` with `WHERE message_id IS NULL`. So a
watch matches one time only, also with two engine processes.

The command:

| Command | Does |
|---|---|
| `iris watch add "<text>"` | Adds a watch. |
| `iris watch list [--json]` | Each watch, newest first, with the mail that arrived. |
| `iris watch remove <w-id>` | Removes a watch. |

The API: `GET /api/watches`, `POST /api/watches` (body `{"text"}`),
`POST /api/watches/{id}/remove`. The verb and the route call the same
`iris_api` functions.

Limits: a text has 1 to 500 characters. At most 100 watches wait at one time.

## Options not chosen

- A sentence that the model reads: a model call for each mail and each watch,
  and a wrong match is possible. dk chose search words.
- A check in the attention thread (each 10 seconds): the sync runs each
  minute, so the tick of each minute is enough.
- No new parser: the watch uses `Query` of `iris-store` (spec 1 section 5.6).

## Failure list

Supported input: a search text that `Query::parse` accepts, 1 to 500
characters. The text comes from the person or an agent.

| Input or event | Result | Test |
|---|---|---|
| Empty text, text over 500 characters, bad filter | Refused (400 or command error). No row. | `a_watch_needs_a_valid_text_and_a_free_place` |
| A 101st watch that waits | Refused. | same |
| FTS5 operators in the text | Plain words (search escapes them). | `escapes_fts_operators` |
| Mail that was in the mirror before the watch | No match. | `a_watch_gives_one_notice_for_the_first_new_match` |
| Mail with no clean text, hostile, from a hostile sender, sent, draft, gone, or older than the margin | No match. | `a_watch_skips_mail_that_is_not_a_safe_new_arrival` |
| Two matches, or two checks | One notice: the lowest row ID. | `a_watch_matches_the_first_safe_arrival_of_the_search` |
| The cleanup deletes the gone message of a watch that matched | The watch stays `arrived`. `message_id` has no foreign key. | `the_cleanup_of_the_gone_message_keeps_the_notice` |
| A stop during a check | The transaction rolls back. The next tick checks again. | SQLite transaction |
| A stored text that a later syntax refuses | The watch waits. The list shows it. | Code path in `check_watches` |

## Assumptions

- Message row IDs only go up. Evidence: `message.id` is
  `INTEGER PRIMARY KEY AUTOINCREMENT` in `schema_1.sql`.
- A put again of a message keeps its row ID. Evidence: test
  `put_again_keeps_the_id_and_updates_the_index`.
- The body, the header and the hostile marks of write 1 come in one
  transaction. Evidence: `crates/iris-understand/src/store.rs`, write 1.
- Gmail `internalDate` is the time that Gmail got the mail. Evidence: Gmail
  API reference. If it is wrong, the 1-hour margin can drop a late mail.

## Acceptance criteria

- A watch gives one notice for the first new mail that matches. Red if a
  second check gives a second notice.
- Old, sent, draft or hostile mail does not match. Red if one of the guards of
  `first_arrival` goes away.

## Rollout

Migration 12 runs at the first start of the new version.

## Risks

- A phishing mail that only the model finds can match before the model call
  (limit issue). The notice shows the mail with its marks of that time.
- A sender that becomes hostile after the match keeps the notice.

Rollback: remove the verb and the routes. The table can stay.
