# Spec: the `iris wait` verb and the wake of a job

- Date: 2026-11-17
- Card: R5-04
- Status: Built

## Problem

An agent of a job often waits for a person: "Dana has the contract now." The
job store (`docs/specs/2026-11-16-job-store.md`) has the state `waiting` and
the move `wake`, but no verb moves a job to `waiting`, and nothing wakes it.
So a job that waits for a reply stops, and the person must start it again.

## Goal

1. In a session, the agent runs `iris wait --until <day or time> [--reply <t-id>]`.
   The job moves to `waiting`, and the session ends.
2. When a reply comes on the wait thread, or when the wait ends, the engine
   wakes the job and starts a new session of the same agent. The agent
   finds its notes (`notes.md`) and the reason of the wake (`job.json`).
3. A reply that the engine counts is in the grant of the new session.

## Not in scope

- `iris ask` and the answer of the person (R5-05). The memory of a job
  (R5-06): this card uses `notes.md` of the workspace as the notes.
- A wake by the person from the web client.
- A wake on a review comment (R4-08 adds it with the start path below).

## Design

### The verb

`iris wait --until <YYYY-MM-DD or RFC 3339 time> [--reply t-<n>] [--why <text>]`, a verb of a
session only. Host mode gets exit code 2. MCP has no tool for it (`iris mcp`
serves the host).

The session socket verb `wait` takes `until`, `reply` and `why`:

1. `until` has one of two forms (`iris::socket::until_ms`):
   - A day `YYYY-MM-DD`: the start of the day, UTC (`iris_store::day_ms`).
   - An RFC 3339 time with its offset, for example
     `2026-11-18T09:30:00-08:00`, in whole seconds. A fraction of a second
     other than zero gets code 2, because each output of the end writes
     seconds.

   Other text gets code 2. An end at or before now gets code 2.
2. `reply`, if given, must be a thread ID: else code 2.
3. `iris_job::session_wait` checks in one write transaction that the
   session is still open, and that the reply thread is a thread ref of the
   scope that is not revoked, then writes the move: else code 3 and no
   change. A thread that the job cannot read cannot add mail to its grant.
   A session that a revoke or a stop ended between the socket check and the
   move cannot move the job. The trigger of migration 21 ends the session
   with `job_state` in the same transaction, so the start path finds it.
4. The answer: the job, the state `waiting`, `until` (RFC 3339) and
   `reply`. The reap thread sends the accepted answers before the isolation
   stops the agent (`Sessions::reap_one`).

### The wake rule (`iris_workspace::wake_due`)

A waiting job wakes, by the engine, with one of these reasons in `why`:

- `reply`: the wait thread has a reply. A reply is a message of the thread
  that is not in the list of the thread ref yet, not sent by you (no label
  `SENT` or `DRAFT`), and that the workspace can read
  (`iris_workspace::readable`: understood, not gone, not hostile, no hostile
  sender, not waiting for its link check, not the source of a signal). Only
  a thread ref that is not revoked counts.
- `time`: `wait_until` is at or before now.

`reply` has priority. A reply wake adds the replies, and only the replies,
to the list of the thread ref (`iris_workspace::replies_in`), so the
messages that wake the job and the messages that join the grant are the
same set by construction. Then it writes the wake. Both are in one write
transaction, and the transaction reads the rule again, so a move by the
person between the read and the write wins. The rule lives in
`iris-workspace`, next to the grant, because it uses the rule of the build.

Why a reply joins the grant with no step by the person (this replaces the
rule of issue #354 for the wait thread): the person granted the thread, and
the agent asked to wait for its reply. The reply counts only after
understanding wrote its hostile marks and the link check passed, the same
gate as each grant. The R4-06 mark `reads_outside` then flags each later
changeset of the job for review, because the agent read mail that you did
not send.

### The start path (`iris_job::woken`, `Sessions::wake`)

A job needs a session if it is `working`, its newest event is a wake by the
engine, and the last session of the job ended with `job_state` (the move to
`waiting`). A session that starts after the wake becomes the last session.
The rule uses the order of the rows, not the clock, so a clock that goes
back cannot make an old session look new. The
agent is the agent of the last session of the job. The store holds all of
this, so a crash or a restart of the engine between the wake and the start
loses nothing: the next supervisor call starts the session.

`Sessions::wake(now)` runs after each supervisor turn (each second):

1. `wake_due(now)`.
2. For each job of `woken`: skip it while a session of the job is live (the
   session of the wait before its reap) or a launch runs. Else start one
   session with `Sessions::run`. A start that worked is not tried again for
   the same wake. A failed start writes one line in the engine log, and the
   engine tries again after 1 minute, doubled after each failure, at most
   1 hour (issue #557). A wake for a review comment gets one try for each
   comment, as `docs/specs/2026-11-17-review-comments.md` says. The person can
   also run `iris job run`.

`Sessions::resume(job)` starts a session with the agent of the last
session. R4-08 calls it for a working job with a new review comment.

`now` is a parameter, so a test moves the clock.

## Options not chosen

- A new table for wakes: the job row and the events hold the wait and the
  wake already. No migration.
- The person adds each reply (issue #354): the agent wakes and has nothing
  new to read. The hostile gate and the review mark keep the risk low.
- A wake on the `Date` header of the reply: the sender controls it.

## Failure list

| Input or event | Result | Test |
|---|---|---|
| `--until` not a day or an RFC 3339 time, with a fraction of a second, or not in the future | Code 2, the session stays open | `a_reply_on_the_wait_thread_wakes_the_job`, `the_end_of_a_wait_is_a_day_or_an_rfc3339_time` |
| `--reply` not a thread ID, or a thread outside the active scope | Code 2 or 3, the session stays open | same, and `a_wait_needs_an_open_session_and_a_thread_of_the_scope` |
| A revoke or a stop ends the session between the socket check and the move | Code 3, the job stays `working` | `a_wait_needs_an_open_session_and_a_thread_of_the_scope` |
| The supervisor loop of the engine | Wakes the job with its clock | `the_supervisor_loop_wakes_the_job` |
| Mail on the thread that you sent, a draft, gone, not understood, hostile, from a hostile sender, queued for the link check, or the source of a signal | No wake | `no_wake_before_the_end_with_no_reply` |
| Mail that you sent or a signal that comes with a reply | Only the reply joins the grant | `a_reply_wakes_the_job_and_only_the_reply_joins_the_grant` |
| A reply on a thread that the person revoked | No reply wake; the end of the wait still wakes the job; the reply stays out | `a_reply_on_a_revoked_thread_does_not_wake_the_job` |
| The wake comes before the reap of the session of the wait | The start waits for the reap | `a_reply_on_the_wait_thread_wakes_the_job` |
| Two wake calls, or a wake and a move by the person at the same time | One move; the transaction reads the rule again; a second call starts no second session | `the_end_of_the_wait_wakes_the_job_once`, `a_job_waits_three_days_and_continues` |
| A wake by the person | No automatic session | `a_wake_by_the_person_starts_no_session` |
| The engine stops between the wake and the start | The next engine start finds the job with `woken` and starts the session | `the_end_of_the_wait_wakes_the_job_once` (store rule) |
| The start fails (no isolation, a changed `agents.toml`) | One line in the engine log; the job stays `working` with no session; the engine tries again after 1 minute, then 2, 4, up to 60 | `a_failed_start_after_a_wake_is_tried_again_later` |
| The engine is off at the end of the wait | The first supervisor call after the start wakes the job | Same rule as above |

## Impact

- `crates/iris-job`: `woken`, `session_wait` (no migration).
- `crates/iris-workspace`: `wake_due`, `replies_in`.
- `crates/iris/src/sessions.rs`: `Sessions::wake`, `Sessions::resume`, the
  supervisor loop.
- `crates/iris/src/socket.rs`: the session verb `wait`.
- `crates/iris/src/lib.rs`: the command `iris wait`.
- `iris-store`: `day_ms` is public.
- Memory: one set of (job, time) pairs for the start tries, one entry for
  each wake while the engine runs. Each second: one list of the waiting
  jobs and one read of the unlisted messages of each wait thread.

## Assumptions

- The session of the wait ends in the move transaction: migration 21 trigger
  (`docs/specs/2026-11-17-session-launcher.md`, "Sessions in the store").
- The workspace keeps `notes.md` between sessions: `docs/spec/03-job-workspace.md`
  section 2.
- Understanding writes `understood_at` after the hostile marks:
  `crates/iris-understand/src/store.rs`. `readable` needs both.

## External writes

None. The wake writes only the store, and the session sends nothing.

## Acceptance criteria

1. A job waits 3 days and continues: with a fake clock, no wake one day
   later, a wake by the engine with `time` at the end, one new session of
   the same agent, and `notes.md` keeps the text of the agent. Red if the
   wake comes early, or no session or two sessions start.
2. A reply on the wait thread wakes the job before the end, and the reply is
   in the grant. Red if mail that you sent wakes it.

## Verify

```bash
cargo test -p iris-workspace --test wake
cargo test -p iris --test engine_sessions -- wait
```

## Known limits

- A reply on a thread that only an item ref grants does not wake the job:
  `--reply` needs a thread ref.
