# Spec: the write view

- Date: 2026-11-17
- Card: R3-04 (write view: write a new mail or a reply, and send it from
  Iris)
- Status: Draft

## Problem

Iris can send mail (R3-01), hold a send in the outbox (R3-02) and check
a send (R3-03). But only the `iris` command can make a draft and a send,
and each one needs two changesets and two reviews. The web client has
no way to write a mail. The person still writes and sends mail in Gmail.

## Goal

1. The person writes a new mail or a reply in the web client. One press
   of Send is the approval of the person. The mail then goes to the held
   outbox, with no other step of the person.
2. The person can stop the mail at each step before the release claims
   it.
3. A reply goes to the parent that the person saw. If the mirror has a
   newer mail in the thread, Iris refuses the send and says so. The check
   reads the mirror, not Gmail: a mail that Gmail got after the last sync
   (60 seconds or less) is not seen. This is a known limit.
4. The person sees each warning of the send checks (R3-03) before the
   press that approves the send.
5. A second try of one press (for example, after a lost answer) makes no
   second mail.
6. Each Gmail write keeps the ledger, the hold, the send switch, the
   checks and the recovery of R3-01, R3-02 and R3-03. This spec adds no
   Gmail call.

## Not in scope

- The intent path: the person writes what the mail must say, and Iris
  writes the draft in the voice of the person. It needs R3-05
  (`iris-voice`, PR #292). It comes in a second client PR of this card,
  through the engine. The client never calls a model.
- A change of an Iris draft, and its undo (issue #238). A press of Send
  makes a new draft each time.
- A check of the parent at Gmail at the press. The parent check reads the
  mirror (goal 3).
- Reply all, a `Reply-To` header of the parent, attachments, HTML, `Bcc`,
  display names in the recipients and send-as aliases. Each one gets a
  limit issue.
- A list of Iris drafts with no send. A write always asks for a send.
- A change of the send switch from the web client. The switch stays a
  command on the owner's machine (held outbox spec, section 3).

## Design

### 1. The flow

1. The person opens `#/write` (a new mail) or `#/write/t-N` (a reply in
   the thread `t-N`). The mail view (`#/mail/m-N`) gets a Reply link to
   `#/write/t-N` of its thread.
2. The person presses Send. The client sends `POST /api/write`
   (section 2).
3. In one transaction, the engine makes a changeset of the author
   `person` with one `draft` action, submits it, approves it as the
   person, and writes the send mark of the action (section 3).
4. The sync thread of the account runs the apply step (held outbox spec,
   section 4). Step 2 applies the `draft` action, and Gmail makes the
   draft (R3-01, section 4).
5. A new step 2a of the apply step makes the send of each marked draft
   (section 3). Step 3 moves the send to `held`.
6. The release sends the mail when the hold ended and the switch is on
   (R3-02).
7. The client shows the state of the write until the mail leaves
   (section 4).

The person approves twice in the review of the `iris` command: the draft,
then the send. In the write view, the press of Send approves both. The
send approval binds to the hash of the draft that the approved `draft`
action made (section 3). So the person approves exactly the content that
the person wrote, and nothing else can go out under that approval.

### 2. `POST /api/write`

The body is a JSON object with unknown fields refused:

| Field | New mail | Reply | Rule |
|---|---|---|---|
| `account` | yes | no | `a-N` of an account |
| `thread` | no | yes | `t-N` |
| `parent` | no | yes | `m-N`: the parent that the person saw (section 5) |
| `to` | yes | yes | list of addresses (R3-01, section 1) |
| `cc` | yes | yes | list of addresses, can be empty |
| `subject` | yes | no | R3-01, section 1. Iris sets the subject of a reply. |
| `body` | yes | yes | R3-01, section 1 |
| `key` | yes | yes | 16 to 64 characters of `A-Z`, `a-z`, `0-9` and `-`. The client makes one random key for each form content (section 6). |
| `flags` | yes | yes | The warnings that the client showed to the person at the press, as flag names (R3-03). Can be empty. |

The engine, in one transaction of `iris_changeset::transaction`:

0. Looks for a mark with the same `key`. If one exists and its
   `request_hash` (the SHA-256 of the target, the parent and the args of
   the request) is the hash of this request, the answer is 200 with the
   write of that mark, and nothing is written. If the hash is different,
   the answer is 409 "This key belongs to another mail.".
1. Makes a changeset of the author `person`.
2. Adds one `draft` action, with the target `{"accounts": ["a-N"]}` or
   `{"threads": ["t-N"]}` and the args `to`, `cc`, `body`, and `subject`
   for a new mail.
3. Submits it with the reason "Written in the write view.".
4. For a reply, reads the parent that the submit resolved
   (`iris_changeset::parent`). If it is not `parent`, the transaction
   ends with no write, and the answer is 409 "A new mail came into this
   thread. Read it, then send again."
5. If the submit denied the action, the transaction ends with no write,
   and the answer is 400 with the reason of the denial (for example, an
   address that is not valid).
6. Compares the flags of the action (the submit computes them, R3-03)
   with `flags`, as sets. If they are not the same, the transaction ends
   with no write, and the answer is 409 with the text "Look at the
   warnings, then press Send again." and the flags of the action. The
   client shows them (section 6), and the next press sends them.
7. Approves the action as the person, with its hash (`approve_in`), as
   the state verbs do (`crates/iris-api/src/verbs.rs`).
8. Writes the send mark (section 3) with `key`, the request hash and the
   flags.

The answer is 201 with `{"write": "cs-N"}`, the ID of the changeset.
The key makes the request safe to try again: the one write connection
of the store runs step 0 and step 8 in one transaction, and the key is
`UNIQUE` in the store, so two tries of one key make one mark. A new press
with a changed form content has a new key, and makes a new mail.

### 3. The send mark and step 2a

Migration (the next free number) adds the table `write_send`:

```sql
CREATE TABLE write_send (
  -- The approved `draft` action of a write.
  action_id INTEGER PRIMARY KEY REFERENCES changeset_action(id),
  -- The `send` action that step 2a made, or NULL before step 2a.
  send_action_id INTEGER UNIQUE REFERENCES changeset_action(id),
  request_key TEXT NOT NULL UNIQUE,
  request_hash TEXT NOT NULL,
  -- The flags that the person saw at the press, as a JSON list.
  flags TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
```

A trigger refuses an insert unless the action has the verb `draft`, the
state `approved`, `decided_by = 'person'` and a changeset of the author
`person`. A trigger refuses an update other than `send_action_id` from
NULL to a `send` action, and a trigger refuses each delete. So only the write path can make a mark, and a
mark cannot move to another action.

Step 2a of the apply step (`iris_changeset::send_written(store, account,
now)`) runs after step 2 and before step 3. For each mark of the account
with `send_action_id IS NULL`, whose draft row exists (the draft row has
the `action_id` of the mark), oldest first, in one write transaction:

1. Read the mark again with `send_action_id IS NULL`. If another step
   made the send first, end with no write. All writes go through the one
   write connection of the store, so the read and the update of steps 1
   and 6 cannot interleave with another writer.
2. If the changeset of the `draft` action is `withdrawn`, or the draft
   row has `foreign_at` or `sent_at`, make no send. Set nothing, and skip
   the mark: the person stopped the write or sent it in Gmail. The mark
   stays with no send; section 4 shows "Stopped".
3. Make a changeset of the author `person` with one `send` action of the
   draft (`{"drafts": ["d-N"]}`), and submit it with the reason "Written
   in the write view.". The submit computes the flags of R3-03.
4. If the submit denied the send, keep the denied action, and go to step
   6. The write state shows its reason.
5. If each flag of the send is in the flags of the mark, approve the send
   as the person, with its hash. The action hash covers the `hash` of the
   draft row (R3-01, section 5). The draft row is the result of the
   approved `draft` action, made by the engine with no other input. If
   the send has a flag that the person did not see (for example, a
   `new_recipient` that changed after a sync), move the send to
   `in_review` (`decide_in`, by `engine`, with the reason "The warnings of
   the mail changed after the press of Send."). The person then decides it
   on the review screen, with its warnings.
6. Set `send_action_id` of the mark to the send action.

`decided_at` of the send is the time of step 2a, so the hold of 60
seconds starts when the draft exists at Gmail and the send is in the
outbox. The person can cancel it there for the full hold.

A crash before the commit of step 2a leaves the mark with no send, and
the next apply step makes it. A crash after the commit leaves the send
approved, and step 3 holds it. So each mark gets at most one send.

### 4. The state of a write

`GET /api/write/{cs}` gives the state of the write `cs-N`. `cs-N` must
be a changeset with a send mark. Other IDs give 404.

| State | When | Fields |
|---|---|---|
| `saving` | The `draft` action is `approved` and has no draft row yet, or the draft row exists and step 2a did not run | none |
| `waiting` | The send is `approved` or `held` | `draft` (`d-N`), `leaves_at` (the end of the hold, `null` while the switch is off), `sending` (the switch state) |
| `review` | The send is `in_review` (section 3, step 5) | `draft`, `reason` |
| `sent` | The send is `applied` | `draft` |
| `stopped` | The `draft` action or the send is `denied`, `failed`, `cancelled` or `expired`, or step 2a skipped the mark (section 3, step 2) | `reason`, `draft` if a draft exists |

A send in `held` with a ledger row in `writing` is `waiting` with no
cancel: the outbox already says "The send started. It cannot be
cancelled." when the person tries.

The stop of a write:

- In `saving`, before the draft exists: `POST /api/changesets/{cs}/withdraw`
  (R2-14). The withdraw cancels the approved `draft` action if it has no
  ledger row. If the apply already claimed it, the draft gets made, and
  step 2a skips the mark (section 3, step 2). The draft stays in Gmail
  drafts, because Iris never deletes a draft (R3-01).
- In `waiting`: `POST /api/outbox/{d-N}/cancel` (R3-02).
- In `review`: the deny of the review screen (R2-06).

### 5. The reply form

`GET /api/threads/{t}/reply` gives the start values of a reply in the
thread `t-N`:

```json
{"account": "a-1", "parent": {"id": "m-9", "from": {"name": "Priya Shah",
 "address": "priya@example.com"}, "date": "...", "text": "..."},
 "to": ["priya@example.com"], "cc": [], "subject": "Re: Q4 numbers"}
```

- `parent`: the message that submit would resolve now. One function,
  `iris_changeset::reply_parent(c, thread)`, gives it to the submit and
  to this route, so both use the same rule (R3-01, section 3). `text` is
  the clean text of the parent, cut to 600 characters on a character
  boundary, or `null`.
- `to`: the `From` address of the parent. If the `From` address is the
  address of the account (the person wrote the newest mail), `to` is the
  `To` addresses of the parent. Addresses that do not pass the address
  check of R3-01 are left out. The person can change `to` before the
  press.
- `subject`: the subject that the apply will set (R3-01, section 3), for
  the screen only.
- 404 if the thread does not exist, 409 "This thread has no mail to
  reply to." if it has no parent.

The new mail form takes the accounts from `GET /api/status`.

### 6. The write view (client)

`client/src/views/Write.svelte`, with the layout that the owner picks on
the before/after page. Rules for each layout:

- The recipients are chips. A chip is made when the person types a comma,
  a space, Enter or leaves the field. The client checks the form of an
  address only to mark a chip that is not valid. The engine decides.
- Send is on when `to` has one valid chip and (for a new mail) the
  subject has text. It is off while a request runs.
- The client makes a new random key (`crypto.randomUUID()`) when the
  form content changes, and keeps it for each press of the same content.
- On 409 with flags, the view shows each warning above the Send button,
  with the words of the outbox (`FLAGS`), and keeps the text. The next
  press sends these flags.
- After 201 or 200, the view shows the state of section 4, read again each 2
  seconds while it is `saving` or `waiting`, with the same poll rules as
  the outbox (`clock.ts`, reads numbered at start, only the newest
  successful read counts).
- On 400 or 409, the form stays with all text, and the reason shows
  above the Send button.
- On no answer or a 5xx, the form stays, and the view says: "Iris does
  not know if it took the mail. Press Send again: Iris sends it only
  once." The next press uses the same key.
- The text of the form stays in `sessionStorage` for the route until a
  201 or Discard, so a reload or a move to another view keeps it. The
  storage ends with the browser tab.
- The mail text that the client shows (the parent) is data: Svelte
  escapes it, as in the mail view.

### 7. The apply step wakes sooner

The sync thread sleeps up to 60 seconds between turns. A written mail
must not wait a full minute in `saving`. The sync thread wakes each
second, and runs only the apply step (no sync) when a mark was made after
the start of its last apply step (`iris_changeset::written_since`). So
each mark wakes each sync thread at most one time, also when its apply
fails. The check is one query of an index on `write_send.created_at`, so
it adds no measurable memory.

## Options not chosen

- Two presses (save a draft, then send it): it shows the engine steps to
  the person. Rejected by the design rule "it just makes sense".
- One changeset with a `draft` and a `send` action: a `send` targets a
  draft row, which does not exist at the submit. It needs a new target
  kind in spec 2 and the open model.
- The client makes the send after the draft exists: a closed tab leaves
  an approved draft with no send. The mark keeps the intent in the store.
- A direct Gmail call from the API: the API has no Gmail client, and the
  ledger and the lock live in the apply step.
- Libraries: no new parser or protocol code. The address and content
  checks are the ones of `iris-compose` (R3-01).

Supported input: the body of section 2, from the signed-in local client.

| A bad address, a long subject, a body over 256 KiB | The submit denies; 400 with the reason; nothing written | API test |
| An account or a thread that does not exist | The submit denies; 400; nothing written | API test |
| An account that needs a new sign-in | The write stays `saving` until the sign-in, as each apply (held outbox spec, section 4); the person can withdraw it | step test |
| A newer mail in the thread than `parent` | 409; nothing written | API test |
| Two tries of one press (a lost answer, then a new press) | One mark: the second try gets 200 and the first write | step test |

| A warning that the client did not show | 409 with the flags; nothing written | step test |
| A send with a flag that the press did not have | The send goes to `in_review`; it does not leave | step test |

## Assumptions

1. A person approval from the signed-in local client is the person:
   the review screen and the state verbs already approve this way.
   Evidence: `crates/iris-api/src/verbs.rs`, `review.rs`.
2. `approve_in` accepts an action in `proposed` (no review step).
   Evidence: `verbs.rs` approves right after the submit.
3. The draft row is made only from the approved `draft` action, with no
   other input. Evidence: `crates/iris-apply/src/send.rs`, `created`.
   The refresh of R3-01, section 4.1 changes a draft row only at the
   release, so it cannot run before step 2a makes the first send.
4. The submit resolves the parent with the same rule as
   `reply_parent`: the build moves the SQL of the submit into
   `reply_parent`, so one function holds the rule.

## External writes

None new. The `drafts.create` and `drafts.send` calls keep the results
of R3-01 (success, rejection, unknown result, retry) and the hold, the
switch and the cancel of R3-02.

## Open questions

- The cut of the parent text (600 characters) can change after the
  owner sees the screen.

## Acceptance criteria

1. A new mail written in the view, with the switch on, leaves after the
   hold, through the fake Gmail. Red if any step of section 1 breaks.
2. A reply goes into the thread with the parent that the form showed.
   Red if `parent` is not checked (a new mail in the thread must give
   409).
3. A withdraw in `saving` and a cancel in `waiting` each stop the mail.
   Red if step 2a makes a send for a withdrawn changeset.
4. Each mark gets at most one send, also with two step 2a runs and a
   crash. Red if the read of step 1 is outside the write transaction.
5. A second try of one key makes no second mail. Red if step 0 is
   missing.
6. A send with a warning that the person did not see goes to review.
   Red if step 2a approves it.
7. The view keeps the text after a 400 or a reload. Red if the storage
   is cleared before the 201.

## Rollout

The migration runs at the next start. Sending stays off until the owner
runs `iris sending on` after the Mac check (#302). Until then a written
mail waits in the outbox.

## Risks

- A mail goes out that the person did not mean: each mail needs a press
  of Send, then waits 60 seconds in the outbox with a cancel, and the
  send switch is off by default.
- Rollback: revert the client PR to hide the view. The engine routes
  then have no caller. A mark with no send stays harmless: step 2a only
  makes a send that the person asked for.

## Spec checks

- [x] Each assumption holds with a second caller, worker or tab: two
  presses make two mails on purpose; two step 2a runs make one send.
- [x] Each assumption holds when an outcome is unknown: a lost answer of
  `POST /api/write` is safe to try again with the same key.
- [x] Each dropped mechanism was dropped for a reason that makes it
  unnecessary: the second review of the send binds to the draft that the
  approved action made.
- [x] Each "idempotent" step is not check-then-act: step 2a reads and
  writes the mark in one write transaction on the one write connection.
- [x] Each property has a test (failure list).
- [x] The hardest problem is the second approval with no second press;
  section 3 binds it to the draft hash.

- [x] The assumptions do not contradict each other.
- [x] The failure list names the supported inputs and the safe result.
